01Algorithms vs patterns

Algorithms, together with the data structures from chapter 4, are the base of every computational application. Before we parallelize a code, it pays to think hard about the key algorithms inside it, because the choice of algorithm often decides how far the code can scale. This chapter separates two ideas that people often mix up.

Parallel algorithmA well-defined, step-by-step procedure that emphasizes concurrency to solve a problem. Examples: sorting, searching, optimization, matrix operations.
Parallel patternA concurrent, separable fragment of code that shows up again and again in different programs. On its own it does not solve a complete problem. Examples: reductions, prefix scans, ghost cell updates.

The same procedure can be an algorithm in one program and a pattern in another. What matters is its role: if it achieves the main goal, it is an algorithm; if it is only one part of a bigger computation, it is a pattern. Learning to spot “parallel-friendly” patterns early makes later parallelization much easier.

The chapter returns to three patterns: the prefix scan (section 11 here), the reduction (section 12), and ghost cell updates (covered later in the book, in chapter 8).

02Learning objectives

After this reading you should be able to:

  • explain algorithmic, computational (step) and time complexity, and the notations Big O, Big Ω and Big Θ;
  • build a simple performance model that counts cache line loads and use it to compare a linear search with a bisection search;
  • explain why non-comparison algorithms such as the hash sort break the O(N log N) limit and parallelize well, even on GPUs;
  • define hash, bucket, perfect hash, minimal perfect hash, compact hash, load factor, collision and open addressing;
  • describe how a spatial hash is used for neighbor finding, remapping, table lookup and sorting on AMR meshes;
  • compute inclusive and exclusive prefix sums, and compare the step-efficient, work-efficient and large-array scan algorithms;
  • explain why parallel global sums are not reproducible and name the enhanced-precision fixes (long double, pairwise, Kahan, Knuth, quad precision);
  • list the traits that make an algorithm suitable for highly parallel hardware.

03Algorithmic complexity

The development of parallel algorithms is a young field, and even its vocabulary still comes from the serial world. The traditional way to evaluate an algorithm is its algorithmic complexity.

DefinitionAlgorithmic complexity is a measure of the number of operations it takes to complete an algorithm. It is a property of the algorithm itself: the amount of work in the procedure.

Complexity is written in asymptotic notation, which gives the limiting bounds of performance: does the run time grow linearly with the problem size, or faster? N is the size of a long array (the number of cells, particles or elements), and O() can be read as “scales on the order of”. Leading constants are dropped by convention. Rules of thumb:

  • a simple loop over N items is O(N);
  • a doubly nested loop over N items is O(N²);
  • a tree-based algorithm is O(N log N).
OBig OThe worst case limit of an algorithm’s performance. A doubly nested loop over an array of size N is O(N²).
ΩBig OmegaThe best case performance of an algorithm.
ΘBig ThetaThe average case performance of an algorithm (the meaning used in this book).
Notation in this chapterThe book associates O with worst case, Ω with best case and Θ with average case. The quiz explicitly asks for that usage. Formally, these symbols mean upper, lower and tight asymptotic bounds; each can describe a specified best, average or worst case. A bound alone does not identify the case. The tree example above is a rule of thumb, not a statement about every tree operation.

Two adjusted definitions for parallel hardware

Traditional texts use algorithmic, computational and time complexity as synonyms. On modern parallel hardware time does not scale with the amount of work, so the book separates them:

Computational complexity (step complexity)The number of steps needed to complete the algorithm. It depends on the implementation and the hardware and includes the available parallelism: on a vector or multi-core machine one step (cycle) can be four or more floating-point operations.
Time complexityTakes into account the actual cost of an operation on a modern computer. The biggest adjustment is the cost of memory loads and caching.
LimitationAsymptotic complexity is one-dimensional. It only tells you how the cost grows in the limit of very large N; it gives no equation for the absolute run time of a real problem of finite size. For that we need a performance model.

04Performance models

A performance model (introduced in chapter 4) describes an algorithm’s performance much more completely than complexity analysis. The biggest difference: we do not hide the constant multiplier. Logarithms are also written exactly: a binary tree really costs log2 N, not just “log N”. In complexity analysis such differences are constants that disappear, but in real-world problems they do not cancel out, and they decide which of two similar approaches is faster.

Example · conference registration You must hand registration packets to 100 participants.
  1. Unsorted folders. Participants line up and for each one you search the 100 folders. Worst case 100 looks, average 50, and 100 if the packet is missing. N participants × N folders is a doubly nested loop: O(N²). Even if the folders shrink as packets are handed out, N + (N−1) + (N−2) + … is still O(N²).
  2. Presorted folders. Sort the packets alphabetically before registration and use a bisection search for each person: O(N log N) in the worst case.

Asymptotic analysis describes one million participants, but the conference has 100. For finite sizes we need a fuller picture.

Bisection search vs linear search, counted in cache lines

Find an entry in a sorted array of 256 four-byte integers. A cache line is 64 bytes, so it holds 16 integers and the whole array is 16 cache lines.

ModelLinear searchBisection (binary) searchRatio
Count operations (steps)worst 256, average 128log2 256 = 8~16× slower
Count cache line loadsworst 16, average (256/16)/2 = 8log2(256/16) = 4only ~2× slower

The time-based model assumes that work on data already in cache is almost free (a couple of cycles), while loading a cache line costs about 100 cycles. So we count only cache line loads and ignore the comparisons. Bisection is still faster, but only about 2×, not the 16× that operation counting promises.

Several more effects can even make the linear search win:

  • a linear algorithm is much easier to parallelize than a logarithmic one;
  • hardware is built to walk linearly through an array and prefetch the next data;
  • if the item sits near the beginning of the array, bisection does much worse than a linear search.
Parallel twist · 32 threadsRun the search on 32 threads of a multi-core CPU or GPU. The threads must wait for the slowest one in each operation. Bisection always costs 4 cache loads, but the linear search varies per thread, and the worst thread controls the time, so the cost is closer to 16 cache lines than to the average of 8.

The book tests this in a real table lookup (listings 5.1 and 5.2). The linear version is a short, cache-friendly loop; the bisection version calls a small helper:

Bisection helper used for the table lookup (listing 5.2)

int bisection(double *axis, int axis_size, double value)
{
   int ibot = 0;
   int itop = axis_size+1;
   while (itop - ibot > 1){          // halve the range each pass
      int imid = (itop + ibot) /2;
      if ( value >= axis[imid] ) ibot = imid;
      else                        itop = imid;
   }
   return(ibot);
}

Spoiler (figure 5.8 later): the bisection search turns out to be no faster than the linear search in that test. But the analysis also shows that the linear search is not as slow as you might expect.

05Comparison sort vs hash sort

This example shows that an approach that is comparison-free and less synchronous is easier to implement and faster on highly parallel hardware.

Comparison sort (bubble sort)
  1. Each person compares their last name with their neighbor in the row and moves left if their name comes earlier, right if later.
  2. Repeat for up to N steps.

Think of each auditorium row as a GPU workgroup. Workgroups cannot communicate with each other, so at the end of a row you must exit the kernel to compare with the next row. Many kernel invocations add code complexity and run time.

Hash sort
  1. Put a sign for each letter at the front of the room.
  2. Each person goes to the table with the first letter of their last name.
  3. For crowded letters, repeat with the second letter; for small groups use any simple sort.

No one compares with anyone. Every person acts independently.

A bubble sort steps through the list, compares adjacent elements and swaps them if they are out of order, repeating until sorted, and it generally performs poorly. Even the best comparison sort has a complexity limit of O(N log N). The hash sort breaks this barrier because it uses no comparisons: on average it is Θ(1) per participant and Θ(N) for all. More important for us, the operation for each participant is completely independent, so it parallelizes easily, even on less synchronous GPU architectures.

Putting it togetherHash-sort both the participants and the folders, then open several registration lines split by alphabet. Two hash sorts are Θ(N); with P processors the work becomes Θ(N/P). For 16 processors and 100 participants the speedup over the serial brute-force method is 100² / (100/16) = 1,600×. This is exactly how well-organized conferences and school registrations run.

06Hash functions

Hashing techniques date from the 1950s and 60s. A hash function encodes a key into a hash used to locate a bucket (or bin). A hash table uses that location and, when necessary, key comparisons and collision handling to retrieve the associated value. The chapter uses a dictionary analogy: a last name is the key and a username is the value. Distinct keys can hash to the same bucket, so hashing alone does not guarantee uniqueness. The best hash design is usually problem-specific.

Perfect hashAt most one entry in each bucket. Simple to handle (no collisions) but can take more memory.
Minimal perfect hashExactly one entry in each bucket and no empty buckets. Slower to compute; worth it for fixed key sets such as programming-language keywords.
Compact hashCompresses the hash so it needs less memory. Both the key and the value are stored, so on retrieval the key can be checked.
Load factorThe fraction of the hash that is filled: n/k, entries divided by buckets. Compact hashes still work at 0.8–0.9; above that collisions hurt efficiency.
CollisionMore than one key wants to store its value in the same bucket. A good hash function spreads keys uniformly, which avoids clustering and allows higher load factors.

Most hashes in this chapter are created on the fly, queried and thrown away, so a fast creation time matters more than memory size. As always, there are trade-offs between programming complexity, run time and memory.

Why the first letter is a weak hashLast names are not evenly distributed across the alphabet, so buckets get unequal numbers of entries. Using the integer representation of the first four letters is not great either: letters give only 52 possible values of the 256 per byte, so only a fraction of the integer keys are used. A hash function designed for characters needs far fewer storage locations.

07Spatial hashing & adaptive mesh refinement

Scientific simulations often use meshes that are finer only where detail matters. In the Krakatau wave example, the team wants high resolution at the wave front and the shoreline but not elsewhere, so they choose adaptive mesh refinement (AMR). (Image analysis could profit from the same idea: when a cell has mixed characteristics, just split it.) The biggest obstacle is that such meshes make the code more complicated and need new techniques that scale on parallel hardware.

Cell-based AMR belongs to the unstructured mesh techniques. The cell data arrays are one-dimensional and can be in any order; extra arrays carry each cell’s size and location. A fully unstructured mesh goes further, with triangles or polyhedra that “fit” the land/ocean boundary at the cost of more complex numerics. AMR methods come in three kinds: patch, block and cell-based; patch and block methods still exploit some regular structure, while cell-based data is truly unstructured.

The CLAMR mini-app (shallow water, cell-based AMR) was written by summer students at Los Alamos in 2011 to see if cell-based AMR could run on GPUs. They found breakthrough parallel algorithms that also made the CPU code faster. The most important one was the spatial hash.

What a spatial hash is

Spatial hashing uses a key based on spatial information: objects are mapped onto a grid of buckets arranged in a regular pattern. Each lookup keeps the average complexity of Θ(1), every spatial query can be done with a spatial hash, and many are much faster than the alternatives.

  • Bucket size follows the characteristic size of the objects: for a cell-based AMR mesh, the minimum cell size; for particles, the interaction distance. Then only the immediately adjacent buckets need to be checked for interactions or collisions.
  • AMR and unstructured meshes are called differential discretized data: cells get smaller where gradients are steeper. There is a limit to how small they get, which keeps buckets from becoming too small.
  • Meshes store their cell indices in all the buckets under each cell; particles and objects store their indices or identifiers.
  • Collision detection is a big application area: smooth particle hydrodynamics, molecular dynamics, astrophysics, and also game engines and computer graphics.

Because only neighbors are visited, the cost per particle no longer grows with the size of the domain: particle interactions stay Θ(N) instead of Θ(N²).

Particle interaction pseudo-code (listing 5.3)

forall particles, ip, in NParticles{
   forall particles, jp, in Adjacent_Buckets{       // not all particles!
      if (distance between particles < interaction_distance){
         perform collision or interaction calculation
      }
   }
}

08Perfect hashing: neighbor finding

With a perfect spatial hash we can guarantee only one entry per bucket, so we never handle collisions. The book studies the four most important spatial operations (code at github.com/lanl/PerfectHash, CPU and OpenCL versions):

Neighbor findingLocate the one or two neighbors on each side of a cell.
RemappingMap another AMR mesh onto the current AMR mesh.
Table lookupFind the intervals in a 2D table for interpolation.
SortingA 1D or 2D sort of the cell data.

Neighbor finding is one of the most important operations: material leaving one cell has to enter the neighboring cell, and in image analysis the neighbors say a lot about the current cell.

CLAMR mesh rules. Across a cell face there can be at most a one-level jump in refinement (this is called a graded mesh). Each cell stores just one neighbor per side: the lower one of a pair on the left/right, and the left one of a pair on the bottom/top. The other one of the pair is found through the first, e.g. ntop[nlft[ic]].

Ways to find neighbors

MethodIdeaComplexity
Naive searchCompare i, j, level of every other cell. Fine for few cells, explodes quickly.O(N²)
k-D treeSplit the mesh into two equal halves in x, then in y, repeat until the object is found. Best for large irregular objects, search from the root.O(N log N)
QuadtreeFour children per parent, one per quadrant, which matches AMR subdivision exactly. For a near neighbor of similar size, start at the leaves; with a graded mesh you go up at most two levels.O(N log N)
Spatial perfect hashWrite cell numbers into a fine grid, then read the neighbor location.Θ(N)

Trees are comparison-based and work on CPUs, but comparisons and tree construction are hard on GPUs, where comparisons beyond the workgroup are difficult. (A truncated quadtree starts from the coarsest mesh level with one quadtree per coarse cell instead of from a single root.)

The spatial hash algorithm

No collisions are possible if the buckets are the size of the finest cells:

  1. Allocate a spatial hash the size of the finest level of the AMR mesh.
  2. Write phase: each cell writes its cell number to all hash buckets underneath it.
  3. Compute the index of a finest-level cell one cell outside the current cell on each side.
  4. Read phase: read the value in that bucket. That is the neighbor.

Write phase on the CPU (listing 5.4, shortened)

for(int ic=0; ic<ncells; ic++){            // GPU: this loop disappears
   int lev = level[ic];
   for (int jj=j[ic]*levtable[levmx-lev]; jj<(j[ic]+1)*levtable[levmx-lev]; jj++)
      for (int ii=i[ic]*levtable[levmx-lev]; ii<(i[ic]+1)*levtable[levmx-lev]; ii++)
         hash[jj][ii] = ic;                      // cell number into every bucket it covers
}

On the GPU (OpenCL, listings 5.5 and 5.7) the code is almost the same. The biggest difference is that there is no cell loop: the kernel launch handles the outer loop, and each thread gets its cell index with get_global_id(0). A guard if (ic >= isize) return; keeps threads from reading past the end of the arrays. The read phase simply reads hash one cell to the left, right, bottom and top, using MAX/MIN to stay inside the mesh.

Results (NVIDIA V100 GPU vs one core of a Skylake Gold 5118 CPU, “Best(2018)” comparison):

  • the hash on one CPU core was about an order of magnitude faster than the k-D tree (66×);
  • the GPU added another order of magnitude, for a total of 3,157×;
  • the GPU port took less than a day; the k-D tree would take weeks or months on the GPU;
  • the hash code is about a dozen lines, while the k-D tree code is about a thousand lines.

This is not a CPU vs GPU contest: using all 24 virtual cores of the CPU would also give a big parallel speedup.

09Perfect hashing: remap, table lookup, sort

Remap

A remap moves values from one mesh to another, so different physics can run on meshes optimized for their needs. The setup is identical to neighbor finding, but the hash is built for the source mesh. In the read phase each target cell queries the hash buckets underneath it and sums the source values, adjusting for the size difference of the cells (dividing by 4 for each level of difference in 2D).

Table lookup

A 51×23 table of equation-of-state values with density and temperature axes, equally spaced. n = axis length, N = number of lookups. Three algorithms:

  • Linear search (brute force): O(n) per query, O(N·n) in total;
  • Bisection: O(log n) per query;
  • Hash: O(1). Because the axes are equally spaced, the interval is just (value − axis[0]) / increment, an arithmetic expression with no conditionals.
The surprise, explainedThe simple model predicted 4–5× per axis for bisection (about 2× with interpolation). But the linear search needs at most two cache loads on one axis and four on the other, and bisection needs the same number. Counting cache loads, no difference is expected. The hash goes straight to the interval but still needs a cache load: about 3× fewer loads, plus extra gain from fewer conditionals.

GPU optimization. A GPU workgroup has a small, fast local memory shared by its threads (about 4,000 doubles). The table has 1,173 values plus 51 + 23 axis values, so it fits. All threads of the workgroup first cooperatively load the table into local memory, then a barrier(CLK_LOCAL_MEM_FENCE) makes sure everything is loaded before any thread interpolates. That is why the GPU gain is larger here than for the other kernels.

Sorting with a spatial perfect hash

Spatial sorting helps with nearest neighbors, removing duplicates, range finding and graphics output. Test case: 1D cells with a minimum size of 2.0; every cell size is a power of two times that (2, 4, 8, 16, 32); sizes and order are random. Knowing the minimum value and the minimum distance between values, the bucket index

bk = ⌊ (Xi − Xmin) / Δmin ⌋

is guaranteed to be a perfect hash. In figure 5.9 the minimum difference is 2.0 and Xmin = 0, so key 8 goes to bucket 4. You can store either the value (read back hash[4]) or the original index (read back keys[hash[4]]). Storing the index is a bit slower but more general: it can reorder all the arrays of a mesh.

Spatial hash sort on the CPU (listing 5.11)

uint hash_size = (uint)((max_val - min_val)/min_diff);
hash = (int*)malloc(hash_size*sizeof(int));
memset(hash, -1, hash_size*sizeof(int));       // -1 = empty bucket

for(uint i = 0; i < length; i++)                 // write: index into its bucket
   hash[(int)((arr[i]-min_val)/min_diff)] = i;

int count=0;
for(uint i = 0; i < hash_size; i++)              // read: sweep buckets in order
   if(hash[i] >= 0) sorted[count++] = arr[hash[i]];
free(hash);
  • Spatial hash sort is Θ(N); quicksort is Θ(N log N). The price: it is specialized to the problem and can temporarily take more memory.
  • The code is barely a dozen lines; quicksort is five times longer and far more complicated.
  • The read phase needs a well-implemented prefix sum to retrieve sorted values in parallel (section 11).
  • Earlier tests (2 million values): the GPU version was 3× faster than the fastest general GPU sort, and the serial CPU version 4× faster than quicksort. With 16 million values on current CPUs: nearly 6×. A sort written in two or three months beat reference sorts built on decades of research.

10Compact hashing

The perfect hash methods can be improved further. Two key observations: we do not need to write to every spatial bucket, and if we handle collisions, the hash can be compressed to use far less memory.

Write optimizations for neighbor finding

With six or more refinement levels a coarse cell writes to many hash buckets (the book’s example: 64) while a fine cell writes to just one. That causes load imbalance and thread divergence.

DefinitionThread divergence: the amount of work differs between threads, and the threads end up waiting for the slowest one.
  1. Neighbor queries only sample a cell’s outer buckets, so do not write the interior.
  2. Only the corners or midpoints are ever queried, so write only those.
  3. Write once per cell and do multiple reads to find a finer, same-size or coarser neighbor. This needs the hash initialized to a sentinel value such as −1 meaning “no entry”.

From sparse to compact

Fewer writes leave a lot of empty space. Sparsity is the empty fraction of the hash and shows the opportunity for compression. The hash can be compressed to as little as 1.25× the number of entries. The load factor is the inverse of the size multiplier (filled entries / table size), so 1.25× means a load factor of 0.8. In parallel code a much lower load factor of about 0.333 (size multiplier 3) is typical, so that no processor is slowed down by long collision chains.

When a bucket is taken, the entry looks for the next open slot: open addressing. Other collision methods often need to allocate memory during the operation, which is hard on a GPU, so open addressing (alternate slots inside the already allocated table) is used. Ways to choose the next slot:

Linear probingTry the next bucket in sequence until one is open.
Quadratic probingSquared increments: +1, +4, +9, … from the original location. Used by the book, because the first couple of tries are still in the cache.
Double hashingA second hash function gives a deterministic but pseudo-random jump distance.

Fancier probing avoids clustering of values, which would make store and query sequences long. Once a slot is found, both key and value are stored; a read compares the stored key with the wanted key and tries the next slot if they differ.

  • The CPU gain from the optimizations is modest (more conditionals, and you must count cache lines, not values) and appears mainly at higher refinement levels. The GPU gains more because thread divergence is reduced.
  • The compact hash is competitive because there is much less memory to initialize to −1. With more sparsity than the test’s 30× it can even be faster than the perfect hash. Cell-based AMR typically compresses at least 10×, often more than 100×.
  • CLAMR switches between a perfect hash (low sparsity) and a compact hash (lots of empty space).

Face neighbors in unstructured meshes

For unstructured (polygonal) meshes a perfect hash is hard to guarantee, so collisions must be handled. Finding the neighbor across each face is so expensive that many codes store the neighbor map; the hash method is fast enough to compute it on the fly:

  1. Find the bucket that contains the center of each face.
  2. Each cell writes its number into that bucket: into the first slot if the face is to the left and up from the cell center, otherwise into the second.
  3. Each cell checks the other slot. A number there is the neighbor; an empty slot means an external face.

Neighbors found with a single write and a single read. The right table size is hard to know in advance: pick a reasonable size from the number of faces or minimum face length and handle collisions.

Remap with a single write

  • Each input cell writes its index only to the lower-left corner of its area in the hash (initialized to −1).
  • An output cell reads where a same-size input cell would write. If it finds −1 (or the wrong level), it looks where the next coarser cell would write, and so on. Output cell 1 reads (0,2), finds −1, then reads (0,0) and finds input cell 1.
  • If the input cells there are finer, it recursively descends, averaging four sub-cells per level (avg_sub_cells, returns sum/4.0).
  • Recursion is “not supported” on GPUs, yet this ran fine on every GPU tested: a limited amount of recursion works for the few levels of a practical mesh.

Hierarchical hash with breadcrumbs

  • Allocate one hash table per mesh level.
  • Each cell writes its index into its own level’s table and leaves a sentinel (−1) in each coarser table above it: a breadcrumb trail meaning “there is data at finer levels”.
  • A read starts at the coarsest table; on a sentinel it descends recursively and sums the finer values.
  • Benefit: the tables do not need to be initialized to a sentinel at the start. Each level can be a perfect or a compact hash, and it also runs fine on GPUs.

11Prefix sum (scan)

The prefix sum, also called a scan, made the parallel hash sort work. It is common in computations with irregular sizes: to work in parallel, each process must know where to start writing. Example: every processor has a different number of particles and must map its local indices to global ones. The output y is a running sum of the input x:

yj = Σi=0j−1 xi   (exclusive scan)

x (particles)34638754
exclusive → start0371316243136
inclusive → end37131624313640

An exclusive scan leaves out the current value and gives each process its starting index in the global array; an inclusive scan includes it and gives the exclusive upper bound of its range (the book calls this the ending index). (Figure 5.16 in the book shows the same arrays.)

Serial inclusive scan (listing 5.15)

y[0] = x[0];
for (int i=1; i<n; i++){
   y[i] = y[i-1] + x[i];          // each step depends on the previous one
}

After the scan, each process knows where its results go and can work fully in parallel. The scan itself looks intrinsically serial, but there are effective parallel versions.

Step-efficient scan

Uses the fewest steps (but not the fewest operations). It is a tree-based pattern: in step 1 each element adds the value 1 to its left, then the value 2 to its left, then 4, and so on. All processes stay busy, and the result is an inclusive scan in log2 n steps, but the total work is larger than in the serial algorithm.

Work-efficient scan

Uses the fewest operations (but more steps). It has two sweeps:

The upsweep starts with half the threads busy and shrinks to one; the downsweep starts with one thread and ends with all threads busy. The extra steps let earlier results be reused, so the total work is only O(N). Which one to choose depends on how many parallel processes you have. Both are limited to the threads of one GPU workgroup or the processors of a CPU.

Scan for large arrays

  1. Kernel 1: a reduction sum on each workgroup, stored in a temporary array that is smaller than the original by the workgroup size (typically up to 1,024 threads).
  2. Kernel 2: scan the temporary array in workgroup-sized blocks. It now holds the offset of each workgroup.
  3. Kernel 3: scan each workgroup-sized chunk of the original array and add the workgroup’s offset to every thread.
In practiceThe parallel scan is heavily optimized for GPUs, so use a library: CUDPP for CUDA, CLPP or the sort_kern.cl scan from PerfectHash for OpenCL. An OpenMP scan comes in chapter 7.

12Global sum & reproducibility

Not every parallel algorithm is about speed. Since the early days, parallel computing has suffered from sums that are not reproducible across processor counts. The cause: finite-precision arithmetic is not associative, so changing the order of additions changes the answer, and parallelization can change the order. On two processors you add each half and then the two partial sums. The problem gets worse with size: the last value becomes a smaller and smaller part of the total and may not change it at all.

Catastrophic cancellationSubtracting nearly equal approximations can expose earlier rounding errors and greatly reduce relative accuracy. The subtraction can be exact for the stored operands while the result differs from that for the intended decimal inputs. 
x = 12.15692174374373 - 12.15692174374372
print(x)        # 1.06581410364e-14  (only a couple of correct digits)
DefinitionA reduction is an operation where an array of one or more dimensions is reduced to at least one dimension less, often to a scalar. Example: total mass or energy from the mass in every cell. The global sum is a reduction.

With fixed inputs, arithmetic settings and operation order, a serial sum repeats the same rounded result. A parallel sum can be more or less accurate, yet different from the serial one: the global sum issue. Programmers blamed every small serial/parallel difference on it, but often the real cause was a subtle bug such as not updating ghost cells (cells that hold the neighboring processor’s values).

For years the only known fix was to sort the data into a fixed order and sum serially: too expensive. Around 2010 several programmers realized it is not only an order problem but also a precision problem. In real-number arithmetic addition is associative, so adding precision can reduce the error far more cheaply than sorting. This does not make arbitrary finite-precision addition associative or guarantee identical results for every reduction order.

Test case: the Leblanc problem

The Leblanc problem (“the shock tube from hell”) separates a high- and a low-pressure region with a diaphragm removed at time zero. Energy is 1.0e−1 on one half and 1.0e−10 on the other: a dynamic range (max/min ratio) of nine orders of magnitude. Doubles have about 16 significant digits, so adding a small value to a big one keeps only about 7. With 134,217,728 cells, summing the high values first leaves the small values almost nothing to contribute; summing the small values first (lowest to highest magnitude) is more accurate, which is the sorting solution again. The accurate answer is easy to compute by multiplying: ncells/2 * 1.0e-1 + ncells/2 * 1.0e-10.

Enhanced-precision fixes

Long doubleEasiest. In the book’s x86 example it uses an 80-bit hardware format; compiler and platform details vary. Not portable: elsewhere it can be 64-bit, or 128-bit in software.
Pairwise summationAdd pairs, then pairs of pairs, in log2 steps. The book’s single-processor implementation needs an extra array half the original size; across processors it may need communication at each step.
Kahan summationThe most practical. An extra double carries the lost remainder, improving effective accuracy without guaranteeing twice as many correct digits. About 4 flops instead of 1. William Kahan, 1965. Best when the accumulator is the larger value.
Knuth summationHandles additions where either term can be larger, collecting the error of both. 7 flops. Donald Knuth, 1969.
Quad precision__float128. Simple to code but almost always done in software, so expensive, and not all compilers support it.

Kahan summation (idea of listing 5.18)

double sum = 0.0, correction = 0.0;
for (long i = 0; i < ncells; i++) {
   double corrected_next_term = var[i] + correction;
   double new_sum = sum + corrected_next_term;
   correction = corrected_next_term - (new_sum - sum);   // what got lost
   sum = new_sum;
}
return sum + correction;

  • In this particular test, pairwise, Kahan and Knuth have a reported error of 0.0; that is not a guarantee of exact sums for all inputs. Quad precision is the slowest method measured here.
  • The extra flops are cheap because the data stays in registers or L1 cache, and a vectorized Kahan/Knuth (section 6.3.4) costs the same as a plain sum. Compared with MPI communication costs the increase is insignificant.
  • This uses the processor’s excess floating-point capability: machines today can do about 50 flops per data load, so extra arithmetic is almost free.
  • The multi-processor version needs MPI and comes in section 8.3.3.

13Traits of good parallel algorithms

The chapter ends with the properties to look for in algorithms for highly parallel hardware:

LocalityUsed often but rarely defined. Locality for cache: keep values used together close together. Locality for operations: do not operate on all the data when you do not need to, e.g. the spatial hash keeps particle interactions O(N) instead of O(N²).
AsynchronousAvoid coordination between threads that causes synchronization.
Fewer conditionalsBesides the direct cost of branches, conditionals cause thread divergence on some architectures.
ReproducibilityHighly parallel techniques often run into the non-associativity of finite-precision arithmetic. Enhanced precision helps.
Higher arithmetic intensityHardware gained floating-point power faster than memory bandwidth, so algorithms that do more flops per byte use parallelism (e.g. vector units) well.

Parallel algorithm research is still young. Many good techniques exist but are not widely known, partly because they come from very different fields of computer and computational science.

14Key takeaways & exercises

  • Choose algorithms with low complexity that lend themselves to parallelism early in development.
  • Comparison-based algorithms have a lower limit of O(N log N); non-comparison algorithms can break it.
  • Hashing is a non-comparison, asynchronous, highly scalable technique; spatial hashing gives Θ(N) spatial operations.
  • For any spatial operation there is a spatial hashing algorithm that scales as O(N).
  • Real performance depends on cache line loads, not just operation counts. Use performance models.
  • The prefix scan parallelizes work on irregular-sized arrays.
  • Reproducible global sums need enhanced precision, which restores associativity and allows reordering, and thus more parallelism.

Exercises from the chapter (with short sample answers)

1. A cloud collision model in an ash plume applies to particles within 1 mm. Write pseudocode for a spatial hash version. What complexity order is it?

Use buckets 1 mm wide. Write each particle index into the bucket of its position, then for every particle loop only over particles in its own and the adjacent buckets and test the distance (like listing 5.3). The work per particle is bounded, so the operation is O(N) (Θ(N)) instead of O(N²).

2. How does the postal service use spatial hashes?

Postal (ZIP) codes are spatial hash keys: an address is mapped to a code for a region, and mail is sorted into the bin for that region without comparing addresses with each other.

3. Big data uses map-reduce. How is it different from the hashing here?

Map-reduce also hashes keys to group data (the map/shuffle step) but then reduces each group, usually across many distributed machines with disk and network in between. The hashing in this chapter is a fast, in-memory spatial mapping used to find neighbors, remap or sort, with buckets defined by geometry.

4. An AMR wave code must record wave height over time at buoy and shore locations, while cells keep being refined. How?

Each time step, build (or reuse) the spatial hash of the current mesh and look up the bucket at each station’s coordinates to get the current cell, then record its height. The lookup is O(1) per station no matter how the cells were reordered or refined.
