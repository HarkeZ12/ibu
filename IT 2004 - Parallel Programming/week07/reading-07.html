01Introduction

Processors keep getting more cores. A program that uses only one core leaves most of the chip idle. To use the other cores we start threads: several streams of instructions that run at the same time and share the same memory. The most common standard for this is OpenMP (Open Multi-Processing).

This reading follows Chapter 7 of Parallel and High Performance Computing (Robey and Zamora), “OpenMP that performs”. It starts with a simple “Hello World” and ends with a split-direction stencil. On the way it shows how OpenMP directives interact with the operating system kernel, the memory hierarchy and the hardware.

The chapter has one main message. Adding a few pragmas in front of loops (loop-level OpenMP) is quick and gives a modest speedup. For real performance you need a different method, high-level OpenMP, which keeps the threads alive for the whole program and cuts thread start-up costs, synchronization waits, cache thrashing and memory use. The book says a modern parallel programmer should know both shared-memory programming (OpenMP, this chapter) and distributed-memory programming (MPI, Chapter 8).

NoteThe source code for the chapter is at github.com/EssentialsofParallelComputing/Chapter7. The stencil programs (stencil_opt2, stencil_opt4, stencil_opt6) are the same ones used in Lab 07.

03OpenMP introduction and concepts

3.1 What OpenMP is

OpenMP is one of the most widely supported open standards for threads and shared-memory parallel programming. It took time to develop. In the early 1990s several hardware vendors introduced their own versions. In 1994 there was a failed attempt to standardize them in the ANSI X3H5 draft. When wide-scale multi-core systems appeared in the late ’90s, the approach came back, and the first OpenMP standard came out in 1997.

Today OpenMP gives a standard and portable API for shared-memory programs with threads. It is known to be easy to use and fast to implement, and it adds only a little code, usually as pragmas or directives. A pragma (C/C++) or directive (Fortran) tells the compiler where to start OpenMP threads, and the two words are often used for the same thing. In C and C++ pragmas are preprocessor statements. In Fortran directives are written as comments, so the program is still standard Fortran when OpenMP is not used. You need a compiler that supports OpenMP, but most compilers have this support built in.

OpenMP makes parallelism possible for a beginner. A block of code can be run in parallel with very little effort, so OpenMP is often the first step in scaling an application beyond one core. Figure 7.1 compares the effort and the performance of OpenMP and MPI.

3.2 The relaxed memory model and race conditions

Modest parallelism with OpenMP is easy, but thorough optimization is hard. The reason is OpenMP’s relaxed memory model. “Relaxed” means that the values of variables in main memory are not updated immediately, because updating memory after every change would be too expensive. Because of the delay, small timing differences between threads that work on shared variables can give different results from run to run.

TermDefinition from the chapter
Relaxed memory modelThe value of the variables in main memory or caches of all the processors are not updated immediately.
Race conditionA situation where multiple outcomes are possible, and the result depends on the timing of the contributors.

Because the memory model is relaxed, a thread’s view of memory must be passed to the other threads with an OpenMP barrier or flush. A flush guarantees that a value moves between two threads, which prevents race conditions. A barrier flushes all locally modified values and synchronizes the threads. On a multi-core system the modified values in cache must be flushed to main memory. Newer CPUs have special hardware that updates only what really changed, but it is still expensive and makes threads stall while they wait.

AnalogyA flush is like removing a thumb drive: you must tell the operating system to write out all cached data and then wait. Code that uses frequent barriers and flushes together with small parallel regions has too much synchronization and performs poorly.

3.3 Shared and private variables

OpenMP was first used for highly regular loops on shared-memory multiprocessors. Inside a threaded parallel construct each variable is either shared or private:

  • Private variable: local and only visible to its own thread.
  • Shared variable: visible to every thread and can be changed by any thread.

To really understand these words you need to know how memory works in a threaded program (Figure 7.2). Each thread has its own stack (private memory), its own instruction pointer and stack pointer. All threads share the heap (dynamic data) and the static data.

OpenMP directives say how to share the work, but they say nothing about where the data is. You must know the implicit rules for the scope of each variable.

  • Work sharing: splitting the work across a number of threads or processes.

3.4 First touch and NUMA

The OS kernel can manage memory for threads in several ways. The most common is first touch:

  • First touch: the first touch of an array causes the memory to be allocated, near the thread that touches it. Before the first touch the memory exists only as an entry in a virtual memory table. The physical memory is created when it is first accessed.

First touch matters because many high-end computing nodes have several memory regions. Then a CPU reaches different parts of memory at different speeds.

DefinitionNon-Uniform Memory Access (NUMA): on some computing nodes, blocks of memory are closer to some processors than to others. This is common when a node has two CPU sockets, each with its own memory. Accessing memory in the other NUMA domain typically takes about twice the time of accessing its own memory.

3.5 One node only

OpenMP works on a single node, not on many nodes with distributed memory. So its memory scalability is limited to the memory on that node. Applications that need more memory must combine OpenMP with a distributed-memory technique, most often MPI (Chapter 8).

04A simple OpenMP program

4.1 Setting the number of threads and compiling

There are four ways to control how many threads a parallel region has:

  • Default: usually the maximum number of threads on the node. It can differ with the compiler and when MPI ranks exist.
  • Environment variable: export OMP_NUM_THREADS=16
  • Function call: omp_set_num_threads(16)
  • Pragma clause: #pragma omp parallel num_threads(16)

Two OpenMP functions appear in every example: omp_get_num_threads() returns the number of threads and omp_get_thread_num() returns the ID of the calling thread. Their header is #include <omp.h>, which is mandatory for OpenMP function calls. With GCC you compile with the flag that turns on OpenMP:

gcc -fopenmp -o HelloOpenMP HelloOpenMP.c
export OMP_NUM_THREADS=4
./HelloOpenMP

4.2 Hello OpenMP in six versions

The chapter fixes the program step by step. In the listings, >> Spawn threads >> marks where threads start, and Implied Barrier marks where the compiler inserts a barrier.

Listing 7.1 · No parallel region
#include <omp.h>
int main(int argc, char *argv[]){
   int nthreads, thread_id;
   nthreads = omp_get_num_threads();
   thread_id = omp_get_thread_num();
   printf("I have %d thread(s) and my thread id is %d\n",nthreads,thread_id);
}

Even with OMP_NUM_THREADS=4 the output is “I have 1 thread(s) and my thread id is 0”. There is no parallel region, so only one thread runs.

Listing 7.2 · A parallel region, but shared variables
int nthreads, thread_id;          // declared OUTSIDE the region
#pragma omp parallel              // >> Spawn threads >>
{
   nthreads = omp_get_num_threads();
   thread_id = omp_get_thread_num();
   printf(" I have %d thread(s) and my thread id is %d\n",nthreads,thread_id);
}                                  // Implied Barrier

Now there are four threads, but every thread says it is thread 3. nthreads and thread_id were declared before the parallel region, so they are shared. Every thread writes to the same variable, and the value printed is whatever the last thread wrote. This is a typical race condition (Figure 7.3). The order of the lines is also random: it depends on which thread writes first and how the output is flushed.

Listing 7.3 · Declare the variables inside the region
#pragma omp parallel
{
   int nthreads = omp_get_num_threads();   // now private
   int thread_id = omp_get_thread_num();   // now private
   printf(" I have %d thread(s) and my thread id is %d\n",nthreads,thread_id);
}

Every thread now prints a different ID (in a random order). Variables declared inside a parallel region are private.

Listing 7.4 · Only one thread prints: single
#pragma omp parallel
{
   int nthreads = omp_get_num_threads();
   int thread_id = omp_get_thread_num();
   #pragma omp single
   {
      printf("Number of threads is %d\n",nthreads);
      printf("My thread id %d\n",thread_id);
   }                                       // Implied Barrier
}                                          // Implied Barrier

Only one thread prints, but which one changes from run to run. single lets any one thread do the block and puts an implied barrier at its end.

Listing 7.5 · The first thread prints: masked
#pragma omp parallel
{
   int nthreads = omp_get_num_threads();
   int thread_id = omp_get_thread_num();
   #pragma omp masked
   {
      printf(" I have %d thread(s) and my thread id is %d\n",nthreads,thread_id);
   }                                       // no barrier here
}                                          // Implied Barrier

Now the output is always from thread 0: “I have 4 thread(s) and my thread id is 0”.

Listing 7.6 · Fewer pragmas
printf("Goodbye slow serial world and Hello OpenMP!\n");   // outside the region
#pragma omp parallel
   if (omp_get_thread_num() == 0) {
      printf(" I have %d thread(s) and my thread id is %d\n",
             omp_get_num_threads(), omp_get_thread_num());
   }                                       // Implied Barrier

The first print does not need to be in the parallel region. Thread zero is chosen with a simple if on the thread number instead of the masked pragma. A pragma applies to the next statement or to a block in curly braces. The only barrier left is the one implied by omp parallel.

4.3 Lessons from Hello OpenMP

Key points
  • Variables defined outside a parallel region are shared by default in the region.
  • Give each variable the smallest scope that is still correct. Declared inside the region, the compiler understands your intent.
  • masked is more restrictive than single: thread 0 must run the block, and masked has no implicit barrier at the end.
  • Watch for race conditions between threads.

4.4 OpenMP versions

OpenMP keeps changing, so you should know which version and features your compiler supports. It started with threads on a single node; vectorization and offloading to accelerators such as GPUs were added later.

VersionMain additions
3.0 (2008)Task parallelism; better loop parallelism: loop collapse and nested parallelism.
3.1 (2011)min and max reductions in C and C++; thread binding control.
4.0 (2013)OpenMP SIMD (vectorization) directive; target directive for offloading to GPUs and other accelerators; thread affinity control.
4.5 (2015)Substantial improvements to GPU (accelerator) support.
5.0 (2018)Further improvements to accelerator support.

Changes have come faster since 2011. Versions 3.0 and 3.1 dealt mostly with standard CPU threading; versions 4.0, 4.5 and 5.0 deal mostly with other forms of hardware parallelism such as accelerators and vectorization.

05Three use cases: loop-level, high-level, MPI plus OpenMP

The first decision is which of three scenarios fits your application. Figure 7.4 shows what to read for each.

Loop-level OpenMP for quick parallelization

Use it when the application needs only a modest speedup and has plenty of memory resources, meaning the memory of a single node is enough. Typical signs:

  • modest parallelism;
  • plenty of memory resources (low memory requirements);
  • the expensive part of the calculation is in just a few for or do loops.

It takes little effort and can be done quickly. With separate parallel for pragmas the risk of race conditions is reduced. Even when the final goal is something better, loop-level OpenMP is often the first step.

High-level OpenMP for better parallel performance

High-level OpenMP is radically different. Standard OpenMP works bottom-up: it adds parallelism at the loop level. High-level OpenMP takes a top-down, whole-system view that looks at the memory system, the system kernel and the hardware. The OpenMP language does not change; the way you use it does. It removes many of the thread start-up and synchronization costs that limit loop-level OpenMP. If you want every last bit of performance, this is for you.

MPI plus OpenMP for extreme scalability

OpenMP can also add a second level of parallelism to an MPI program. Threads are used on a small set of processors: within a node, or better, within one NUMA region, where all memory accesses cost the same. This avoids some of the complexity and performance traps of OpenMP. A more modest hybrid uses OpenMP for the two to four hyperthreads of each processor. For small thread counts loop-level OpenMP is enough; to let more threads replace MPI ranks you need some of the steps toward high-level OpenMP.

06Examples of standard loop-level OpenMP

Parallel regions start with pragmas around blocks that can be split among independent threads, such as for or do loops. OpenMP relies on the OS kernel for memory handling, and this often limits how close it gets to peak performance. Each thread has a temporary view of memory, so it does not pay for storing to memory after every operation. When that view must be matched with main memory, a barrier or flush is needed. Each synchronization costs time for the flush, and fast threads must wait for slow ones.

Correctness matters as much as speed. Threads run at different speeds, and together with relaxed memory this can cause serious errors even in well-tested code. Careful programming and special tools are essential.

The examples ran on a Skylake Gold 6152 dual-socket system and a 2017 Mac laptop. Threads were placed on cores and bound to them to reduce run-to-run variation:

export OMP_PLACES=cores
export OMP_CPU_BIND=true

6.1 Vector addition and first touch

Vector addition shows the three things that decide correctness and performance: work-sharing directives, implied variable scope and memory placement by the operating system.

Listing 7.7 · Vector add with one pragma (vecadd_opt1.c)
#define ARRAY_SIZE 80000000          // large enough to force data into main memory
static double a[ARRAY_SIZE], b[ARRAY_SIZE], c[ARRAY_SIZE];

for (int i=0; i<ARRAY_SIZE; i++) {     // initialization: SERIAL
   a[i] = 1.0;  b[i] = 2.0;
}
vector_add(c, a, b, ARRAY_SIZE);

void vector_add(double *c, double *a, double *b, int n){
   #pragma omp parallel for            // >> Spawn threads >>
   for (int i=0; i < n; i++){
      c[i] = a[i] + b[i];
   }                                    // Implied Barrier
}

This gives modest speedup but could be better. Arrays a and b are first touched by the main thread during the serial initialization, so their memory is placed near thread zero. Some threads then read from the other memory region, which is slower. The array c is first touched inside the parallel loop, so it ends up near each thread.

Listing 7.8 · Vector add with first touch (vecadd_opt2.c)
#pragma omp parallel for               // initialization is now parallel too
for (int i=0; i<ARRAY_SIZE; i++) {
   a[i] = 1.0;  b[i] = 2.0;
}

The initialization loop uses the same static partition as the compute loop, so each thread first touches exactly the part it will use later, and the OS puts that memory near it. Threads in the second NUMA region no longer have slower access. This improves memory bandwidth and load balance. A good first-touch implementation often gains 10 to 20%.

6.2 Checking the NUMA configuration

With NUMA enabled in the BIOS, the Skylake Gold 6152 is about two times slower when it accesses remote memory. On Linux you can see your configuration with numactl and numastat (packages numactl-libs or numactl-devel).

The node distances at the end roughly show the cost of reaching memory, like the number of hops. Here remote memory costs 21 versus 10, a little over two times. Some two-region systems just list a default 20 versus 10 instead of the real cost.

  • Only one NUMA region, or a small difference in cost: first touch matters less.
  • Memory set to interleaved accesses: optimizing for local memory will not help.
  • No specific information, or optimizing for larger HPC systems in general: use first touch.

6.3 Stream triad

for (int k=0; k<NTIMES; k++){            // NTIMES = 16, for an average
   cpu_timer_start(&tstart);
   #pragma omp parallel for
   for (int i=0; i<STREAM_ARRAY_SIZE; i++){
      c[i] = a[i] + scalar*b[i];
   }
   time_sum += cpu_timer_stop(tstart);
   c[1]=c[2];                            // keeps the compiler from optimizing the loop away
}

Again one pragma on the compute loop is enough for threading, and a second pragma on the initialization loop adds first-touch speedup.

6.4 Stencil, cold cache and warm cache

The stencil adds the neighbours of a cell and takes the average as its new value. Its memory reads are more complex, so it shows the effect of threads reading memory written by other threads. In the first version each parallel for block is synchronized by default (implied barrier), which prevents race conditions.

Listing 7.10 · Loop-level stencil (stencil_opt2.c, main parts)
#pragma omp parallel for                 // first-touch initialization
for (int j = 0; j < jmax; j++)
   for (int i = 0; i < imax; i++){ xnew[j][i] = 0.0; x[j][i] = 5.0; }

for (int iter = 0; iter < 10000; iter++){
   #pragma omp parallel for              // flush loop: empties the cache
   for (int l = 1; l < jmax*imax*4; l++) flush[l] = 1.0;
   #pragma omp parallel for              // stencil
   for (int j = 1; j < jmax-1; j++)
      for (int i = 1; i < imax-1; i++)
         xnew[j][i]=(x[j][i] + x[j][i-1] + x[j][i+1] + x[j-1][i] + x[j+1][i])/5.0;
   SWAP_PTR(xnew, x, xtmp);
}

The flush loop writes a big array to push x and xnew out of the cache. It imitates code whose data is not in cache from an earlier operation.

  • Cold cache: the data is not in cache.
  • Warm cache: the data is in cache.

Both are valid cases to study. Both happen in real applications, and it can be hard to know which one will happen without deep analysis.

6.6 Reduction: a global sum

A reduction is any operation that starts with an array and calculates a scalar result (introduced in Chapter 5). OpenMP handles it with a reduction clause:

Listing 7.11 · Global sum
double do_sum_novec(double* restrict var, long ncells){
   double sum = 0.0;                    // still needed when OpenMP is off
   #pragma omp parallel for reduction(+:sum)
   for (long i = 0; i < ncells; i++){
      sum += var[i];
   }
   return(sum);
}

Each thread computes a local sum, then the local sums of all threads are added together. OpenMP initializes the reduction variable to the right value for the operation (zero for +). The line sum = 0.0 is still needed so that the code is correct without OpenMP.

6.7 Loops that loop-level OpenMP can handle

Loop-level OpenMP works on most loops, but not all. The loop must be in canonical form, the plain loop that programmers learn first:

  1. The loop index variable must be an integer.
  2. The loop index cannot be modified inside the loop.
  3. The loop must have standard exit conditions.
  4. The loop iterations must be countable.
  5. The loop must not have any loop-carried dependencies.

To test the last rule, reverse the order of the loop or change the order of its operations. If the answer changes, the loop has loop-carried dependencies. Vectorization on the CPU and threading on the GPU have similar restrictions. This kind of parallelism is called fine-grained:

  • Fine-grained parallelization: loops or other small blocks of code are run by several processors or threads and may need frequent synchronization.
  • Coarse-grained parallelization: each processor works on large blocks of code with infrequent synchronization (the style of distributed-memory message passing).

07Variable scope and function-level OpenMP

7.1 Variable scope rules

To move to high-level OpenMP you must understand variable scope. The OpenMP specification is vague about many details, so Figure 7.7 collects the rules compilers use. In general a variable on the stack is private and a variable on the heap is shared (Figure 7.2). For high-level OpenMP the most important case is the scope inside a routine called from a parallel region.

WhereSharedPrivate
Parallel constructDeclared outside the construct, or in a shared clauseAutomatic variables inside the construct, or in a private / firstprivate clause
Fortran routine in a parallel regionsave attribute, initialized variables, common block, module variablesAll local variables, or declared threadprivate
C routine in a parallel regionFile-scope variables, extern or staticAll local variables, or declared threadprivate
ArgumentsInherited from the calling environment
AlwaysAll loop indices are private

Pay most attention to variables on the left-hand side of an expression: the scope of variables that are written matters most. Private variables are undefined when a parallel region starts and after it ends (Listing 7.12). The firstprivate and lastprivate clauses change this in special cases. A private variable should be set before it is used in the block and not used after it.

Listing 7.12 · Private variable entering a parallel block
double x;                                // declared outside
#pragma omp parallel for private(x)
for (int i=0; i < n; i++){
   x = 1.0;                              // x is not defined on entry: set it first
   double y = x*2.0;                     // declared inside: private, better style
}
double z = x;                            // x is NOT defined here
Style ruleIf a variable should be private, declare it inside the loop. A local variable behaves exactly like an OpenMP private variable. It does not exist before or after the loop, so wrong uses are impossible.

Clauses that can go on the parallel directive and other blocks:

  • shared(var,var), private(var,var)
  • firstprivate(var,var), lastprivate(var,var)
  • reduction([+,min,max]:<var,var>)
  • threadprivate, a special directive used in a thread-parallel function

The book strongly recommends tools such as Intel Inspector and Allinea/ARM MAP before starting high-level OpenMP.

7.2 Function-level OpenMP: a whole function in parallel

Before high-level OpenMP, the parallel region is expanded from loops to bigger pieces of code to lower overhead and raise parallel efficiency. Eventually it covers a whole subroutine. Then OpenMP gives much less control over scope: there is no place to put scoping clauses. The defaults usually work, but not always.

  • The only OpenMP pragma control for functions is threadprivate, which makes a declared variable private.
  • Most variables in a function are on the stack and are already private.
  • A pointer to an array allocated in the routine is a local variable on the stack, so it is private and different for every thread. If we want the array to be shared, there is no directive for that.
  • Solution from Figure 7.7: in Fortran add the save attribute; in C declare the pointer static or make it file scope. Then it lives in the heap/static area and is shared.
Listing 7.14 · Function-level scope in C
void function_level_OpenMP(int n, double *y)   // pointer y: scope of the caller, private here
{
   double *x;                                   // pointer to x is private
   static double *x1;                           // pointer to x1 is shared
   int thread_id;
#pragma omp parallel
   thread_id = omp_get_thread_num();
   if (thread_id == 0) x  = (double *)malloc(100*sizeof(double));
   if (thread_id == 0) x1 = (double *)malloc(100*sizeof(double));
   // lots of code
   if (thread_id == 0) free(x);
   if (thread_id == 0) free(x1);
}

The memory for x is on the heap and could be shared, but the pointer is private, so only thread zero can reach it. The memory for x1 is on the heap and the pointer is shared, so all threads can use it.

In the Fortran version (Listing 7.13) the traps are similar: the pointer of an allocatable array is private but its memory is on the heap; x1 on the stack is private; real :: x2 = 0.0 is shared in Fortran 90 (private in Fortran 77), because initialized variables get the save attribute, go to the heap and are initialized only on their first occurrence; variables with save are shared. The book recommends writing save explicitly to avoid confusion.

08High-level OpenMP

8.1 Why high-level OpenMP?

The central idea is to improve loop-level parallelism by minimizing fork/join overhead and memory latency. Another major goal is to reduce thread wait times. When the work is divided among threads explicitly, threads no longer wait implicitly for each other and can go on to the next part. You control where synchronization happens. Unlike the usual fork-join model, high-level OpenMP keeps threads dormant but alive, which reduces overhead tremendously (Figure 7.8).

8.2 How to implement it

High-level OpenMP takes more time: it needs advanced tools and much testing, and it is more prone to race conditions than loop-level OpenMP. It is also not obvious how to get from loop-level to high-level. You need to know the memory bounds of all loops, use profiling tools and work through the steps methodically and incrementally:

  1. Base implementation: implement loop-level OpenMP.
  2. Step 1, reduce thread start-up: merge the parallel regions; join all loop-level parallel constructs into larger parallel regions.
  3. Step 2, synchronization: add nowait clauses to for loops where synchronization is not needed, and calculate and manually partition the loops across threads, so barriers can be removed.
  4. Step 3, optimize: make arrays and variables private to each thread when possible.
  5. Step 4, code correctness: check thoroughly for race conditions after every step.
Memory hookTurtle → dog → cheetah → hawk: loop-level → merged regions → nowait → explicit thread bounds. Each animal is faster.

Step 1 puts the whole code in a single parallel region. Threads are created once, at the start. Unused threads do not die; they stay dormant during serial parts, which are run by the main thread, so the serial code barely changes. When a parallel part comes again, the same threads are reused.

Step 2 removes the synchronization that every for loop has by default. First add nowait wherever correctness allows. Then divide the work explicitly:

tbegin = N * threadID     / nthreads
tend   = N * (threadID+1) / nthreads

Manual partitioning reduces cache thrashing and race conditions, because threads do not share the same space in memory.

Step 3 states explicitly which variables are shared or private (rules of Figure 7.7), so the compiler does not have to guess. Compilers cannot parallelize loops with complex loop-carried dependencies or loops not in canonical form; being explicit helps here. Arrays are partitioned across the threads, so a thread touches only its own memory, and memory locality can be fixed.

Step 4 uses the tools of Section 11 to find and fix race conditions.

8.3 Example: the stencil, step by step

First find the bottlenecks and the most compute-intensive loop, add standard loop pragmas at the innermost level, and understand the scope of variables in those loops. Then move the directives outward.

Listing 7.15 · One parallel region for the whole iteration loop (stencil_opt4.c)
#pragma omp parallel                     // >> Spawn threads >> ONCE
{
   int thread_id = omp_get_thread_num();
   for (int iter = 0; iter < 10000; iter++){
      if (thread_id ==0) cpu_timer_start(&tstart_flush);
      #pragma omp for nowait              // no barrier at the end of this loop
      for (int l = 1; l < jmax*imax*4; l++) flush[l] = 1.0;
      if (thread_id == 0){ flush_time += cpu_timer_stop(tstart_flush);
                           cpu_timer_start(&tstart_stencil); }
      #pragma omp for
      for (int j = 1; j < jmax-1; j++)
         for (int i = 1; i < imax-1; i++)
            xnew[j][i]=(x[j][i] + x[j][i-1] + x[j][i+1] + x[j-1][i] + x[j+1][i])/5.0;
                                        // Implied Barrier
      if (thread_id == 0){ stencil_time += cpu_timer_stop(tstart_stencil);
                           SWAP_PTR(xnew, x, xtmp); }
   }
} // end omp parallel

The two old pragmas are merged into one region, so the parallel region starts once instead of 10,000 times. Serial parts such as the timer and the pointer swap run on the main thread.

Listing 7.16 · Precalculated loop bounds (stencil_opt6.c, main parts)
#pragma omp parallel
{
   int thread_id = omp_get_thread_num();
   int nthreads  = omp_get_num_threads();
   int jltb = 1 + (jmax-2) * ( thread_id     ) / nthreads;   // lower bound
   int jutb = 1 + (jmax-2) * ( thread_id + 1 ) / nthreads;   // upper bound
   ...
   for (int iter = 0; iter < 10000; iter++){
      for (int l = ifltb; l < ifutb; l++) flush[l] = 1.0;    // own range, no omp for
      for (int j = jltb; j < jutb; j++)
         for (int i = 1; i < imax-1; i++)
            xnew[j][i]=( x[j][i] + x[j][i-1] + x[j][i+1] + x[j-1][i] + x[j+1][i] )/5.0;
      #pragma omp barrier                   // Explicit Barrier
      if (thread_id == 0){ SWAP_PTR(xnew, x, xtmp); }      // thread ID instead of masked
      #pragma omp barrier                   // Explicit Barrier
   }
}

Remember that arrays start at 1 in Fortran and at 0 in C. Loops with the same bounds can reuse them without recalculating. Insert barriers where they are needed to prevent races, but not too many, or performance drops.

Start from the innermost loop and know which variables stay private and which become shared. As the region grows, serial parts go into a masked region (or an if on thread zero): one thread works and the others stay alive but dormant. The number of pragmas drops a lot and performance improves (Figure 7.11).

10Advanced examples

Three harder cases: the split-direction stencil (thread scope of variables), the Kahan summation (a more complex reduction) and the prefix scan (explicit partitioning of work).

10.1 Split-direction, two-step stencil

Stencils are building blocks of scientific codes that solve partial differential equations. In a two-step stencil, values are first calculated on the faces of the cells, with a separate pass for each direction. The face arrays have different sharing needs:

  • x-face data lines up with the way threads split the rows. A thread needs only its own part, so it can be private.
  • y-face data crosses between threads (the calculation uses row j+1), so the y-face array must be shared.

First touch already keeps memory local to each thread (except at page edges between threads). Making array parts completely private where possible improves locality further, which matters more and more as the gap between processor and memory speed grows.

Listing 7.20 · Split stencil with OpenMP (main parts)
int jltb = 1 + (jmax-2) * ( thread_id     ) / nthreads;
int jutb = 1 + (jmax-2) * ( thread_id + 1 ) / nthreads;

double** xface = (double **)malloc2D(jutb-jltb, imax-1);   // private: own pointer, own part
static double** yface;                                      // shared pointer
if (thread_id == 0) yface = (double **)malloc2D(jmax+2, imax);
#pragma omp barrier        // everyone must see the allocated memory
... x-face loop on own rows, y-face loop on own rows ...
#pragma omp barrier        // next loop uses the neighbour thread's y faces
... combine faces into a[j][i] ...
free(xface);
#pragma omp barrier        // all threads done with yface
if (thread_id == 0) free(yface);

For the x faces, the pointer double **xface is on the stack, so each thread has its own. Each thread allocates only its own rows. The memory is on the heap, but because only that thread holds the pointer, the others cannot reach it.

An automatic array such as double xface[3][6] would go on the stack. For large arrays the compiler may move it to the heap (each compiler has its own threshold); only one thread has the pointer, so it is still effectively private.

For the y faces, a static pointer is used: one thread allocates and all threads use the same pointer and memory (Figure 7.7: C routine → file scope, extern or static). A common mistake: with a normal double **yface pointer, every thread has its own private pointer and only one gets memory. The other pointers point to nothing and cause an error when used.

DefinitionSuper-linear speedup is performance better than the ideal scaling curve for strong scaling. It happens because the smaller array parts fit into a higher level of the cache.

10.2 Kahan summation with threads

The enhanced-precision Kahan sum (Chapter 5) cannot be parallelized with a pragma because of its loop-carried dependencies. The solution follows the vectorized version from Chapter 6, in two phases:

  1. Each thread computes a Kahan sum (sum + correction) over its own range tbegin…tend.
  2. The local results go into a shared array (a static pointer allocated by the masked thread, followed by a barrier). After another barrier, one masked thread sums across the threads with Kahan again, and a final barrier ends it.

The code uses #ifdef _OPENMP. The compiler defines _OPENMP when OpenMP is on; without it the function just returns the local sum, so the same code works serially.

10.3 Threaded prefix scan

The prefix scan (Chapter 5) is important for algorithms with irregular data: once each thread knows its starting position, the rest can run in parallel. It has three phases:

  1. All threads: prefix scan of each thread’s own part of the data.
  2. Single thread: calculate the starting offset of each thread’s data.
  3. All threads: apply that offset to all of the thread’s data.
int tbegin = length * ( thread_id     ) / nthreads;
int tend   = length * ( thread_id + 1 ) / nthreads;
// phase 1: exclusive scan of own range
if (nthreads == 1) return;
#pragma omp barrier
if (thread_id == 0) { /* phase 2: offsets for each thread */ }
#pragma omp barrier
#pragma omp simd
for (int i = tbegin + 1; i < tend; i++) output[i] += output[tbegin];   // phase 3

The same routine works in a serial program and inside an OpenMP parallel region, which avoids code duplication. In theory it scales as parallel time = 2 × serial time / nthreads. On the Skylake Gold 6152 it peaks at about 44 threads, 9.4 times faster than serial.

12A task-based algorithm

In a task-based approach the work is divided into separate tasks that are handed out to individual processes. Many algorithms are more natural this way. OpenMP has supported tasks since version 3.0, with improvements in later versions.

Example: a reproducible global sum by adding values pairwise. The usual array approach needs a working array and complicated indexing. The task approach avoids the working array: it recursively splits the data in half on the downward sweep until a piece has length 1, then adds pairs on the upward sweep.

Listing 7.23 · Pairwise sum with OpenMP tasks
double PairwiseSumByTask(double* restrict var, long ncells){
   double sum;
   #pragma omp parallel          // launch the parallel region
   {
      #pragma omp masked         // start the main task on one thread
      {
         sum = PairwiseSumBySubtask(var, 0, ncells);
      }
   }
   return(sum);
}
double PairwiseSumBySubtask(double* restrict var, long nstart, long nend){
   long nsize = nend - nstart;
   long nmid = nsize/2;
   double x,y;
   if (nsize == 1) return(var[nstart]);          // leaf: one value
   #pragma omp task shared(x) mergeable final(nsize > 10)
   x = PairwiseSumBySubtask(var, nstart, nstart + nmid);
   #pragma omp task shared(y) mergeable final(nsize > 10)
   y = PairwiseSumBySubtask(var, nend - nmid, nend);
   #pragma omp taskwait                         // wait for both subtasks
   return(x+y);
}

Tasks must be spawned inside a parallel region but by only one thread, hence the nested parallel and masked blocks. Each call launches two subtasks with half of the data, waits for both with taskwait and returns the sum. Good performance needs a lot of tuning: avoid spawning too many threads and keep the granularity of tasks reasonable. For some algorithms tasks are the much better strategy.

13Summary, style guide and exercises

  • Loop-level OpenMP is quick and easy to create.
  • An efficient OpenMP implementation can give promising speedup.
  • Good first-touch implementations often gain 10–20%.
  • Understanding variable scope across threads is important for correct OpenMP code.
  • High-level OpenMP can boost performance on current and future many-core architectures.
  • Threading and debugging tools are essential for more complex OpenMP.
Style guidelines from the chapter
  1. Declare variables where they are used, so they are automatically private, which is generally correct.
  2. Change declarations to get the right scope instead of writing long lists in private and shared clauses.
  3. Avoid critical and other locking constructs where possible; they hurt performance badly.
  4. Reduce synchronization: add nowait to for loops and use #pragma omp barrier only where necessary.
  5. Merge small parallel regions into fewer, larger ones to reduce OpenMP overhead.

⏱The 60-second version

  1. OpenMP = threads on one node that share memory. You add pragmas; the compiler makes the threads.
  2. Memory is relaxed: values are not updated at once. Two threads writing the same shared variable = race condition.
  3. Stack = private (each thread has its own). Heap and static = shared. Declared outside the region = shared; declared inside = private.
  4. First touch: memory lands near the thread that touches it first. So initialize arrays in a parallel loop too (+10–20%), because of NUMA (remote memory ≈ 2× slower).
  5. Loop-level OpenMP = a pragma before each loop. Easy, ~10× faster, but low efficiency on many threads (stencil: 17× on 88 threads = 19%).
  6. High-level OpenMP = one big parallel region, nowait, own loop bounds, private data, check for races after every step. Threads stay dormant but alive.
  7. Hard cases need care: static pointer to share, barriers around shared data, Kahan and prefix scan done by hand, tasks for recursive work.
  8. Use tools (Inspector for races, MAP for bottlenecks) and regression tests.

03OpenMP concepts

Big idea: threads share one memory, but that memory is updated lazily, so where a variable lives decides whether threads fight over it.

Private

Only its own thread sees it.
Lives on the stack.
Declared inside the region.

Shared

Every thread sees and changes it.
Lives on the heap / static data.
Declared outside the region.

  • Pragma (C/C++, preprocessor statement) = directive (Fortran, written as a comment).
  • Relaxed memory model: values in memory/caches are not updated immediately.
  • Race condition: several outcomes possible; result depends on timing.
  • Flush moves a value between threads. Barrier = flush everything + synchronize. Both are expensive (thumb-drive analogy).
  • Work sharing: splitting work across threads. Directives say nothing about where data is.
  • First touch: memory is really allocated at the first access, near that thread; before that it is only a virtual-memory entry.
  • NUMA: two sockets, each with its own memory; the far memory ≈ 2× slower.
  • OpenMP = one node only; more memory needed → combine with MPI.
Trap: “flush” and “barrier” are not the same. A flush only makes values visible; a barrier also makes threads wait for each other.
Why can the same OpenMP program give different results on two runs?

Relaxed memory model + shared variables: the timing of the writes decides the result (race condition).

Where is memory placed under the first-touch policy?

Near the thread that first touches (accesses) the array, not where malloc was called.

Which part of memory is private per thread, and which is shared?

Each thread has its own stack (private). The heap and static data are shared.

05Three use cases

Big idea: pick the scenario first; it decides how you use OpenMP.

Loop-level

Modest speedup, plenty of memory, cost in a few loops. Bottom-up. Little effort. First step for everyone.

High-level

Every bit of performance. Top-down, whole-system view (memory, kernel, hardware). Same language, different method.

MPI + OpenMP

Extreme scale. Threads inside a node or one NUMA region, or the 2–4 hyperthreads per processor.

What changes between loop-level and high-level OpenMP: the language or the method?

Only the method. The OpenMP language stays the same.

Why keep threads inside one NUMA region in MPI + OpenMP?

All memory accesses there cost the same, which avoids some complexity and performance traps of OpenMP.

07Variable scope and functions

Big idea: stack = private, heap = shared. Inside a called function you cannot write clauses, so you control scope with declarations.

SituationSharedPrivate
Parallel constructdeclared outside, shareddeclared inside, private, firstprivate
C functionfile scope, extern, staticlocal variables, threadprivate
Fortran functionsave, initialized vars, common, modulelocal variables, threadprivate
Argumentsinherited from the caller
Loop indicesalways private
  • Check written variables (left side of =) first.
  • Private = undefined on entry and after exit (unless firstprivate / lastprivate).
  • Best style: declare inside the loop → exactly like private, no misuse possible.
  • Whole function in parallel: only pragma control is threadprivate. To share a pointer: C static/file scope, Fortran save.

In a C function called from a parallel region, how do you make an array pointer shared?

Declare it static (or at file scope). There is no OpenMP directive for “shared” there.

Undefined. Use lastprivate if you need it.

Big idea: spawn threads once, keep them dormant but alive, split the work yourself and synchronize only where needed.

  2. Step 1, thread start-up: merge parallel regions.

Put the four steps in order.

Reduce thread start-up (merge) → synchronization (nowait, bounds) → optimize (private) → correctness (check races).

What happens to unused threads during a serial part in high-level OpenMP?

They do not die; they stay dormant and are reused when the next parallel part starts.

10Advanced examples

Big idea: when a pragma is not enough, partition by hand, choose private vs shared on purpose and put barriers around shared data.

Split stencil

x-face: private (pointer on each stack, own rows). y-face: needs row j+1 from the neighbour → static shared pointer, thread 0 allocates, barriers before use and before free.

Kahan sum

Loop-carried dependency → no pragma. Phase 1: each thread its own range. Phase 2: one masked thread sums the per-thread results (shared array, barriers).

Prefix scan

3 phases: all threads scan own part → one thread computes offsets → all add offset. Works serial and threaded. Ideal: 2·serial/nthreads; peak 44 threads, 9.4×.

  • Super-linear speedup: better than ideal, because smaller pieces fit in a higher cache level. Split stencil: 2–8 threads, falls off above 8.
  • _OPENMP is defined by the compiler when OpenMP is on → #ifdef _OPENMP keeps one code for serial and threaded runs.
Trap: a plain double **yface pointer would be private: only thread 0’s copy gets memory, the others point to nothing → error.
Why must the y-face array be shared but the x-face array can be private?

The y-face calculation uses a[j+1], which belongs to the neighbouring thread; the x-face uses only cells in the thread’s own rows.

What causes super-linear speedup?

Each thread’s smaller part of the data fits into a higher (faster) level of the cache.

!Top exam traps

  1. single has the barrier; masked does not.
  2. Declared outside the region → shared, even if each thread writes it.
  3. Private variables are undefined on entry and after the region.
  4. First touch is about the initialization loop, not the compute loop.
  5. Parallel efficiency divides by the thread count (ideal speedup), not by the serial time.
  6. A loop with loop-carried dependencies is not canonical; reversing it changes the answer.
  7. OpenMP alone covers one node; more memory needs MPI.
  8. High-level OpenMP: the language is the same; threads are spawned once; it is more prone to races.
  9. Heap memory with a private pointer is reachable only by that thread.
  10. Super-linear speedup comes from the cache, not from extra cores doing magic.
