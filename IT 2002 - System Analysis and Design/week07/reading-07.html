01Introduction

In Weeks 5 and 6 we looked at what the system does. The use-case diagram lists the use cases, the activity diagram shows the steps of each use case, and the use-case description writes them down. But a system does not only act. It also knows things. To make an appointment, the system must know the patient, the doctor, the date and the time. Where do we show these things, and how are they connected?

The answer is the structural model. It shows the people, places and things that the system keeps information about, and how they are related. In this reading we build a structural model with three tools. CRC cards are small paper cards that describe one class each. A class diagram draws all classes and their relationships in one picture. An object diagram tests the class diagram with real examples.

The reading follows Lecture 7 and Chapter 4 of the textbook (Tegarden et al., 7th edition). Sections 3 and 4 explain what a structural model is and how to find its classes. Section 5 is about CRC cards. Sections 6 and 7 are about class diagrams and object diagrams. Section 8 gives a seven-step method, Section 9 a worked example, and Section 10 the checks that keep all models consistent.

NoteKeep this reading open during the lecture and the lab. In the lab you write CRC cards and draw class diagrams and object diagrams with the free tool diagrams.net. All systems in the examples are small and invented, except the library example, which comes from the textbook.

02Learning objectives

After completing this reading, students should be able to:

  • explain what a structural model is for;
  • find classes with text analysis, brainstorming, common object lists and patterns;
  • write CRC cards and role-play them with the scenarios of a use case;
  • draw class diagrams with attributes, operations, visibility and associations;
  • read and write multiplicities and use association classes;
  • choose between generalization, aggregation and composition;
  • draw an object diagram and use it to find mistakes;
  • follow the seven steps that create a structural model; and
  • check that the CRC cards, the class diagram and the functional models agree.

03Structural models

3.1 What is a structural model?

A structural model (also called a conceptual model) shows the objects that a system uses and creates. These are the people, places and things we keep information about: patients, books, tickets, invoices. The model also shows how they are related to each other. A patient, for example, schedules appointments.

The model is built in two stages. In analysis it is a conceptual model. It shows the logical organization of the objects and does not say how they are stored or handled. We can then think about the business and ignore technical details. In design it is changed into a model for databases and software. This reading is about the analysis stage.

A structural model gives analysts and users a shared vocabulary. When a user says “patient” and the analyst draws a class called Patient, they speak about the same thing. It also gives the static view of the system: what is in it, not what happens over time. Remember that at this stage the classes are not programming classes. They are ideas from the business.

Key pointThe functional model shows what the system does. The structural model shows what the system knows. All of the models are driven by the use cases.

3.2 Classes, attributes and operations

A class is a template for creating objects. The objects (or instances) of a class have the same structure and behavior, but different values. Patient is a class. John Doe and Mary Smith are two objects of this class.

There are two kinds of classes. A concrete class has instances. An abstract class has none. It is only a useful idea. For example, we may create the abstract class Person to hold what Employee and Customer have in common. The system will never create an object that is only a person. At this stage we only use domain classes: classes that represent things of the problem domain.

An attribute is a piece of information that the system should keep about an object. Take only what the task needs. The employee's name is useful for a payroll system. The color of the employee's hair is probably not. Use only simple types, such as text, numbers, dates and yes/no values. If an attribute is complex, it is really a relationship to another class. A patient's insurance carrier is not a text. It is a class with a name, an address and a phone number.

An operation says what an object can do. In analysis we call it an operation (in design it becomes a method). Take only the operations that the functional requirements need, for example make appointment for the class Patient.

3.3 Three kinds of relationships

Classes are connected by relationships. All of them belong to one of three kinds (Table 3.1). Each kind answers a different question.

Table 3.1 · Three kinds of relationships between classes
KindSaysTestExample
Generalizationa-kind-ofCan the subclass stand in for the superclass everywhere?An employee is a kind of person.
Aggregationa-part-ofIs it a part of a whole?A door is a part of a car.
Associationeverything elseIs there another link between the classes?A patient schedules an appointment.

Generalization lets the subclass inherit the attributes and operations of the superclass. The common parts are written once, in the superclass. The textbook calls the test of this relationship the principle of substitutability. If we can use a secretary wherever we use an employee, then Secretary is a subclass of Employee. Aggregation relates parts to wholes. A piston is a part of an engine, and an engine is a part of a car. An association is the weakest of the three. A patient is not a part of an appointment, but the two are linked.

3.4 Class, attribute or instance?

Beginners often mix up three things: a class, an attribute and an instance. Ask what the word names. A class names a kind of thing. An instance is one of them. An attribute is a fact about an instance. Table 3.2 gives examples.

Table 3.2 · Class, attribute or instance?
WordIt is a…Why
PatientClassA kind of person that the system keeps data about.
Dr. SmithInstanceOne doctor. The class is Doctor.
phone numberAttributeA simple fact about a patient.
insurance carrierClassIt has its own data: name, address, phone.
12 October 2026ValueThe value of the attribute date of one appointment.
ageDerived attributeCalculated from the birth date (/age).
health teamClassA collective noun: a team is made of doctors and nurses.
Example“Ford” is not a class of cars. It is one manufacturer. So Ford is an instance of the class Manufacturer, and “Ford Focus” is an instance of the class CarModel.

04Finding the classes

How do analysts find the classes of a new system? Four techniques are common (Figure 4.1). Most analysts use all of them, because each one finds things that the others miss.

4.1 Text analysis

In text analysis we read the texts that we already have: the functional requirements, the use-case descriptions and the activity diagrams. The nouns suggest classes and the verbs suggest operations. This is a simple method, and the textbook says that its simplicity is its strength: it gives a rough first model quickly. Table 4.1 lists the guidelines, with an example for each.

Table 4.1 · Text analysis guidelines (after Figure 4-1 of the textbook)
In the textIt suggestsExample
Common nounA classpatient, appointment
Proper nounAn instance of a classDr. Smith
Collective nounA class made up of instances of another classhealth team
AdjectiveAn attributenew patient
Doing verbAn operationcontacts, cancels
Being verbGeneralization (a-kind-of)a nurse is an employee
Having verbAggregation or associationa schedule has appointments

Take the sentence “The patient contacts the office and asks for a new appointment.” The nouns patient, office and appointment are candidate classes. The verbs contacts and asks are candidate operations. The adjective new may be an attribute (the status of the appointment). Applied to the use case Manage Appointments, the textbook finds the candidates patient, doctor, appointment, office, receptionist, name and address.

4.2 Brainstorming

In brainstorming a group sits together and suggests classes from their experience. A facilitator starts with a question, for example: “Think of your last visit to a doctor. Which things were involved?” The group may name doctors, nurses, illness, treatment and insurance card. The textbook lists four rules from Bellin and Simone for the facilitator.

  1. Take every suggestion seriously. It is better to delete a class later than to forget an important one.
  2. Think fast. Collect all ideas first and judge them later.
  3. Manage the group. Everybody takes part, and nobody dominates. A round-robin (turns) helps.
  4. Keep a light mood. People suggest more ideas when they feel comfortable.

4.3 Common object lists

A common object list is a checklist of the kinds of things that most businesses have (Table 4.2). Go through it and ask for each line: do we have this in our problem? Tangible things are the easiest to find. Roles and incidents need more thought. Reusable libraries of objects exist for some domains, for example for medicine.

Table 4.2 · A checklist of common objects
CategoryMeaningExamples
Tangible thingsThings you can touchbooks, desks
IncidentsEvents that happenmeetings, flights
RolesWhat people do in the businessdoctor, patient
InteractionsTransactions between partiesa sales transaction
OtherPlaces, containers, organizations, records, catalogs, policiesoffice, folder, invoice

4.4 Patterns

A pattern is a useful group of classes that work together and solve a problem that comes up again and again. Most business transactions need the same classes: a transaction, its line items, the items, a place and the participants. If we start from this pattern, we do not begin with a blank page. In the appointment example, we can see an appointment as a transaction. The pattern then suggests the new classes Place, Item (a good or a service) and Transaction Line Item, which are useful for billing. The textbook merges several published patterns into one (Figures 4-2 and 4-3), and lists domains for which patterns exist, such as accounting, contracts, documents and employment.

4.5 Challenge every candidate

Text analysis, brainstorming and checklists give a long list. Many items are wrong, so the next step is to challenge each candidate. Ask: What information must the system keep about it? If the answer is “none”, remove it. The library example of the textbook shows how (Table 4.3). The analyst found the nouns of the use case Borrow Resource and then removed those that are only actors, the client or the system itself.

Table 4.3 · Challenging the candidates of the library example
CandidateDecisionReason
patronKeepThe system keeps name, ID number and address.
resourceKeepAbstract class: title, ID number, publisher.
student, guest, faculty/staffKeepKinds of patrons.
librarian, Personnel Office, Registrar's OfficeRemoveThey are only actors.
libraryRemoveIt is the client, not part of the system.
library systemRemoveIt is the system that is being built.
IDRemoveThe same as the patron (an attribute).

The analyst then checked the list with the librarian, Joe. Joe added other libraries as patrons (for interlibrary loans), journals, podcasts and music as resources, and the location and the collection of resources. Finding classes is not finished with the first list. It goes on in several rounds.

05CRC cards

5.1 Responsibilities and collaborations

A CRC card (Class, Responsibility, Collaboration) is a small card, usually an index card, that describes one class. It is a low-tech tool, and that is its strength: you can write on it, move it on a table and throw it away. The textbook uses cards together with the computer tools of the Unified Process, not instead of them.

A class has two kinds of responsibilities. Knowing: what an object must know. This is its attributes and its relationships. Doing: what an object must do. An object can do it alone, or it can ask another object, its collaborator, to help. Most use cases need several classes that work together. The textbook describes this as a client that sends a request, a server that receives it and does the work, and a contract that formalizes the interaction. For example, when a patient makes an appointment, the Patient (client) asks the Appointment (server) to create itself.

5.2 The parts of a CRC card

Figure 5.1 shows the card of the class Patient (after Figure 4-5 of the textbook). The front is about doing, the back about knowing. Table 5.1 explains the parts.

Table 5.1 · The parts of a CRC card
PartWhat it holds
Class nameA noun, but not a proper noun (not a name of one person or thing).
ID and typeA number, so that the class can be traced to the use cases. Type: concrete or abstract, domain.
DescriptionA short definition of the class.
Associated use casesThe use cases in which the class takes part.
ResponsibilitiesThe doing responsibilities. They become operations.
CollaboratorsThe classes that help with a responsibility. If a collaborator helps with two responsibilities, list it twice.
AttributesThe knowing responsibilities (back of the card).
RelationshipsGeneralization, aggregation and other associations (back of the card).

5.3 Role-playing

Once the cards are written, the team plays them. This is called role-playing, and it finds classes, attributes and operations that nobody thought of. Each team member plays an actor or a class. The group acts out one scenario at a time. A scenario is one path through a use case. You find the paths in the decisions of the activity diagram and in the alternate flows of the use-case description. Table 5.2 gives the five steps.

Table 5.2 · Role-playing the CRC cards in five steps
#StepWhat you do
1Review the use casesRead the activity diagrams and descriptions. Start with the use case that is the most important, the most complex or the least understood. Do not start with the easiest.
2Pick actors and objectsFind the actors and the cards that belong to the use case. Give each role to a person.
3Role-playAct out a scenario. Every step must belong to an actor or to a card. Where the play breaks down, something is missing.
4RepeatDo steps 1 to 3 for the other use cases.
5DocumentUpdate the cards. Add swimlanes to the activity diagram. Improve the events of the use-case description.

Role-playing also finds vague steps. In the textbook, the step “The Patient provides the receptionist with their information” is acted out. Then the team asks: Which information? The step must be changed to say that the patient gives the appointment type and the preferred times. A step that hides a decision forces everybody to guess. Make the step explicit, and play the scenario again.

5.4 Swimlanes

After role-playing, we show the results in the activity diagram by adding swimlanes (see Reading 6). We make one lane for each actor and each class that takes part. We put every activity into the lane of the one who does it. An activity in a class lane becomes a responsibility on the CRC card of that class. An object can only create, read, update and delete itself, so create appointment belongs in the lane of Appointment.

Swimlanes also show roles that the use-case diagram hides. In the Manage Appointments example, the lanes show an internal actor, the Receptionist. She is a human part of the system, so she is not on the use-case diagram, but she does a part of the work. We add her to the use-case description too.

5.5 A second card: Appointment

The card of Patient is only one card of the set. Table 5.3 shows the card of the class Appointment (after Figure 4-22 of the textbook). Look at the responsibilities. They come from the swimlane of Appointment in the activity diagram (Create Appointment, Cancel Appointment, Change Appointment), and from the use case. The card also has the responsibility cancel without notice, which matches the operation of the same name in the class diagram of the textbook (Figure 4-11).

Table 5.3 · The CRC card of the class Appointment

Key pointCRC cards turn the story of a use case into classes. The activities in a class lane become responsibilities, and the responsibilities become operations.

06Class diagrams

A class diagram is a static model. It shows the classes and the relationships that stay valid over time. Figure 6.1 shows the main elements in simple form. We look at each one in the next sections.

6.1 Classes, attributes and visibility

A class is drawn as a box with three parts: the name at the top, the attributes in the middle and the operations at the bottom. The value of the attributes is the state of an object. The operations are its behavior.

Some attributes can be calculated from others. They are derived attributes, and we write a slash before the name. The age of a person is derived from the birth date: /age. You do not store it, you calculate it.

We can also show who may see an attribute. This is the visibility (Table 6.1). By default attributes are private and operations are public. Change the default only for a good reason.

Table 6.1 · Visibility of attributes and operations
SymbolVisibilityWho can see it
+PublicEvery other object.
#ProtectedThe class itself and its subclasses.
-PrivateOnly the class itself.
ExampleThe class Patient has the private attributes - name, - birthDate and - /age (derived). It has the public operation + makeAppointment().

6.2 Operations

Every class can create, read, update and delete its objects. If we showed these on every class, the diagram would be full of noise. So we show only the operations that are unique to the class and tied to the use cases. The textbook sorts operations into four types (Table 6.2).

Table 6.2 · Four types of operations
TypeWhat it doesExampleShow it?
ConstructorCreates a new object.insert()Not if it only creates.
QueryReads the state of an object, and changes nothing.calculate last visit()Not if it only returns an attribute.
UpdateChanges attribute values, maybe the state.change status()Yes, if it can change the state.
DestructorRemoves the object.delete()No.

An operation is followed by brackets, even if it has no parameters: calculateLastVisit(). If it needs a value, the parameter is written inside, as in makeAppointment(appointment).

6.3 Associations and multiplicity

An association is a line between two classes. We label it with a name (for example schedules) or with a role (marked with a plus sign). We use the name or the role, not both. A small black triangle next to the name shows the reading direction: patient schedules appointment. A class can also be associated with itself. A patient can be the primary insurance carrier of other patients, such as a spouse or a child.

Every end of an association has a multiplicity. It says how many objects of this class can be linked to one object of the class at the other end. We write it as minimum..maximum (Table 6.3). To read a multiplicity, start at one class, follow the line and read the number at the far end.

Table 6.3 · Multiplicities
WrittenMeansExample
1 (or 1..1)Exactly oneAn appointment has one patient.
0..1Zero or oneA spare tire is in zero or one trunk.
0..*Zero or moreA patient has zero or more appointments.
1..*One or moreA theater shows one or more movies.
2..4A given rangeA team has two to four members.
1..3, 5Separate rangesA bus has one to three or five doors (rare).
How to read a diagram aloudUse the pattern: Each [class A] is linked to [multiplicity] [class B]. Then turn it around. For the line between Patient and Appointment: Each patient schedules zero or more appointments. Each appointment is scheduled by exactly one patient. If a sentence sounds strange to a user, show the user the sentence, not the diagram. Users often find the mistake at once.

In the first line of Figure 6.2, each invoice belongs to exactly one purchase order (the 1 next to PurchaseOrder). Each purchase order can have zero or more invoices (the 0..* next to Invoice). Read every association in both directions. If one direction sounds wrong, the multiplicity is wrong.

Example“A patient must be assigned to only one doctor, and a doctor can have one or many patients.” Draw Patient and Doctor with a line. At the Doctor end write 1. At the Patient end write 1..*.

6.4 Association classes

Sometimes the link itself has attributes. This happens mostly when two classes are in a many-to-many relationship. A student takes many courses, and a course has many students. Where do we put the grade? Not in Student, because a student has a different grade in every course. Not in Course, because a course has a different grade for every student. A grade exists only for one student and one course together.

The answer is an association class. We draw it as a class that is attached with a dashed line to the middle of the association, and it carries the attributes of the link (Figure 6.3). Another example from the textbook is a job: it links a person and a company and may have a salary and a title.

Key pointCreate an association class only when the link has a unique attribute, operation or relationship. If it has none, remove the class and keep a plain association.

6.5 Generalization, aggregation and composition

Generalization is drawn as a solid line from the subclass to the superclass, with a hollow triangle at the superclass. The subclass inherits everything of the superclass and may add its own. Doctors, nurses and receptionists are kinds of employees, and employees and patients are kinds of participants. Typical words: is a kind of.

Aggregation and composition are for parts and wholes. Typical words: is a part of, is made up of. UML knows two kinds (Table 6.4). In both, the diamond is next to the whole.

Table 6.4 · Generalization, aggregation and composition compared
RelationshipQuestionSymbolExample
GeneralizationIs it a kind of?Hollow triangle at the superclassA nurse is a kind of employee.
AggregationIs it a logical part? Can the part belong to several wholes?White diamond at the wholeAn employee is part of a department.
CompositionIs it a physical part? Does the part belong to one whole only?Black diamond at the wholeA room is part of a building.

A simple test tells aggregation and composition apart: if the whole is destroyed, do the parts go with it? If yes, use composition. Rooms go with the building. Employees do not go with the department. Many experts say that the two diamonds are only “syntactic sugar” (extra notation), because the multiplicities show the same information. If your audience finds the two diamonds confusing, use a plain association with the right multiplicities.

6.6 A complete example

Figure 6.5 shows a part of the class diagram of the appointment system (simplified from Figure 4-11 of the textbook). Look for each element that we have learned. Participant is abstract (the name is in italics) and has the derived attribute /age. Employee and Patient are kinds of participants, and Doctor and Nurse are kinds of employees. A patient schedules zero or more appointments, and each appointment has one patient. Each patient is linked to one medical history (a plain association). The operations are only those that the use cases need.

6.7 From a story to a class diagram

Let us build a small model from a story. We use all that we have learned so far.

StoryThe IBU sports center keeps its members and the courses that they attend. Every member has a name, a phone number and a birth date. A course has a title and a price. A member can attend many courses, and a course has many members. The center records the date on which a member joined a course. A coach leads every course. A coach is a kind of employee.

We read the story sentence by sentence. Table 6.5 shows what we find and what we draw.

07Simplifying diagrams and object diagrams

7.1 Simplifying a class diagram

A real system can have hundreds of classes, and one diagram with all of them cannot be read. Table 7.1 shows three ways to simplify it.

Table 7.1 · Three ways to simplify a class diagram
WayWhat you do
Show only concrete classesLeave out the abstract classes. But this can make the diagram harder to read, when many associations of the abstract class are copied to the subclasses.
Use viewsShow a part of the model: only the classes of one use case, only one kind of relationship, or less detail in each class (name only, name and attributes, name and operations).
Group into packagesPut classes that belong together into one package and draw the packages.

7.2 Object diagrams

An object diagram is a part of a class diagram with real objects instead of classes. We take a small part of the class diagram and fill it with examples: John Doe, Appt1, Dr. Smith. The name of an object is underlined and written as object : Class. The values of the attributes are written in the box. A line between two objects is a link, an instance of an association.

Why do we draw them? It is easier to think about real examples than about abstractions. Object diagrams help us to find attributes, operations and relationships that are missing or in the wrong place. In the example of the textbook (Figure 4-18), a look at the appointment of John Doe shows that the attribute reason may be better as an association with a Symptom class. That is a change to the class diagram that we would not see without the example.

Look at the lower part of Figure 7.1. The line between johnDoe and appt1 is a link. It is an instance of the association schedules. The multiplicity 0..* above says that John Doe may have more appointments, and the multiplicity 1 says that appt1 belongs to him alone. When we draw an object diagram, we must be able to keep every multiplicity.

Key pointDraw an object diagram when you are not sure about a multiplicity or about where an attribute belongs. If the example cannot be drawn, the class diagram is wrong.

08Creating a structural model in seven steps

Structural modeling is iterative: first a rough model, then better and better. Today most analysts start from the use cases. The textbook recommends seven steps (Figure 8.1 and Table 8.1). It uses CRC cards first because they are easy to play, and then moves the information to the class diagram.

Table 8.1 · Seven steps to create a structural model
  1. Create CRC cards. Do a text analysis of the use-case descriptions (they are written as subject, verb, direct object, preposition, indirect object). Write the classes on cards.
  2. Review the cards. Ask: which tangible things, roles, incidents and interactions are there? Add what is missing.
  3. Role-play. Play every scenario of every use case. Add what the play shows.
  4. Create the class diagram. Transfer the cards: responsibilities become operations, attributes stay attributes, relationships are drawn as generalization, aggregation or association. Attributes are private and operations public, unless there is a reason.
  5. Review the class diagram. Now challenge every class, attribute, operation and relationship. Let a team member play the devil's advocate.
  6. Add patterns. Compare the model with known patterns and take what helps.
  7. Review the model. Verify and validate the cards and the diagram (Section 10).
RememberEvery change goes back onto the CRC cards. If the cards and the diagram say different things, nobody can trust either of them.

09Worked example: the library

The textbook builds the structural model of a library management system in small steps. Let us follow the steps for the use case Borrow Resource.

  1. Create the cards. The analyst, Susan, finds the nouns of the use case, challenges them (Table 4.3) and writes a card for each class that she keeps. The class Patron is abstract. It holds the name, the ID number and the address that Faculty/Staff, Student and Guest have in common. The class Resource is abstract too, with the attributes title, ID number and publisher. A Collection holds many resources and can add and delete a resource.
  2. Review with the user. Joe, the librarian, adds the other libraries as patrons, journals, podcasts, movies and music as resources, the location of a resource and the collections.
  3. Role-play. The team plays every use case. It finds that the activity diagram needs a few more activities. The diagram is redrawn with swimlanes (Figure 4-9 of the textbook).
  4. Draw the class diagram. The cards are moved into a first-cut class diagram (Figure 4-19). Patron and Resource appear as abstract superclasses, and Collection holds resources (aggregation).
  5. Add a pattern. Borrowing is a transaction, so the transaction pattern fits. Check-Out Desk, Transaction and Transaction Line Item are added (Figure 4-20), and the cards are updated.
  6. Ask new questions. Do we need all the subclasses (Book, Journal, DVD, CD, Podcast and others)? Does the use case now need to mention the new classes? Susan has to go back to Joe and to change the use case. This is what “iterative” means.

10Verifying and balancing the model

Before we go on to the behavioral models, we verify and validate the structural model. We use a walkthrough, as for the functional models (Reading 6). The analyst presents the model to developers and users, explains every class, attribute, operation and relationship, and links each class to at least one use case. People who did not build the model often find missing classes. Role-playing is a kind of walkthrough too.

We also check that the models agree with each other (Figure 10.1). There are two groups of checks. The first group compares the CRC cards with the class diagram (Table 10.1). The second group compares the structural models with the functional models (Table 10.2).

Table 10.1 · Do the CRC cards and the class diagram agree?
#CheckExample
1Every card is a class on the diagram, and every class has a card.The card Patient and the class Patient.
2Responsibilities on the front of a card are operations of the class, and the other way round.Make appointment is makeAppointment() in Patient.
3Collaborators imply a relationship on the back of the card and an association on the diagram.Appointment is a collaborator, so Patient and Appointment are associated.
4Attributes on the back of a card are attributes of the class.amount is in the card and in the class.
5Relationships on the card use the right symbol on the diagram.A-kind-of Participant is a hollow triangle. Has-parts is a diamond.
6An association class exists only if the link has something unique.Treatment has attributes of its own.
7The representation rules hold.A class cannot be its own subclass.
NoteWhen you add a pattern, the changes must be carried back to every card. In the textbook, after the transaction pattern is added, the Patient card must say that a patient is a kind of Participant (not of Person), and not a part-whole link to Medical History.
