01Introduction

Reading 4 showed how to write down what a system must do. A requirements definition is a list, and a list is hard to see as a whole. A client who reads forty numbered sentences cannot easily say: “Yes, this is the system I want.” We need a picture that shows the whole system on one page, in a form that the user can read without special training. This picture is the use-case diagram.

A use-case diagram shows two things: who uses the system (the actors) and what the system does for them (the use cases). It is simple on purpose. Users understand it, so it is a very good tool for a conversation between the analyst and the client. The diagram is drawn early, while the requirements are still being gathered, and it often makes the users remember functions that they forgot to mention.

02Learning objectives

After completing this reading, you should be able to:

  • explain what a use case is and why use cases matter in object-oriented development;
  • tell a logical model from a physical model;
  • name the elements of a use-case diagram and draw each of them correctly;
  • decide whether something can be an actor, and find the actors of a system;
  • use <<include>>, <<extend>> and generalization correctly;
  • follow the five steps that identify the major use cases;
  • follow the four steps that create a use-case diagram;
  • read a diagram and recognize the most common mistakes in diagrams.

03Functional modeling and use cases

3.1Three functional models

Chapter 3 of the textbook is about functional modeling. A functional model describes the business processes and the way the information system interacts with its environment. It shows the external, or functional, view of the system: how the users see the system, and not how the system works inside. Three models are used together:

Table 3.1 · The three functional models
ModelWhat it showsQuestion it answers
Use-case diagramThe main functions of the system and the users who interact with them.Who uses the system, and what for?
Activity diagramThe activities inside one business process and the order in which they happen.What happens, step by step?
Use-case descriptionA text that combines and extends the two diagrams.What exactly happens, in words?

This week we study only the first model, the use-case diagram. Activity diagrams and use-case descriptions come in the next lecture. All three models can describe the as-is system (how the business works today) or the to-be system (the new system that we want to build).

3.2What is a use case?

A use case is a formal way of representing how a business system interacts with its environment. In simple words, it is one function that the system offers to its users: “Manage Appointments”, “Borrow Resource”, “Place Order”. A use case is a high-level overview of a business process. It shows how the user sees the process, and not the internal mechanisms that make it work.

Why do use cases matter so much? The textbook gives four reasons:

  1. Object-oriented development is use-case driven. The use cases are the basis for the whole system.
  2. They are the primary drivers for all UML diagrams. Every later diagram shows the functionality of a use case from another point of view.
  3. They are the foundation for testing. Every use case, and every path through it, must be tested (Chapter 7).
  4. They are the foundation for user-interface design. Screens are designed to support use cases (Chapter 9).

A use case can be drawn for the current system or for the new one. Figure 3.1 shows where the use-case diagram stands in the functional modeling process. It comes right after the requirements have been gathered and before the processes are modeled in detail. The process is iterative: when you draw activity diagrams, you may discover a missing use case and return to the diagram.

3.3Logical models and physical models

Use-case diagrams are logical models. A logical model describes what the business does, and gives no hint about how it is done. It is also called a problem domain model. A physical model, in contrast, describes how the work is carried out: by hand or by computer, on paper or on the Web, in a filing cabinet or in a database. Physical models are made later, in design.

Table 3.2 · Logical and physical statements about the same functions
FunctionLogical (analysis)Physical (design)
AppointmentsRecord an appointment.Save the appointment in the MySQL database.
GradesShow grades to the student.Display the grades on the web page of the portal.
OrdersPlace an order.Tap the green Order button in the mobile app.
PaymentsPay for the ride.Charge the credit card through the payment API.

Why start with the logical model? Because it lets the analyst and the user think about how the business should run without being distracted by technology. If a use case is called “Click the Save button”, it is already a physical statement. The correct name is a goal of the user, such as “Manage Appointments”.

3.4Use case and scenario

A use case describes one and only one function in which users interact with the system. But there are usually several ways to go through this function. Each possible path through a use case is called a scenario. A scenario is an instance of a use case, like an object is an instance of a class.

Table 3.3 · One use case and some of its scenarios
Use caseScenarios (paths through the use case)
Manage AppointmentsA new patient makes an appointment. · An existing patient makes an appointment. · An existing patient changes an appointment. · An existing patient cancels an appointment.
Borrow ResourceA patron borrows an available book. · A patron tries to borrow a book that is out, and reserves it. · A patron asks for a book from another library.
Place OrderA customer orders and pays by card. · A customer orders and uses a coupon. · A customer's payment is refused.

The diagram shows the use case only once. The scenarios are used later, in activity diagrams and in testing. They also explain why the textbook says that a good use case is not too small: “change an appointment” and “cancel an appointment” are scenarios of Manage Appointments, and not separate use cases.

Key pointA use case is one function of the system, seen from the user's side. It is a logical model: it says what, not how. A scenario is one path through a use case.

04Elements of a use-case diagram

A use-case diagram has only a few kinds of elements: actors, use cases, a subject boundary, and the relationships between them. Figure 4.1 shows the symbols. The textbook gives the full syntax in Figure 3-1; our figure is a simplified version of it.

Figure 4.2 shows the first example of the textbook: the appointment system of a doctor's office. Three kinds of users are in the picture. Patients manage appointments, doctors record the times when they are available, and the management produces the schedule. We use this diagram, and the same system, in the following sections.

4.1Actors

An actor is drawn as a stick figure. The most important thing to remember is that an actor is a role, and not a specific person. “Patient” is an actor. “Mary Wilson” is not. Think of the actor as a class, and of the real people as objects that can play this role. One person can play several roles (a teacher may also be a student of another course), and many persons can play the same role.

An actor can be:

  • a person (role) who uses the system (patient, librarian, customer);
  • another system that talks to our system (a payment service, a registrar's system). Such an actor can be drawn as a rectangle with the word <<actor>> and the name of the system;
  • something that gives input to the system, receives output from it, or both.

Actors are always outside the system. They are the principal elements of the environment in which the system works. Test yourself with Table 4.1.

Table 4.1 · Can it be an actor?
CandidateActor?Reason
Ms. Mary SmithNoA specific person. Her role, for example Customer, is the actor.
CustomerYesA role that people play when they buy.
Internet customerYesA specialized role: a customer who buys over the Web.
Mr. John SealsNoA specific person, not a role.
SupplierYesA role: a company that delivers goods, or the system it uses.
Data entry clerkYesA role that enters data into the system.
Database administratorYesA role with its own goals (backup, access rights).
The customer's databaseNoPart of the system, not outside it.

4.2Specialized actors

Sometimes an actor plays a specialized role of a more general actor. A New Patient is a kind of Patient, but there are things that only a new patient does, for example filling in a registration form. The specialized actor is connected to the general actor with a line that ends with a hollow triangle, pointing at the general actor. The specialized actor inherits everything that the general actor can do, and adds something of its own.

4.3Use cases and their names

A use case is drawn as an oval inside the boundary. It is a major process that the system performs, and it must benefit an actor. If no actor profits from a use case, then it should not be on the diagram.

A use case is named with a short verb–noun phrase: Manage Appointments, Produce Schedule, Borrow Resource. The name says what the user wants to reach, and not which buttons the user presses.

Table 4.2 · Good and weak use case names
NameGood?Comment
Produce ScheduleYesVerb + noun, one goal of the management.
Borrow ResourceYesA goal of the patron, at the right size.
AppointmentNoA noun only. What happens with the appointment? Use Manage Appointments.
Click Save ButtonNoA physical step, not a goal.
Database UpdateNoA technical action inside the system, not seen by the actor.
Make Appointment and Pay and Print ReceiptNoThree functions in one oval. Split it, or find a general name.
Do ThingsNoToo vague to be useful.

4.4Associations

An association is a line between an actor and a use case. It shows that the actor takes part in this use case. Three rules help:

  • Every association connects one actor and one use case. A line never connects two actors, and it never connects two use cases (use cases are connected with include, extend or generalization).
  • The line usually means two-way communication: the actor gives something to the system and gets something back. If the communication goes only one way, add a solid arrowhead to show the direction of the information.
  • The diagram does not show order. The lines do not say what happens first.

4.5The subject boundary

The use cases are enclosed in a box, the subject boundary. The name of the subject (the system) is written in the box or on its top. The boundary defines the scope: what is inside the system and what is outside. Actors stand outside, use cases inside.

Where to draw the boundary is one of the hardest decisions. It can separate a software system from its environment, a subsystem from other subsystems, or a single process from the rest. In the appointment system, the doctor and the management use the system and stay outside. The textbook also discusses the receptionist, who talks to the patients in the doctor's office. The receptionist could be shown as an internal actor in an inner boundary. The textbook leaves the receptionist out, because internal actors start to bring in implementation decisions, and the receptionist is treated as part of the system. Expect the boundary to change during the project.

Key pointActors are roles outside the boundary, use cases are verb + noun goals inside it, and associations connect one actor with one use case.

05Include, extend and generalization

Sometimes a use case includes, extends or generalizes the functionality of another use case. The three relationships have different meanings, and mixing them is the most common mistake in use-case diagrams. To make diagrams easy to read, higher-level use cases are normally drawn above the lower-level ones.

5.1Include

<<include>> means mandatory behavior that several use cases share. When a use case always needs the same piece of work, we put this piece into its own use case, and the others include it. In the textbook, Record Availability and Produce Schedule both need routine work to maintain the doctor's schedule. This work is a separate use case, Manage Schedule, that both of them include.

The arrow is dashed, is labeled <<include>>, and goes from the base use case to the included use case. In this example, the included use case is drawn below; its position is a layout choice. Reading rule: “Record Availability always uses Manage Schedule.”

5.2Extend

<<extend>> means optional behavior that happens only under some condition. The textbook example: each time a patient makes an appointment, the patient is asked to verify payment arrangements. Sometimes, however, it is necessary to make new payment arrangements. This happens rarely, so it is an extension of Manage Appointments, called Make Payment Arrangements.

The arrow is dashed, is labeled <<extend>>, and goes from the extension to the base use case, so it points to Manage Appointments (upward in this example). Unlike include, it points from the extension toward the base. Reading rule: “Make Payment Arrangements sometimes extends Manage Appointments.” The base use case is complete without the extension.

5.3Generalization

Generalization means “is a kind of”. A special use case inherits all the behavior of a general use case, and adds its own. In the textbook, Manage Appointments is specialized into Make Old Patient Appt and Make New Patient Appt. Both do everything that Manage Appointments does, and each adds something special. The arrow is a solid line with a hollow triangle at the general use case, and it goes from the special to the general use case.

5.4Choosing the right relationship

When you are not sure which relationship to use, ask the question in Table 5.1. The lecture gives a short test: always happens → include; sometimes happens → extend; is a kind of → generalization.

Table 5.1 · Include, extend and generalization compared
<<include>><<extend>>Generalization
MeaningAlways happens; shared behaviorSometimes happens; optionalIs a kind of
LineDashed, open arrowheadDashed, open arrowheadSolid, hollow triangle
Arrow goesFrom base to includedFrom extension to baseFrom special to general
TestDoes the base need it every time?Does it happen only under a condition?Can I say “A is a kind of B”?
ExampleRecord Availability includes Manage ScheduleMake Payment Arrangements extends Manage AppointmentsMake New Patient Appt is a kind of Manage Appointments

Figure 5.4 puts all three relationships, and the specialized actors, into one diagram. This is the textbook's Figure 3-4 for the appointment system, redrawn. Read it slowly: find each arrow, say its meaning in a sentence, and check its direction. In this figure, include arrows point down and extend and generalization arrows point up. These positions are layout choices, not UML rules. Always follow the elements: include: base → included; extend: extension → base; generalization: special → general. Rotating or rearranging the diagram does not change those rules.

5.5Do not overuse the relationships

Beginners often decorate diagrams with <<include>> and <<extend>> everywhere. This makes the diagram hard to read and moves it away from the user's view. Use a relationship only when it helps the reader. A diagram with only actors, use cases and associations is a correct diagram. In particular:

  • do not split a use case into small steps and join the steps with <<include>> (that is functional decomposition, not use-case modeling);
  • do not add an included use case such as “Log In” to every use case. If login matters, show it once, or leave it for the description;
  • do not use <<extend>> for something that always happens.

06Identifying actors and major use cases

6.1The five steps

The textbook recommends five steps to find the major use cases.

  1. Review the requirements definition. Read the requirements definition (Reading 4) or the story that describes the requirements. This gives you the whole picture of the business process.
  2. Identify the subject boundary. Decide what is in scope. It will probably change while you work.
  3. Identify the primary actors and their goals. The actors come from the list of stakeholders and users. The goals are the functions that the system must give the actor.
  4. Identify the business processes and major use cases. Write only the major use cases. Do not describe one use case completely now. Define acronyms and jargon, so that people from outside the user group can understand the use cases.
  5. Review the current set of use cases. Split some use cases, merge others, add new ones. Identifying use cases is iterative, and users often change their minds.

6.2Stakeholders, actors and goals

A stakeholder is a person, group or organization that can affect the system or is affected by it. An actor is a role that a stakeholder or user plays: “doctor”, not “Dr. Jones”. Not every stakeholder is an actor. The sponsor who pays for the system may never touch it, so the sponsor is not an actor. The patient who books an appointment is both a stakeholder and an actor.

The goals of an actor are the functions that the system must offer for the system to be a success. To find them, ask three questions about every actor:

  1. Does the actor need to create, read, update, delete or execute (CRUDE) any information in the system?
  2. Are there external changes that the actor must tell the system about?
  3. Is there information that the system should give to the actor?
Table 6.1 · The three questions applied to the appointment system
ActorCRUDE (information)External changesInformation for the actor
PatientCreate, change and cancel an appointment.Moves to another address; new insurance.Confirmation of the appointment.
DoctorCreate and update availability.Holiday; sick leave.The list of today's patients.
ManagementRead the schedule; execute the report.A new doctor joins the office.The weekly schedule.

Each row of the table points to a use case: the patient's goals lead to Manage Appointments, the doctor's goals to Record Availability, and the management's goals to Produce Schedule. Steps 2 and 3 are intertwined: when you discover a new actor, you often discover that the boundary was too small or too large.

6.3Clues in a story

Most requirements come as text, so you need a way to read the text. A simple method is to look at the words. Nouns that name a kind of user are candidates for actors. Verbs that describe a goal are candidates for use cases.

Story · University gymAt the university gym, members swipe a card at the entrance. A member can book a place in a group class and can cancel the booking. The trainer enters the attendance after every class. The manager prints a monthly report about the attendance. Payments of membership fees are handled by the bank's system.
Table 6.2 · Reading the gym story
Clue in the textBecomesComment
member, trainer, managerActors (people)Roles. Everybody who uses the system is a member, trainer or manager.
the bank's systemActor (system)External system. Drawn as <<actor>> Bank System.
swipe a cardUse case: Enter GymOptional. It is in scope only if the new system controls the entrance.
book a place, cancel the bookingOne use case: Manage BookingsTwo verbs, one goal, as in Manage Appointments.
enters the attendanceUse case: Record AttendanceA goal of the trainer.

WarningThe text is only a clue. Not every noun is an actor and not every verb is a use case. Check each candidate: is it a role outside the system? Does the use case benefit an actor? Is it a goal and not a step?

6.4The right size and number of use cases

The hardest question is the size of a use case. We could have made “make an appointment”, “change an appointment” and “cancel an appointment” three separate use cases, but this would give a huge set of small ones. One use case, Manage Appointments, covers all of them.

  • Too many use cases probably means that the use cases are too small or that the boundary is too large.
  • Too few use cases means that each use case is too large and complex, and the activity diagrams that describe them will be hard to read.
  • All use cases on one diagram should be on the same level of abstraction. Do not mix “Manage Appointments” with “Click Save Button”.
  • When the diagram becomes crowded, group the use cases into packages and draw one diagram per package.

The right number depends on the complexity of the problem domain. Complexity can be moved between the number of use cases on the diagram and the detail in the activity diagrams. A useful rule of thumb for a classroom system: five to fifteen use cases on one diagram.

07Drawing the diagram

7.1The four steps

When the major use cases are known, drawing the diagram is easy. Only four kinds of things are drawn: use cases, actors, the boundary and associations.

  1. Place and draw the use cases. Take them from the list of major use cases. Add include, extend and generalization relationships. There is no formal order, so arrange them for readability.
  2. Place and draw the actors. Put each actor near the use cases that it uses, so that fewer lines cross.
  3. Draw the subject boundary. It separates the use cases (the functions of the system) from the actors (the roles outside).
  4. Add the associations. Connect each actor with the use cases it takes part in.

7.2Layout tips

  • Minimize crossing lines. Move the symbols until the diagram is easy to follow. Expect to redraw it several times.
  • People on the left, other systems on the right. A habit, not a rule, but it makes diagrams easy to compare.
  • Draw the higher-level use cases above the lower-level ones.
  • Keep the diagram on one page. If it does not fit, use packages.
  • Give the diagram a title, which is the name of the subject.

Remember that there are many correct diagrams for the same problem. Two students can draw different diagrams, and both can be right. Also remember: whenever a use case changes, check whether the diagram must change too.

7.3A checklist for a finished diagram

Table 7.1 · Checklist for a use-case diagram
#Check
1The system has a name, and the boundary is drawn around the use cases.
2Every actor is outside the boundary and is a role, not a person's name.
3Every use case is inside the boundary and has a verb–noun name.
4Every use case is connected to at least one actor, or is included or extended by another use case.
5Every association connects exactly one actor with one use case.
6The arrows of include, extend and generalization have the correct direction and label.
7All use cases are at the same level of abstraction.
8Nothing from the requirements is missing, and nothing is on the diagram that is not in the requirements.

7.4Drawing with diagrams.net

In the lab you will draw your diagrams with diagrams.net (formerly draw.io). It is free, runs in the browser at app.diagrams.net, and needs no installation or account. The first time you open it, choose where to save: Device saves the file on your computer. The shape library for use cases is called UML. Switch it on with More Shapes at the bottom of the left panel, tick UML, and click Apply. The library contains the actor, the use case oval, and the boundary (a container).

Two useful habits: save often as a .drawio file (this is the editable file), and at the end export the diagram as a PNG image with File → Export as → PNG. Always check the arrow direction and the label of every include and extend relationship, because the tool will not check them for you.

08Worked examples

This section is the heart of the reading. Each example gives a short story, the actors and use cases that we find in it, and the diagram. Read the story first, try to draw your own diagram on paper, and only then look at ours. Your diagram can be different and still be correct.

8.1Online university registration

This example comes from the practice slide of the lecture. We follow the five steps of Section 6.1 and the four steps of Section 7.1.

StoryAn online university registration system. Department staff examine, add, remove and change courses. Students examine courses, add and drop them, and view their enrollment. Department staff print reports. No student may take too many courses. Students with unpaid fees cannot register; the fees data belongs to the financial office.
  1. Review the requirements. The story above is our requirements. It names the users and the functions.
  2. Boundary. The registration system is the subject. The financial office has its own system with the fees data, so that system is outside.
  3. Actors and goals. Student: examine courses, register (add and drop), view enrollment. Department staff: manage courses (examine, add, remove, change), print reports. Financial office: provides the fees data. It is an external system, so it is an <<actor>> on the right.
  4. Major use cases. Browse Courses, Register for Courses (adding and dropping are two scenarios of one goal), View Enrollment, Manage Courses (examine, add, remove and change are CRUDE operations on courses), Print Reports. The two rules in the story become Check Fees and Check Course Load. Both are needed every time a student registers, so they are included.
  5. Review. Is “Drop Course” a separate use case? No, it is a scenario of Register for Courses. Do we need Log In? It is not in the story, so we leave it out.

Why is Check Fees associated with the Financial Office? Because the financial office supplies the information that the use case needs. Notice that the Student is not connected to Check Fees: the student never starts it, because the system starts it by itself when the student registers.

8.2Library management system

This is the running example of the textbook (Figure 3-5). The analyst, Susan, found two human actors, three external system actors and six use cases. She first thought of “borrow books” and “return books”, but because the library also lends DVDs and CDs, she generalized them into Borrow Resource and Return Resource. If a resource is not available, the patron can reserve it or ask another library for it. These are optional extensions of Borrow Resource. Retiring a resource that is returned is an extension of Return Resource.

  • Actors: Patron and Librarian (people); Registrar's System, Personnel System and Other Library (external systems — we assume that the Registrar's and Personnel Systems identify students and staff, and that Other Library supplies resources).
  • Use cases: Borrow Resource, Return Resource, Reserve Resource, Borrow Resource from Another Library, Procure Resource, Retire Resource.
LessonA name change (book → resource) can make three use cases out of nine. Choose names at the right level of generality.

8.3Online food ordering

StoryA customer chooses meals and places an order. To place an order the customer must pay, either by card or in cash on delivery; card payments are handled by an external payment service. If the customer has a coupon, the coupon can be applied during payment. The restaurant staff see the new orders and prepare them. The customer can follow the status of the order.
Table 8.1 · Decisions in the food ordering diagram
DecisionReason
Place Order includes Pay for OrderEvery order must be paid, so payment is mandatory: include.
Apply Coupon extends Pay for OrderOnly some customers have a coupon. It is optional: extend, with the arrow pointing to the base.
Payment Service is an <<actor>>It is an external system that takes part in payment.
“Prepare Meal” is not a use caseCooking happens in the kitchen, outside the system. The staff are connected to Place Order only because they receive the order. A real project would probably add a use case for them, such as Manage Orders.

8.4Hotel reservation

StoryAnybody can search for free rooms and book a room. Guests who have an account (registered guests) can also see the history of their bookings. At arrival the receptionist checks the guest in. At departure the receptionist checks the guest out, and the bill is paid through the bank's payment service.
  • Guest is the general actor. Registered Guest is a specialized actor: it inherits Search Rooms and Book Room and adds View Booking History. This is simpler than drawing three lines from Registered Guest.
  • Receptionist is a different role, even if the hotel's staff may also book rooms for guests by phone. If they do, add the line from Receptionist to Book Room.
  • Check In Guest and Check Out Guest are two use cases, because they happen at different times and have different results. This is different from “change” and “cancel” in the appointment example: there they are two paths through the same goal.

8.5IBU Exam Portal

This is the project of the Week 4 lab. Students see their exam grades online, teachers enter the grades of their courses, and the student affairs office checks and publishes them.

This diagram is simple and correct. Think about the questions that an analyst would ask the client. Can a student download a transcript? That adds one use case, as in the figure. Who sees the grades before they are published? Only the teacher and the student affairs office: this is a nonfunctional requirement (security), and not a new use case. Do teachers also correct grades? Probably yes, but it is part of Enter Grades (the textbook would say: it is a scenario).

8.6Bike sharing system

StoryA rider unlocks a bike at a station and returns it to any station. When a bike is returned, the ride is paid through an external payment service. If the rider notices that the bike is damaged, the rider can report the damage when returning it. The maintenance worker repairs the damaged bikes.
  • Return Bike includes Pay for Ride: a ride is always paid.
  • Report Damaged Bike extends Return Bike: it happens only when the bike is damaged.
  • Repair Bike has no relationship to the other use cases. It is a separate goal of the maintenance worker. It is connected with the rest only through the data (the damage report), and the diagram does not show data.

09Common mistakes

Most diagrams that students draw for the first time contain some of these mistakes. Use the table as a review list before you submit a diagram.

10Key takeaways

  • A use case is one function of the system, seen from the user's side. It is a logical model: what, not how.
  • An actor is a role, not a specific person. It can be a person or another system, and it stays outside the boundary.
  • A use case is an oval with a verb–noun name, and it must benefit an actor.
  • Every association connects one actor and one use case.
  • Include: always happens. Extend: sometimes happens. Generalization: is a kind of. Learn the direction of each arrow.
  • The subject boundary shows the scope, and it will change during the project.
  • Find the major use cases at the same level in five steps; draw the diagram in four steps.
  • There are many correct diagrams for the same problem. Check them against the requirements, not against one model solution.
