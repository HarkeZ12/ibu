02Quick sort: the idea

Quick sort is a divide-and-conquer sorting algorithm that works on the following principle:

  1. (Optionally) shuffle the array. The lecture calls this the performance “guarantee”, in quotation marks (Section 8 explains why).
  2. Partition (“divide”) the array so that, for some position j, the element a[j] is in its final place, there is no larger element to its left and no smaller element to its right.
  3. Sort each part recursively (“conquer”).

Once both parts are sorted, the whole array is sorted. So, unlike merge sort, quick sort has nothing to combine at the end.

Merge sortQuick sort
How it dividesin half, without looking at the elementsaround a pivot, by comparing every element with it
Where the work happenswhile merging (after the recursive calls)while partitioning (before the recursive calls)
What happens at the endtwo sorted halves are mergednothing: the parts are already in place

Quick sort was devised in 1959 by Tony Hoare. In his paper, it compared very favourably in speed with the sorting methods known at the time, hence the name. It is also known as partition-exchange sort, but “quick sort” is catchier, so that is the name that stuck around. :)

03Choosing the pivot

The element around which we partition the array is called the pivot. Different implementations choose it in different ways:

  • some pick the first element of the array, as the code in our course does;
  • some pick the last element of the array;
  • some pick a random element of the array;
  • the median-of-three approach picks the median of the first, the middle and the last element.

After partitioning around 3, everything smaller than 3 is on its left and everything larger on its right. The 3 is now in its final position, and it will never move again. The two parts, however, are not sorted yet, so we apply quick sort to both of them recursively, until we are left with parts of one element (or none), which cannot be partitioned any further.

Two versions of the exampleThe study notes describe the lecture’s illustration with the last element as the pivot, on [9, −3, 5, 2, 6, 8, −6, 1, 3] (pivot 3, result [−3, 2, −6, 1], 3, [8, 5, 9, 6]). The slides you got use the same numbers in a different order, [3, 9, −3, 5, 2, 6, 8, −6, 1], with the first element, like our code. Both lead to the same point: 3 lands at index 4, with four smaller elements on its left and four larger on its right. The order inside each part depends on the partitioning algorithm.
From the lecturePartitioning rearranges the array so that all elements left of the pivot are less than (or equal to) it, and all elements right of it are greater than (or equal to) it. With the first element 3 as the pivot, Sedgewick’s partitioning gives [2, 1, −3, −6] 3 [6, 8, 5, 9]: “3 is home at index 4”. “Everything in [2, 1, −3, −6] is smaller than 3, but it is not in order.”

04Sedgewick’s two-way partitioning

Partitioning is the key operation of quick sort, and there are several ways to do it. The one we study and use in this course is two-way partitioning by Robert Sedgewick, who resolved many open problems in the analysis of quick sort’s pivot selection schemes and proposed a number of optimizations. He is also the author (with Kevin Wayne) of Algorithms, 4th edition, the recommended book for this course. :)

  1. The first element, at index low, is the pivot. The pointers i and j start just outside the range: i = low, j = high + 1.
  2. Move i to the right as long as a[i] < pivot: those elements already belong on the left.
  3. Move j to the left as long as pivot < a[j]: those elements already belong on the right.
  4. Now a[i] is not smaller than the pivot and a[j] is not larger. If the pointers have not crossed, swap a[i] and a[j]: both are now on the correct side.
  5. Repeat until the pointers cross (i ≥ j). j is now the index where the two parts split.
  6. Finally, swap the pivot a[low] with a[j]. This brings the pivot into the gap between the two parts, and j is returned.
Strict <Both inner loops use a strict <, so i and j also stop on an element equal to the pivot. i stops at the first element not smaller than the pivot, j at the first element not larger than it.

Figure 1 follows the lecture’s example, the letters K R A T E L E P U I M Q C X O S, with K as the pivot. The pointer i stops at R straight away (R > K), and j walks past S, O and X before it stops at C (C < K). Swapping R and C fixes both at once. The next round swaps T and I (i passes A; j passes Q and M), and the one after that swaps L and E (i passes E; j passes U and P). Then i stops at L (index 6) and j at E (index 5), but now j is to the left of i. The pointers have crossed, so partitioning is over, and the last swap puts K at index 5, between the two parts. Every letter to its left is now smaller than K, and every letter to its right is larger.

While the pointers move, the invariant is: everything left of i is ≤ K and everything right of j is ≥ K.

06The whole sort

With partitioning in place, the sort itself is short. The public function quick_sort() shuffles the array (Section 8) and calls sort() on the whole range. If the range has fewer than two elements (high <= low), sort() returns, because there is nothing to sort. Otherwise, it calls partition(), which returns the pivot’s final index j, and then sorts [low..j − 1] and [j + 1..high] recursively. The pivot itself is left out of both calls, since it is already in place.

 1 quick_sort(arr, len) {
 2     shuffle(arr, len)
 3     sort(arr, 0, len - 1)
 4 }
 5 sort(arr, low, high) {
 6     if (high <= low) {
 7         return
 8     }
 9     j = partition(arr, low, high)
10     sort(arr, low, j - 1)
11     sort(arr, j + 1, high)
12 }

Figure 2 runs the whole sort on [4, 7, 2, 9, 5, 8, 3, 6] in this order (the study notes run it without the shuffle, so that you can follow it). The first partition puts 4 at index 2, with [2, 3] on its left and [9, 5, 8, 7, 6] on its right. The left part is settled after one more call. On the right, the pivot 9 happens to be the largest element, so everything else ends up on its left, and that call achieves very little. Five partitions and 24 comparisons later, the array is sorted.

07How fast is quick sort?

Best case. Every pivot lands exactly in the middle of its range, so half of the elements go before it and half after it. Just like in merge sort, the array is then halved about log N times, and each level of partitioning touches about N elements. That gives N log N steps, so the best case is Ω(N log N).

From the lectureBest-case example: [4, 7, 5, 6, 2, 3, 1]. The pivot 4 is the median, so it splits the array into [2, 1, 3] and [6, 5, 7]. Their pivots 2 and 6 are medians too, and the array is sorted after 2 levels of partitioning.

Average case. On average, the pivots do not split the ranges exactly in half, but every call still splits the array in two, so the average case is linearithmic as well, Θ(N log N) (the slides add: about 1.39 N log₂ N comparisons). In the lecture’s measurements, quick sort is even a little faster than merge sort, because it moves elements around less and needs no auxiliary array.

Worst case. It happens when every pivot is the smallest or the largest element of its range. It depends on the choice of pivot and the order of the elements. Since our implementation always picks the first element, that is exactly what a sorted or a reverse-sorted array gives us.

The pivot 1 has nothing to its left, so the right part is [3, 5, 8, 9]. Its pivot 3 again has nothing to its left, which leaves [5, 8, 9], and so on. Every partition removes only one element, so we get about N partitions of about N elements each (the slides: N − 1 partitions × ~N comparisons), which is O(N²). For these five elements, that is 6 + 5 + 4 + 3 = 18 comparisons in 4 partitions, which does not hurt. For 100,000 sorted elements, our run made 5,000,149,998 comparisons, about five billion.

08Why shuffle the array?

This is where shuffling comes in. If we shuffle the array uniformly before sorting it, the first element of every range is a random element, whatever order the input arrived in. A sorted or reverse-sorted input gets broken up, and the chance of shuffling an array of distinct elements back into sorted order is one in N!, which is very low. :) When we shuffled the same 100,000 sorted elements first, quick sort needed about two million comparisons instead of five billion.

The table is from the slides. The study notes report 2,184,832 comparisons for another shuffled run of the same 100,000 elements: the shuffle is random, so every run gives a slightly different number, always around two million.

Shuffling does not remove the worst caseAn unlucky shuffle can still produce bad pivots, so quick sort stays O(N²) in the worst case. Before the shuffle, a sorted input hits the worst case every single time. After it, the worst case depends only on the random numbers, and the chance of hitting it is extremely small for every input. That is why the lecture calls shuffling a performance “guarantee”, in quotation marks.

The Knuth shuffle

A popular and efficient way to shuffle is the Knuth shuffle, also known as the Fisher-Yates shuffle. It goes through the array from left to right, and in every iteration i it picks an index r between i and N − 1, uniformly at random, and swaps the ith element with the rth one. Every one of the N! possible orders of the array is then equally likely.

1 shuffle(arr, len) {
2     for (i = 0; i < len; i++) {
3         r = i + rand() % (len - i)
4         swap(arr, i, r)
5     }
6 }

rand() % (len − i) is between 0 and len − i − 1, so r is between i and len − 1: position i gets one of the elements not placed yet. Positions before i are done. The last element has no choice left (rand() % 1 = 0).

ir = i + rand() % (len − i)swaparray after

The slides’ run on arr = [1, 2, 3, 4, 5, 6], len = 6, with the random values 3, 1, 3, 1, 1, 0.

From the lectureOther good ways to avoid a bad pivot: a random pivot (the same “guarantee” as the shuffle) or the median of three (good on sorted input, but no guarantee).

09Space, stability and adaptivity

Space. Quick sort is an in-place sort: every swap happens inside the array itself, and there is no auxiliary array like in merge sort. It does use the call stack, though, because every recursive call that is still waiting keeps its data there. In the best and average case, the recursion is about log N levels deep, so the space complexity is Θ(log N). In the worst case (a sorted array without the shuffle), it is N levels deep, so the space complexity is O(N).

From the lectureMeasured: over 100 shuffles of 100,000 elements, the recursion was at most 46 calls deep (log₂ N ≈ 17). Not exactly log₂ N, but nowhere near N.

Stability. Quick sort is not stable. Partitioning swaps elements over long distances, and the final swap of the pivot can jump over many elements it was never compared with, so two equal elements can come out in the opposite order. You can see it in Figure 1: the first E (E₁) starts before the second one (E₂), but the last swap sends E₂ from index 5 to index 0, in front of E₁.

Adaptivity. Quick sort is also not adaptive. With the shuffle in front of it, its running time does not depend on the order in which the input arrived at all, because the shuffle destroys that order. Without the shuffle, it is even worse than not adaptive: a sorted array is its worst case, so the closer the input is to sorted, the slower quick sort gets.

11Dual-pivot quick sort

The idea of dual-pivot quick sort is to take two pivots: the first and the last element of the range. The left pivot must not be larger than the right one, so if it is, we swap them. Then we partition the rest of the range into three parts: elements smaller than the left pivot, elements between the two pivots (inclusive), and elements larger than the right pivot. Finally, we swap both pivots into place and sort the three parts recursively, so every partition places two elements instead of one.

The procedure uses three counters. The study notes call them i, j and k; the slides call the same counters lt, gt and k:

CounterStarts atMeaning
lt (study notes: i)low + 1, right after the left pivoteverything before it is smaller than the left pivot
gt (study notes: j)high − 1, right before the right pivoteverything after it is larger than the right pivot
kequal to ltthe iterator; everything from lt up to k lies between the pivots

While k is not past gt (k <= gt), we look at a[k]:

  • If it is smaller than the left pivot, swap it with a[lt] and increment both lt and k.
  • If it is larger than the right pivot, swap it with a[gt] and decrement gt. Do not move k here, because the element that has just arrived from position gt has not been looked at yet.
  • Otherwise, it belongs in the middle part, so simply increment k.

When the loop ends, decrement lt and swap a[lt] with the left pivot, then increment gt and swap a[gt] with the right pivot. Both pivots are now in place. Return both positions, then sort the three parts recursively: [low, lt − 1], [lt + 1, gt − 1] and [gt + 1, high].

 1 partition(arr, low, high) {
 2     if (arr[high] < arr[low]) {
 3         swap(arr, low, high)
 4     }
 5     lt = low + 1
 6     gt = high - 1
 7     k = lt
 8     while (k <= gt) {
 9         if (arr[k] < arr[low]) {
10             swap(arr, k++, lt++)
11         } else if (arr[high] < arr[k]) {
12             swap(arr, k, gt--)
13         } else {
14             k++
15         }
16     }
17     swap(arr, low, --lt)
18     swap(arr, high, ++gt)
19     pivots = new int[2]
20     pivots[0] = lt
21     pivots[1] = gt
22     return pivots
23 }

Study notes example. On [4, 7, 2, 9, 5, 8, 3, 6], the pivots are 4 and 6. The 7 is too large, so it is swapped to the right, and 3 arrives in its place. The 3 and the 2 are smaller than 4 and stay on the left. The 9 and then the 8 are too large and go to the right as well, which leaves 5 in the middle. Once the pivots are swapped in, we get [2, 3], 4, [5], 6, [9, 7, 8].

Dual-pivot quick sort has the same complexity as the two-way version, N log N on average and N² in the worst case, but it tends to be faster in practice, mostly because it goes over the array fewer times, which suits the processor’s cache. It was published by Vladimir Yaroslavskiy in 2009, and since Java 7 (2011), it has been Java’s default sort for arrays of primitive types such as int. Arrays of objects are sorted with Timsort, which is stable and which we met last week.

12Merge sort or quick sort?

Merge sort and quick sort are generally considered two of the best sorting algorithms available, and a critical part of today’s computing and programming infrastructure. Both are N log N on average. So which one should you use?

Arrays → quick sort. Quick sort is an in-place sort, while merge sort needs an auxiliary array of N elements. Allocating that array and copying elements into it costs time, which is why quick sort is usually preferred for sorting arrays. Merge sort, for its part, stays N log N even in the worst case, and it is stable.

Linked lists → merge sort. Two-way partitioning walks one pointer in from each end of the array and swaps elements that are far apart, and a singly linked list can only be walked in one direction (forward) and has no access by index. In a linked list we can insert items easily, without moving any data, so merging two sorted linked lists needs no extra space at all: we relink the nodes instead of copying the elements.

13Summary and glossary

  • Quick sort partitions the array around a pivot, so that the pivot is in its final place with nothing larger to its left and nothing smaller to its right, and then sorts both sides recursively.
  • Sedgewick’s two-way partitioning takes the first element as the pivot, moves i from the left and j from the right, swaps the pairs that are on the wrong sides, and finally swaps the pivot with a[j].
  • Quick sort is N log N in the best and average case and N² in the worst case, which a first-element pivot hits on sorted and reverse-sorted arrays.
  • Shuffling the array first (with the Knuth shuffle) makes the worst case extremely unlikely for every input, although it does not remove it.
  • Quick sort is in-place, but it uses log N stack space on average and N in the worst case. It is not stable and not adaptive.
  • Dual-pivot quick sort partitions around two pivots into three parts. It has the same complexity, it is often faster in practice, and Java uses it for arrays of primitive types.
  • Quick sort is usually preferred for arrays, and merge sort for linked lists.

Just remember to shuffle first, and quick sort will live up to its name. :)

  1. Shuffle → partition → recurse. After partitioning, the pivot is in its final place: nothing larger on its left, nothing smaller on its right. Nothing to combine at the end.
  2. Pivot choices: first (our code), last, random, median of three (first, middle, last).

  4. Time: N log N best and average, N² worst = sorted or reverse-sorted input with a first-element pivot.
  5. Knuth shuffle (r = i + rand() % (len − i)) makes the worst case extremely unlikely, but does not remove it.
  6. In-place, stack space log N (worst N). Not stable, not adaptive.
  7. Dual-pivot: first and last are pivots (swap if left > right), three parts, counters lt, k, gt. Yaroslavskiy 2009, Java 7 for primitives.
  8. Arrays → quick sort, linked lists → merge sort.

02The idea

Big idea: merge sort works after the recursive calls (merging); quick sort works before them (partitioning), so there is nothing left to combine.

1 · shuffle (optional, the “guarantee”)2 · partition: a[j] in its final place3 · sort both parts recursively
Trap: after partitioning, the two parts are on the correct sides but not sorted. Only the pivot is final.
Who devised quick sort, and when?

Tony Hoare, 1959.

What does quick sort do after both parts are sorted?

Nothing: the array is already sorted. There is no merge step.

Another name for quick sort?

Partition-exchange sort.

03Choosing the pivot

Big idea: the pivot decides how evenly the range is split.

Four ways

First element (our code), last element, random element, median of three (first, middle, last).

Lecture example

[3, 9, −3, 5, 2, 6, 8, −6, 1]: first → 3, last → 1, median of 3, 2, 1 → 2. After partitioning around 3, it is at index 4.

Trap: the median of three is the median (middle value) of three elements, not their average and not the middle element.
Which pivot does the course code use?

The first element of the range, arr[low].

Median of three for [8, 1, 4, 9, 6]?

First 8, middle 4, last 6 → median 6.

When does the recursion stop?

When a part has one element or none (high <= low).

04Sedgewick’s two-way partitioning

Big idea: two pointers walk towards each other; each stops at an element on the wrong side; swap them; when they cross, the pivot goes to j.

i (from the left)

Moves while a[i] < pivot. Stops at the first element not smaller (≥ pivot).

j (from the right)

Moves while pivot < a[j]. Stops at the first element not larger (≤ pivot).

KRATELEPUIMQCXOS around K: swaps R↔C, T↔I, L↔E; then i = 6 (L), j = 5 (E) → crossed; swap K with a[5] → E C A I E K L P U T M Q R X O S.

Trap: the pivot is swapped with a[j], not a[i]. j is the last element of the left part.
Strict < in both loops: what happens on an element equal to the pivot?

Both pointers stop on it (and it may be swapped).

Where does K end up?

Index 5.

What is true of everything left of i while the loop runs?

It is ≤ the pivot. Everything right of j is ≥ the pivot.

05Partition code

Big idea: ++i and --j move first, then compare. Two guards keep the pointers inside the range.

LineCodeRemember
2–3i = low, j = high + 1start just outside
5–6arr[++i] < arr[low] · if (i == high) breaki stops at the end
8–9arr[low] < arr[--j] · if (j == low) breakj stops at the pivot
11–12if (i >= j) break · swap(arr, i, j)crossed → stop
14–15swap(arr, low, j) · return jpivot home

[4, 7, 2, 9, 5, 8, 3, 6]: i at 7 (1), j at 3 (6) → swap(1, 6); i at 9 (3), j at 2 (2) → break; swap(0, 2) → [2, 3, 4, 9, 5, 8, 7, 6], return 2.

Trap: the guard for j is j == low (it may stop on the pivot itself, e.g. when the pivot is the smallest element), and j starts at high + 1, not high.
Pivot is the smallest element. Where does j stop?

At low (the pivot itself); the pivot stays where it is and j = low is returned.

Pivot is the largest element. Where does i stop?

At high (the i == high guard). j stops at high too, so the pivot is swapped to the end.

✍Tracing a partition by hand

Recipe for “what does the array look like after the first partition?”

  1. Circle the pivot: a[low].
  2. From the left (starting at low + 1), find the first element ≥ pivot. That is i.
  3. From the right (starting at high), find the first element ≤ pivot. That is j.
  4. If i < j: swap them and continue from the next positions. Otherwise stop.
  5. Swap the pivot with a[j]. Check: everything left is smaller, everything right is larger.

Quick check

The pivot’s final index = the number of elements smaller than it (for distinct elements). Use it to check your answer, but the order inside each part comes only from the swaps.

[5, 2, 8, 1, 9, 3], first partition?

i at 8 (2), j at 3 (5) → swap → [5, 2, 3, 1, 9, 8]; i at 9 (4), j at 1 (3) → crossed; swap(0, 3) → [1, 2, 3, 5, 9, 8], j = 3.

[6, 1, 2, 3], first partition?

i runs to the end (guard i == high), j stops at 3 (index 3); i ≥ j → swap(0, 3) → [3, 1, 2, 6], j = 3.

06The whole sort

Big idea: quick_sort = shuffle + sort(0, len − 1); sort returns if high <= low, else partition and recurse on [low, j − 1] and [j + 1, high].

On [4, 7, 2, 9, 5, 8, 3, 6]: pivots in order 4 → 2 → 9 → 6 → 8; 5 partitions, 11 calls to sort, 24 comparisons. Depth first: the left part is finished before the right part starts.

Trap: the pivot j is in neither recursive call. Empty calls like sort(0, −1) and sort(8, 7) do happen; they return at once.
Which call follows sort(0, 7) with j = 2?

sort(0, 1), the left part first (line 10).

Why does pivot 9 achieve very little?

It is the largest element, so all the others end up on its left; the range shrinks by just one.

07Best, average, worst

Best · Ω(N log N)

Every pivot is the median: log N levels × N.

Average · Θ(N log N)

Uneven but still two parts; ~1.39 N log₂ N compares. A bit faster than merge sort.

Worst · O(N²)

Every pivot is the smallest or largest: sorted / reverse-sorted with a first-element pivot.

Trap: the worst case is the sorted array (and reverse-sorted), not a random one. [1, 3, 5, 8, 9] → 4 partitions, 6 + 5 + 4 + 3 = 18 comparisons.
Why is a sorted array the worst case for our code?

The first element is always the smallest, so the left part is always empty and each partition removes only one element.

Why is quick sort usually faster than merge sort?

It moves elements less and needs no auxiliary array.

08Shuffle and the Knuth shuffle

Big idea: after a uniform shuffle, the first element of every range is random, whatever the input order was.

The “guarantee”

Worst case still O(N²), but it now depends only on the random numbers and is extremely unlikely for every input. Sorted, 100,000: ~5 billion → ~2 million compares.

Knuth / Fisher-Yates

For i from 0: r = i + rand() % (len − i) (between i and len − 1), swap(i, r). All N! orders equally likely.

Trap: r is chosen from i to N − 1, not from 0 to N − 1. It may equal i (the element stays).
Does shuffling make the worst case impossible?

No. It makes it extremely unlikely; that is why “guarantee” is in quotation marks.

len = 6, i = 2: possible values of r?

2 to 5 (rand() % 4 is 0..3).

Two other ways to avoid a bad pivot?

A random pivot (same guarantee) and the median of three (good on sorted input, no guarantee).

09Space, stability, adaptivity

Space

In-place (no auxiliary array), but the call stack: log N best/average, N worst.

Not stable

Long-distance swaps; in Figure 1 the last swap moves E₂ from index 5 to 0, in front of E₁.

Not adaptive

Shuffle destroys input order; without it, sorted input is the worst case.

Trap: “in-place” does not mean O(1) extra space for quick sort: the recursion still needs log N (worst N) stack space.
Why is quick sort unstable?

Swaps (especially the final pivot swap) jump over elements they were never compared with, so equal elements can change order.

Deepest recursion measured on the slides?

46 calls, over 100 shuffles of 100,000 elements (log₂ N ≈ 17).

10Other partitioning algorithms

Dual-pivot

Two pivots → three parts.

Dijkstra 3-way

Less / equal / greater than the pivot. Fast with many equal keys.

Bentley-McIlroy

Faster 3-way: equal keys gathered at the ends, then swapped into the middle.

Which strategy is fast when there are many duplicates?

Three-way partitioning (Dijkstra, Bentley-McIlroy).

11Dual-pivot quick sort

Big idea: first and last element are the pivots (swap them if left > right); one pass makes three parts and places two pivots.

a[k] is …do
< left pivotswap(k, lt), k++ and lt++
> right pivotswap(k, gt), gt−−, k stays (new element not looked at)
otherwisek++

Start: lt = low + 1, gt = high − 1, k = lt; loop while k <= gt. End: swap(low, --lt), swap(high, ++gt). Recurse on [low, lt−1], [lt+1, gt−1], [gt+1, high].

[4, 7, 2, 9, 5, 8, 3, 6] → [2, 3] 4 [5] 6 [9, 7, 8]. [24, 8, 42, 75, 29, 77, 38, 57] → [8] 24 [42, 38, 29] 57 [75, 77], lt = 1, gt = 5.

Trap: after a swap with gt, k does not move. Study notes name the counters i, j, k; slides name them lt, gt, k.
Complexity of dual-pivot quick sort?

Same: N log N average, N² worst. Faster in practice (fewer passes, cache-friendly).

Who, when, where?

Vladimir Yaroslavskiy, 2009; Java’s default for primitive arrays since Java 7 (2011). Objects: Timsort.

12Merge sort vs quick sort

Quick sort → arrays

In-place; no allocating and copying an auxiliary array. Faster on average.

Merge sort → linked lists

N log N even in the worst case, stable; merging relinks nodes, no extra space. Partitioning needs walking from both ends.

Trap: “merge sort needs N extra space” is about arrays. On linked lists its merge needs no extra space.
Why is quick sort a poor fit for a singly linked list?

Two-way partitioning walks a pointer in from each end; a singly linked list can only be walked forward and has no index access.

Which is faster at 10,000,000 random elements: quick sort or merge sort?

Quick sort, 1.1 s vs 1.3 s (Timsort 335 ms beats both).

!Top exam traps

  1. After partitioning only the pivot is final; the parts are not sorted.
  2. The pivot is swapped with a[j], and j is returned.
  3. i stops on ≥ pivot, j on ≤ pivot (strict < → they stop on equal keys).
  4. Worst case = sorted or reverse-sorted input with a first-element pivot, O(N²).
  5. Shuffling does not remove the worst case; it makes it unlikely for every input.
  6. Knuth: r between i and N − 1.
  7. In-place, but stack space log N (worst N).
  8. Not stable, not adaptive (merge sort: stable, not adaptive).
  9. Dual-pivot: after a swap with gt, k stays. Same Big-O, faster in practice.
  10. Java: dual-pivot for primitives, Timsort for objects.
  11. Arrays → quick sort; linked lists → merge sort.
