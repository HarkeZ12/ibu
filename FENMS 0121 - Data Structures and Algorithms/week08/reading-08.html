02Comparison and non-comparison sorts

All of the sorting algorithms we studied so far are comparison-based sorting algorithms. As the name suggests, they sort the array by comparing its elements against one another: if one element is greater than the other, they swap places, or one of them is copied first. If you look at their code, the only thing they ever do with two elements is compare them, as in arr[j] < arr[i].

Does every sorting algorithm have to work like this? No. An integer carries more information than the result of a comparison: it has digits that we can read one by one, and it can be used directly as an index into an array. Non-comparison sorts use exactly this. The best known are radix sort, counting sort and bucket sort, and this week we study the first two.

The lower boundChapter 8 of the book proves that a sort which only compares elements needs Ω(N log N) comparisons in the worst case. Radix sort and counting sort do not contradict this, because they read digits and use values as indices, which the proof does not allow.
From the lectureAny algorithm that sorts only by comparing elements needs at least about N log₂ N comparisons in the worst case. Non-comparison sorts rely on other principles: mathematical rules, the digits or characters of the elements, or a value used directly as an array index. The three on the slide:
  • Radix sort: sorts integers one digit at a time, by distributing them into 10 buckets (part 1 of the lecture);
  • Counting sort: counts how many times each value occurs, then places every element straight into its position (part 2);
  • Bucket sort: spreads the elements into ranges (buckets), sorts each bucket on its own, and joins the buckets (not covered further).
“The lower bound does not apply to them: reading one decimal digit has 10 possible answers, a comparison only 2.”

03Radix sort

Radix sort is a non-comparison sorting algorithm that distributes the elements into bins, or “buckets”, based on their radix (hence the name). Whereas the previous algorithms could be applied to almost any kind of data, radix sort needs a “special condition” in the data: we must be able to pick out a radix from every element. For integer data, the digits serve as the radixes, so the radix is 10 and we need ten buckets, labelled from 0 to 9.

The operating principle of radix sort on integers:

  1. In every iteration, sort the elements by one digit, starting from the least significant digit (LSD), the units.
  2. To sort by a digit, go through the array from left to right and drop each element into the bucket of its current digit.
  3. Join the buckets together in order, from bucket 0 to bucket 9: the array is now sorted by that digit.
  4. Repeat for the next digit (tens, hundreds, …) until you run out of digits.

Radix sort by hand

Let us apply radix sort to the lecture’s example, [41, 2, 38, 57, 37, 66, 90, 88, 7, 35] (Figure 1). In the first iteration, the elements are distributed by their units digit: 90 goes to bucket 0, 41 to bucket 1, 2 to bucket 2, and so on. Three elements end with a 7, so bucket 7 holds 57, 37 and 7, in the same order in which they appear in the array. Joining the buckets gives [90, 41, 2, 35, 66, 57, 37, 7, 38, 88], which is sorted by the units digit.

In the second iteration, we distribute the elements by the tens digit. The numbers 2 and 7 do not have a tens digit, so we use 0 as a placeholder, as if they were written 02 and 07, and they go into bucket 0. After joining the buckets, the array is [2, 7, 35, 37, 38, 41, 57, 66, 88, 90], and it is sorted. Since the largest element, 90, has two digits, we needed two iterations. In general, radix sort makes as many iterations as there are digits in the largest element, whatever the lengths of the smaller ones. We sorted the array without ever comparing two of its elements with each other.

From the lectureThe radix (or base) is the number of possible digit values, and so the number of buckets: 10 for decimal digits. Radix sort needs keys that can be split into digits (or characters). The procedure slides: “We place the elements from left to right: 41 → bucket 1, 2 → bucket 2, 38 → bucket 8, …”, “57, 37 and 7 share bucket 7, in their original order”, and in the 2nd iteration “a missing digit is a 0: 02 and 07”; 35, 37 and 38 go to bucket 3, “still in array order”. “There are as many iterations as there are digits in the largest element, and no two elements are ever compared.”

04Why the least significant digit, and why stable?

The most significant digit tells us the most about the order of two numbers, so why start from the other end? Because the last pass decides the final order. Take [51, 19, 45, 12]:

Sorting by the units and then by the tens gives [12, 19, 45, 51], but sorting by the tens first and the units second gives [51, 12, 45, 19], which is only sorted by the units, the digit of the last pass.

This is also why every pass must be stable. When the tens pass puts 35, 37 and 38 into bucket 3, it must keep them in the order that the units pass gave them, or it throws away the work of the earlier pass. Inside a pass, the elements of one bucket are never compared with each other: their order is simply the order in which they arrived.

Exam trapA pass that reverses the elements inside a bucket still puts every element in the right bucket, but it destroys what the previous passes did. Radix sort is correct only because each pass is stable.
From the lecture“Radix sort must be stable: we must not mix up the elements inside a bucket. 57 comes before 37 in the array, so we copy them into bucket 7 in that order, and do not swap them.” The stability slide uses [4, 8₁, 8₂, 1]: two equal 8s, and “bucket 8 keeps them in order.”

05Radix sort in code

We use the same code structure as in the previous weeks. The NonComparisonSort namespace contains a public radix_sort(), a static sort() that sorts the array by one digit, a helper get_max() and the public counting_sort(). Here is the public function from the lecture, with the line numbers the slides use:

 1 radix_sort(arr, len) {
 2     if (len < 2) {
 3         return
 4     }
 5     max = get_max(arr, len)
 6     for (exp = 1; max / exp > 0; exp *= 10) {
 7         sort(arr, len, exp)
 8     }
 9 }
10 get_max(arr, len) {
11     max = arr[0]
12     for (i = 1; i < len; i++) {
13         if (arr[i] > max) {
14             max = arr[i]
15         }
16     }
17     return max
18 }

radix_sort() finds the largest element and runs one pass per digit with for (exp = 1; max / exp > 0; exp *= 10). For a largest element of 451, 451 / 1, 451 / 10 and 451 / 100 are all greater than 0, but 451 / 1000 is 0 in integer division, so the loop runs three times, once for each digit.

Inside a pass, (arr[i] / exp) % 10 picks out the current digit: for 451, it gives 1, then 5, then 4. A number with no digit at that position, such as 7 in the tens pass, gives 0, which is our placeholder zero.

06One pass: frequency and aux

Instead of ten real buckets, sort() uses a frequency array of ten counters and an auxiliary array aux:

 1 sort(arr, len, exp) {
 2     aux = new Data[len]
 3     frequency[10] = {0}
 4     for (i = 0; i < len; i++) {
 5         digit = (arr[i] / exp) % 10
 6         ++frequency[digit]
 7     }
 8     for (i = 1; i < 10; i++) {
 9         frequency[i] += frequency[i - 1]
10     }
11     for (i = len - 1; i >= 0; i--) {
12         digit = (arr[i] / exp) % 10
13         aux[--frequency[digit]] = arr[i]
14     }
15     for (i = 0; i < len; i++) {
16         arr[i] = aux[i]
17     }
18     delete[] aux
19 }
  1. Count (lines 4–7): how many elements have each digit.
  2. Running totals (lines 8–10): frequency[d] now tells us where bucket d ends. In the units pass of Figure 1, frequency[7] becomes 8, so bucket 7 ends just before position 8.
  3. Place backwards (lines 11–14): go through the array from the end and place every element with aux[--frequency[digit]] = arr[i]. The 7 goes to position 7, then 37 to position 6 and 57 to position 5.
  4. Copy back (lines 15–17): aux is copied into arr and deleted.

Filling every bucket from its end, backwards, keeps equal digits in their original order, which makes the pass stable.

From the lectureThe slide traces sort() on the units pass: lines 2–7 count the digits 1, 2, 8, 7, 7, 6, 0, 8, 7, 5; lines 8–10: running totals, “frequency[d] is where bucket d ends”; i = 9: 35 → digit 5, frequency[5]: 4 → 3, so aux[3] = 35; i = 8: 7 → digit 7, frequency[7]: 8 → 7, so aux[7] = 7; then i = 7 … 0, copy back: “arr is now sorted by digit 0.”

07Radix sort complexity

In every iteration, radix sort goes over all N elements and places them into b buckets, and there are d iterations, one for each digit of the largest element. This gives

Θ(d (N + b)) in the best, the average and the worst case

Some books leave out b, since ten buckets are nothing next to a large N, and write Θ(d N). For the purposes of this course, it is fine to memorize either one. :)

Radix sort needs the auxiliary array of N elements and the b counters, so its space complexity is Θ(N + b) in all cases. It is stable, since every pass is stable, and it is non-adaptive, because the number of iterations depends only on the number of digits in the largest element and not on how sorted the array already is.

Worst caseAverage caseBest case
TimeΘ(d (N + b))Θ(d (N + b))Θ(d (N + b))
SpaceΘ(N + b)Θ(N + b)Θ(N + b)

N: the number of elements, d: the number of digits of the largest element, b: the number of buckets (the base, 10 for decimal digits). Stable: equal elements keep their order. Non-adaptive: sorted input is not faster.

Non-negative integers onlyRadix sort, as we implemented it, works only for non-negative integers, and the course code does not check this. When we ran it on [−5, −1, −9, −3], the array came back unsorted, because max / exp > 0 is false straight away and no pass runs. With mixed signs, the digit is negative and the code writes outside its arrays.
From the lectureSpace: “We need b buckets and room for the N elements in them (the buckets cannot be made ‘in place’) … In the code: the aux array and the 10 counters.” Stable: “Every step (placing into buckets) is stable, so the entire algorithm is stable.” Non-adaptive: “The number of iterations depends only on the number of digits of the largest element, not on the order of the elements.” On negatives: “a negative element gives a negative digit, and the code fails (an all-negative array comes back unsorted).”

08Radix sort vs. the world

So, is radix sort better than merge sort and quick sort? The answer is: it depends on the data. In theory, d (N + b) can be less than N log N. For a million elements whose largest element has ten digits:

AlgorithmSteps
Merge sort / quick sortN log₂ N ≈ 1,000,000 × 19.93 ≈ 19.9 million
Radix sortd (N + b) = 10 × (1,000,000 + 10) = 10,000,100

However, a step of radix sort costs more than a comparison, so the steps alone do not tell us which one is faster. In the book’s experiment, with values between 0 and a million, radix sort sorted 3.2 million elements 8 times faster than merge sort, while in the lecture’s measurements (Section 12), the two are about equally fast.

Things get harder when the data are not integers:

  • Floating-point numbers do not have digits in the sense radix sort needs, so we would have to multiply them by a power of ten (10, 100, 1000, …) and sort them as integers.
  • Strings can be sorted character by character, with 128 buckets for ASCII, or 256 if we sort byte by byte, but Unicode has 1,114,112 possible code points, so we would need over a million buckets.

That is why radix sort is generally said to be an excellent specialized algorithm, which performs very well on one type of data (integers), while merge sort and quick sort are better general-purpose algorithms, which need nothing more than a way to compare two elements.

From the lecture“The steps are not the same size: a radix step computes a digit and writes the element far away in memory.” For integers, radix sort can still perform very well, “since digits are easy to find with arithmetic (/ and %). However, if the number of buckets grows too large, performance drops.” Floats: one solution is to multiply by a power of 10, “if we know the precision we need.” Strings: 256 buckets for bytes “also covers UTF-8 text, byte by byte”; strings also differ in length, “so the short ones must be padded.” Sorting by several fields or sorting objects “would be next to impossible: radix sort needs digits, while a comparison sort only needs a <.” That is also why C++ std::sort is a quick sort variant and not a radix sort: “a library function cannot assume that its keys are integers.”

09Counting sort

Counting sort is a non-comparison sorting algorithm that sorts an array by counting how many times each value occurs in it. It works well when the values come from a limited range, especially when that range is small compared to the number of elements, such as a million exam marks from 0 to 100.

Counting sort by hand

The procedure has four steps. We follow the lecture’s example, [4, 2, 2, 8, 3, 3, 1] (Figure 3):

  1. Find the largest element, max, which is 8 here.
  2. Create a count array of length max + 1, with all elements set to 0, and store the count of each element at its own index. The 3 appears twice, so count[3] is 2, and the 5 does not appear at all, so count[5] is 0. This gives [0, 1, 2, 2, 1, 0, 0, 0, 1].
  3. Turn the counts into running totals, by adding to every element of count the element at the previous index. This gives [0, 1, 3, 5, 6, 6, 6, 6, 7], and now count[v] says how many elements are smaller than or equal to v. For example, five elements are 3 or less.
  4. Go through the original array in reverse order. For every element, decrement count at the index of that element, and use the new value as the position of the element in the output array.

The last element of our array is 1. count[1] is 1, so we decrement it to 0 and place the 1 at position 0 of the output. The element before it is a 3, and count[3] goes from 5 to 4, so this 3 goes to position 4. The other 3 then goes to position 3, the 8 to position 6, the two 2s to positions 2 and 1, and finally the 4 to position 5. The output array is [1, 2, 2, 3, 3, 4, 8], and once again, no two elements were compared.

From the lectureCounting sort “works well when the range of input values (k) is small compared to the number of elements to be sorted (N).” The idea: “count how often each distinct value occurs, and use those counts to place every element straight into its sorted position.” The running-totals slide: count[1] = 1 + 0 = 1, count[2] = 2 + 1 = 3, count[3] = 2 + 3 = 5, … “5 elements are ≤ 3, so the last 3 belongs at index 4.” The summarized procedure: (1) find max and create a count array of length max + 1; (2) count each element, count[v]++; (3) turn the counts into cumulative sums; (4) walk the array backwards: decrement count[v] and put v at that index.

Live demo: counting sort exactly like the course code: max, the counts, the running totals, and then every placement of the backward walk. Integers from 0 to 30, separated by spaces or commas (2 to 12 numbers).

10Counting sort in code

The function counting_sort() follows these steps exactly:

 1 counting_sort(arr, len) {
 2     if (len < 2) {
 3         return
 4     }
 5     max = get_max(arr, len)
 6     count = new int[max + 1]()
 7     output = new Data[len]
 8     for (i = 0; i < len; i++) {
 9         ++count[arr[i]]
10     }
11     for (i = 1; i <= max; i++) {
12         count[i] += count[i - 1]
13     }
14     for (i = len - 1; i >= 0; i--) {
15         output[--count[arr[i]]] = arr[i]
16     }
17     for (i = 0; i < len; i++) {
18         arr[i] = output[i]
19     }
20     delete[] count
21     delete[] output
22 }

It finds max with get_max(), creates int* count = new int[max + 1](), where the () sets all counters to zero, and an output array of the same length as the input. Its four loops count the elements with ++count[arr[i]], compute the running totals, place the elements backwards with output[--count[arr[i]]] = arr[i], and copy output back into arr.

int, not DataNotice that count is an array of int, since it holds frequencies, which have nothing to do with the type of the elements. The lab sheet still shows Data* count, which would overflow for a small type such as char.

Why backwards?

With decreasing counters, the last of several equal elements is placed first, at the end of its block. In our example, the second 3 went to position 4 and the first 3 to position 3, so the two kept their original order, which makes counting sort stable. Every pass of radix sort is exactly this counting sort, applied to one digit.

From the lectureThe code slide traces arr = [3, 1, 4, 1, 5, 2, 4, 3], max = 5: lines 5–10 count the values; lines 11–13 running totals, count[3] = 5: “five elements are ≤ 3”; i = 7: arr[7] = 3, count[3]: 5 → 4, so output[4] = 3; i = 6: arr[6] = 4, count[4]: 7 → 6, so output[6] = 4; then i = 5 … 0 and copy back: arr = [1, 1, 2, 3, 3, 4, 4, 5].

11Counting sort complexity and viability

Counting sort goes over the N elements of the array a few times and over the count array once. If we write k for the size of the count array, which is the largest value plus one, the time complexity is

Θ(N + k) in the best, the average and the worst case

The space complexity is Θ(N + k) as well, for the count array and the output array. Counting sort is stable and non-adaptive, since the number of iterations does not depend on how the elements are ordered.

Similar to radix sort, counting sort performs very well on integer data, and it can beat merge sort and quick sort when the range of values is of the order of the number of elements. However:

  • a negative number cannot be used as an index into count;
  • when k is much larger than N, it wastes memory: sorting five numbers whose largest value is a million needs a count array of 1,000,001 integers, about 4 MB.

In conclusion, counting sort is a good specialized sorting algorithm, but not a good general-purpose one.

From the lecture“k is not a constant.” Stability on the slide: [4, 8₁, 8₂, 1]: at i = 2, 8₂ → output[3]; at i = 1, 8₁ → output[2]. “The last 8 is placed first, at the end of the 8s, and the first 8 just before it. (Walking forwards with the same code would reverse them.)” Negative integers: “how would you ‘use’ negative indexes? (A fix: subtract the minimum from every element first, and add it back at the end.)” Counting sort has the same limitations as radix sort: “it is tedious or difficult to apply to characters, strings, floating-point numbers, …”

13Summary and glossary

  • Comparison-based sorts learn about the elements only by comparing them, and none of them can do better than Ω(N log N) in the worst case. Non-comparison sorts, such as radix sort and counting sort, read digits or use values as indices instead.
  • Radix sort sorts integers one digit at a time, from the least significant digit, by distributing them into ten buckets and joining the buckets in order. It makes one pass for every digit of the largest element.
  • Every pass of radix sort must be stable, or the later passes destroy the work of the earlier ones. Our sort() makes each pass with a counting sort on the digit (arr[i] / exp) % 10.
  • Radix sort takes Θ(d (N + b)) time and Θ(N + b) space in all cases. It is stable and non-adaptive.
  • Counting sort counts how many times each value occurs, turns the counts into running totals, and places every element, going backwards, at the position its counter gives. It takes Θ(N + k) time and space in all cases, and it is stable and non-adaptive.
  • Both algorithms, as implemented here, work only on non-negative integers. They are excellent specialized algorithms, while merge sort and quick sort remain the better general-purpose ones.

So, can we do better than N log N? Perhaps, if your data are integers. :)

⏱The 60-second version

  1. Comparison sorts (everything so far) need Ω(N log N) in the worst case. Non-comparison sorts (radix, counting, bucket) read digits or use values as indexes, so the bound does not apply to them.
  2. Radix sort: 10 buckets (0–9); one pass per digit, from the least significant digit (units); drop the elements in array order, join buckets 0 → 9. A missing digit is a 0.
  3. Number of passes = number of digits of the largest element: for (exp = 1; max / exp > 0; exp *= 10); digit = (arr[i] / exp) % 10.
  4. Every pass must be stable; sort() does it with frequency[10] (counts → running totals) and aux, filling from the back: aux[--frequency[digit]] = arr[i].
  5. Radix: time Θ(d (N + b)) (or Θ(d N)), space Θ(N + b), all cases. Stable, non-adaptive.
  6. Counting sort: max → count of length max + 1 → counts → running totals (count[v] = how many ≤ v) → walk backwards: output[--count[arr[i]]] = arr[i].
  7. Counting: time and space Θ(N + k), k = max + 1, all cases. Stable, non-adaptive.
  8. Both: non-negative integers only (as implemented). Excellent specialized, not general-purpose.

02Comparison vs. non-comparison

Big idea: a comparison only says “smaller or not”. An integer can tell us more: its digits, and it can be an index.

Comparison-based

Bubble, selection, insertion, Shell, merge, quick sort. Only question asked: arr[j] < arr[i]. Lower bound Ω(N log N), worst case.

Non-comparison

Radix (digits, 10 buckets), counting (values as indexes), bucket sort (ranges, each bucket sorted on its own).

Trap: radix and counting sort do not disprove the Ω(N log N) bound. The proof assumes a sort that only compares, and they do not.
Name three non-comparison sorts.

Radix sort, counting sort, bucket sort.

Why does the lower bound not apply to them?

They read digits and use values as indices, which the proof does not allow. A digit has 10 possible answers, a comparison only 2.

Which chapter proves the bound?

Chapter 8 of the book.

03Radix sort

Big idea: sort by one digit at a time, units first, with ten buckets; join the buckets 0 → 9 after every pass.

1 · digit = units2 · drop left to right into bucket 0–93 · join 0 → 94 · next digit

The lecture’s example

[41, 2, 38, 57, 37, 66, 90, 88, 7, 35] → units → [90, 41, 2, 35, 66, 57, 37, 7, 38, 88] → tens → [2, 7, 35, 37, 38, 41, 57, 66, 88, 90]. Bucket 7 in pass 1: 57, 37, 7. Bucket 0 in pass 2: 02, 07.

Trap: the number of passes comes from the largest element’s digits, not the smallest, not the first, and not N.
Why is it called “radix” sort?

It distributes the elements by their radix (base): 10 possible digit values, 10 buckets.

Where does 7 go in the tens pass?

Bucket 0: a missing digit is a placeholder 0 (07).

How many passes for [5, 1200, 33]?

4: the largest element, 1200, has four digits.

04LSD and stability

Big idea: the last pass decides the final order, so it must be the most significant digit, and every pass must keep the order of the previous one.

LSD (units → tens)

[51, 19, 45, 12] → [51, 12, 45, 19] → [12, 19, 45, 51] ✔

Tens first, units last

[51, 19, 45, 12] → [19, 12, 45, 51] → [51, 12, 45, 19] ✘ sorted only by the units

Trap: “unstable but right buckets” is still wrong: reversing 35, 37, 38 inside bucket 3 throws away the units pass.
Which pass decides the final order?

The last one, so it must sort by the most significant digit; LSD order gets there.

Why must each pass be stable?

Otherwise the later passes destroy the order the earlier passes produced for equal digits.

Are elements inside a bucket ever compared?

No. They stay in the order they arrived.

05The exp loop

Big idea: exp walks 1, 10, 100, … and the loop stops as soon as max / exp becomes 0 in integer division.

for (exp = 1; max / exp > 0; exp *= 10)
    sort(arr, len, exp)        // digit = (arr[i] / exp) % 10

max = 451

exp 1, 10, 100 → digits 1, 5, 4 → 3 passes; 451 / 1000 = 0 → stop.

Missing digit

7 with exp = 10: 7 / 10 = 0, 0 % 10 = 0 → the placeholder zero.

Trap: arr[i] / exp without % 10 keeps every higher digit (4517 / 100 = 45); the digit is 5.
What do lines 2–4 of radix_sort() do?

Return straight away for fewer than 2 elements.

(30602 / 1000) % 10?

30602 / 1000 = 30, 30 % 10 = 0.

What does get_max() cost?

One walk through the array: lines 11–17 of the code slide, Θ(N).

06frequency and aux

Big idea: no real buckets. Count the digits, turn the counts into running totals (= where each bucket ends), then fill aux backwards.

4–7 · count8–10 · running totals11–14 · backwards: aux[--frequency[digit]]15–17 · copy back, delete aux

Units pass of the example

counts [1, 1, 1, 0, 0, 1, 1, 3, 2, 0] → totals [1, 2, 3, 3, 3, 4, 5, 8, 10, 10]. i = 9: 35 → aux[3]; i = 8: 7 → aux[7]; then 37 → 6, 57 → 5.

Trap: --frequency[digit] decrements before the index is used: the first element with digit 7 goes to 7, not 8.
What does frequency[d] mean after the running totals?

How many elements have a digit ≤ d, i.e. where bucket d ends.

Why walk backwards in lines 11–14?

Each bucket is filled from its end, so equal digits keep their order: the pass is stable.

How big is frequency?

10 counters, one per decimal digit.

07Radix complexity

Big idea: d passes, each over N elements and b buckets; the same in every case.

Time

Θ(d (N + b)) best = average = worst. Some books: Θ(d N). Both are fine for this course.

Space

Θ(N + b): aux (N) and the counters (b). Not in-place.

Stable

Every pass is stable.

Non-adaptive

Passes depend only on the digits of the max, not on the order.

Trap: negative numbers. All-negative → max / exp > 0 is false at once, no pass runs, array stays unsorted. Mixed signs → negative digit → writes outside its arrays.
What are d, N, b?

d: digits of the largest element; N: number of elements; b: number of buckets (10).

Is radix sort faster on an already sorted array?

No, it is non-adaptive.

What happens on [−5, −1, −9, −3]?

max = −1, −1 / 1 > 0 is false, no pass runs: the array comes back unsorted.

08Radix vs. the world

Big idea: fewer steps on paper, but each step is more expensive; and it needs digits. Specialist, not all-rounder.

On paper

1,000,000 elements, 10 digits: N log₂ N ≈ 19.9 million vs. d (N + b) = 10,000,100.

In practice

Book: 8× faster than merge sort (3.2 million values). Lecture: about equal (1.3 s).

  • Floats: multiply by a power of ten (10, 100, 1000, …) and sort as integers.
  • Strings: 128 buckets (ASCII), 256 (bytes); Unicode 1,114,112 code points → over a million buckets.
  • Merge and quick sort only need a way to compare two elements.
Trap: “d (N + b) < N log N, so radix sort is always faster” is false: the steps are not the same size.
Why is std::sort not a radix sort?

A library function cannot assume its keys are integers (slide).

How many buckets to sort by bytes?

256.

09Counting sort

Big idea: count each value, turn counts into “how many ≤ v”, and place every element straight into its slot, walking backwards.

1 · max2 · count[max + 1], count each3 · running totals4 · backwards: decrement, place

The lecture’s example

[4, 2, 2, 8, 3, 3, 1]: max 8 → counts [0, 1, 2, 2, 1, 0, 0, 0, 1] → totals [0, 1, 3, 5, 6, 6, 6, 6, 7] → placements 1→0, 3→4, 3→3, 8→6, 2→2, 2→1, 4→5 → [1, 2, 2, 3, 3, 4, 8].

Trap: the count array has max + 1 slots (indexes 0 to max), not N slots.
When does counting sort work well?

When the range of values (k) is small compared to the number of elements (N), e.g. a million exam marks 0–100.

After the running totals, what is count[v]?

The number of elements smaller than or equal to v.

Where does the last 3 of the example go?

count[3]: 5 → 4, so output[4].

10Counting sort code

Big idea: four loops: count, running totals, place backwards, copy back.

count = new int[max + 1]()      // () → all zeros
++count[arr[i]]                 // lines 8–10
count[i] += count[i - 1]        // lines 11–13, i = 1..max
output[--count[arr[i]]] = arr[i] // lines 14–16, i = len − 1..0

int counters

Frequencies have nothing to do with the element type. The lab sheet’s Data* count would overflow for char.

Backwards = stable

The last of equal elements is placed first, at the end of its block.

Trap: walking forwards with the same code reverses equal elements (unstable).
What does the () in new int[max + 1]() do?

Sets every counter to zero.

Slide trace [3, 1, 4, 1, 5, 2, 4, 3], i = 7?

arr[7] = 3, count[3]: 5 → 4, output[4] = 3.

How is counting sort related to radix sort?

Every pass of radix sort is this counting sort, applied to one digit.

11Counting complexity

Big idea: N for the elements, k for the count array; nothing depends on the order.

Time and space

Θ(N + k) in every case, k = max + 1.

Properties

Stable, non-adaptive. Beats merge/quick sort when k is of the order of N.

  • k ≫ N wastes memory: 5 numbers, max 1,000,000 → 1,000,001 counters ≈ 4 MB.
  • Negatives cannot be indexes. Slide fix: subtract the minimum first, add it back at the end.
Trap: k is not a constant; it grows with the largest value, not with N.
Is counting sort a good general-purpose sort?

No: a good specialized one (integers in a limited range).

Time for N = 10, max = 4?

Θ(N + k) with k = 5.

✍Tracing by hand

Radix sort: “what does the array look like after pass p?”

  1. Write the digit of every element for this pass (missing digit = 0).
  2. Read the array left to right and append each element to its bucket.
  3. Read the buckets 0 → 9, top to bottom. That is the new array; the next pass starts from it.

Counting sort: “where does element x go?”

  1. count[0..max], then running totals: count[v] = how many ≤ v.
  2. Walk backwards: for each element, count[x] − 1 is its slot; decrement.
  3. Equal values: the one further right takes the higher slot.

Quick check

The running totals always end with N. In radix sort, after the last pass the array is sorted; after pass p it is sorted by its last p digits.

[23, 5, 81, 13] after the units pass?

Buckets 1: 81; 3: 23, 13; 5: 5 → [81, 23, 13, 5].

Counting sort [2, 0, 2, 1]: running totals?

Counts [1, 1, 2] → totals [1, 2, 4].

…and where does the last 2 (index 2) go?

Walking backwards: index 3 is 1 → output[1]; index 2 is 2 → count[2]: 4 → 3, output[3].

!Top exam traps

  1. Start from the least significant digit (units), not the most significant.
  2. Passes = digits of the largest element.
  3. Inside a bucket, keep the array order; join buckets 0 → 9.
  4. A missing digit is a 0: 7 goes to bucket 0 in the tens pass.
  5. --frequency[d] / --count[v] decrement before use.
  6. Running totals: count[v] = how many ≤ v; the last one is N.
  7. count has max + 1 slots; k is not a constant.
  8. Backwards walk = stable; forwards would reverse equal elements.
  9. Both: Θ in all cases, stable, non-adaptive, non-negative integers only.
  10. Radix Θ(d (N + b)) time, Θ(N + b) space; counting Θ(N + k) time and space.
  11. They do not break the Ω(N log N) bound: it applies only to comparison sorts.
