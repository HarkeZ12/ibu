Part 1 · Analysis of algorithms
01

Why not just use a stopwatch?

An algorithm is a set of clear, unambiguous instructions that solves a problem. It takes zero or more inputs, must produce at least one output, every step must be simple enough for a computer to carry out, and it must finish in finite time. A good algorithm is also correct for every input, deterministic (same input, same result) and efficient.

Most problems can be solved in many ways, so we need to compare solutions. Timing a program sounds natural, but a stopwatch answers a very narrow question: how long this program took, on this machine, for this input. Change any of the three and the number changes. Worse, you can only time a program after you have written it and waited for it to finish.

Case study · N-body simulation

Simulating stars that all pull on each other means computing the force for every pair of bodies: a loop inside a loop, about N² work. For 10⁸ bodies that is roughly 5·10¹⁵ pair calculations, which at a billion per second is about 58 days for one step (the notes count N² instead of N(N−1)/2 and get 116 days).

The Barnes–Hut algorithm treats a distant cluster of stars as one body at its centre of mass. That turns the work into about N log N ≈ 2.7·10⁹ steps: under 3 seconds on the same machine. Same hardware, same simulation, different algorithm.

Key idea

We want to predict cost from the shape of the code, before it runs, in a way that still holds on a different machine.

02

Counting operations

Instead of seconds, we pick one operation and count how many times it runs as a function of the input size N. We usually pick the operation in the innermost loop (a comparison, an array access, following a pointer), because it runs most often. Any two sensible choices differ only by a constant factor, which we will throw away anyway.

A loop inside a loop

// How many pairs of positions hold values that sum to zero?
for (int i = 0; i < len; ++i)
    for (int j = i + 1; j < len; ++j)   // starts at i + 1
        if (arr[i] + arr[j] == 0) ++found;

For a given i, the inner loop runs N − 1 − i times. Adding the rows up:

(N−1) + (N−2) + … + 1 + 0 = N(N−1) / 2

The trick for the sum: write it forwards and backwards and add column by column. Every column adds up to N, there are N − 1 columns, so two copies give N(N−1) and one copy is half of that.

Exam trap

If j started at 0, the code would visit all N² cells, check every pair twice and pair each element with itself. Starting at i + 1 saves just over half the work, but the count still grows about 4× when N doubles. A saving in the constant is not a change in the order of growth.

One more loop, one more factor of N

Three nested loops with i < j < k make N(N−1)(N−2)/6 comparisons. The 6 is there because three positions can be written in 3! = 6 orders and the loops only produce the increasing one. For N = 1000 that is about 166 million comparisons, 333 times more than the double loop.

Loops that halve

while (n > 1) { n /= 2; ++steps; }

Starting at N and halving: N, N/2, N/4, … After k steps we are at N/2ᵏ, and we stop when that reaches 1. So the loop runs ⌊lg N⌋ times, where lg means log base 2.

Multiply the input by a thousand and the loop needs only about ten more steps.

Does the log base matter?

log_b N = lg N / lg b, so changing the base multiplies by a constant (lg N ≈ 3.32 · log₁₀ N). Constants are dropped, so inside O and Θ the base does not matter. The book writes lg N for an exact count of halvings and log N inside O and Θ.

03

Order of growth

Exact counts like ½N² − ½N are more precise than we need. We simplify in two steps:

  1. Drop the lower-order terms. At N = 1000, ½N² is 500,000 and ½N is only 500. The biggest term takes over as N grows.
  2. Drop the leading coefficient. The ½ depends on how the loop was written and on the machine. What matters is N² versus N.

What is left is the order of growth: the highest-order term without its coefficient.

Tilde vs order of growth. f(N) ∼ g(N) means f(N)/g(N) → 1. The tilde keeps the coefficient (½N² − ½N ∼ ½N²), which helps predict running time. The order of growth throws the coefficient away too, which helps sort algorithms into classes.

04

Upper, lower and tight bounds: O, Ω, Θ

Start with something that is not code. A restaurant charges 200 € for the room plus 25 € per guest: f(N) = 200 + 25N. A friend asks how expensive the dinner will be. You could answer in three ways:

AnswerKind of promiseNotation
"At most 40 € per guest"upper bound: never above 40NO(N)
"At least 20 € per guest"lower bound: never below 20NΩ(N)
"Between 20 and 40 € per guest"tight bound: both at onceΘ(N)

The lower promise always holds. The upper one fails for small groups: 5 guests pay 325 €, which is 65 € each, because the room is shared by so few people. 200 + 25N ≤ 40N only becomes true at N = 14. So the upper promise needs small print: "for groups of 14 or more". That small print is n₀. The 40 € could just as well be 50 €; what carries the information is "per guest", the growth class.

The definitions

  • f is O(g) if there are constants c > 0 and n₀ with f(N) ≤ c·g(N) for all N ≥ n₀. Grows no faster than g (like ≤).
  • f is Ω(g) if there are c > 0 and n₀ with f(N) ≥ c·g(N) for all N ≥ n₀. Grows no slower than g (like ≥).
  • f is Θ(g) if it is both: c₁·g(N) ≤ f(N) ≤ c₂·g(N) for all N ≥ n₀. Grows at the same rate (like =).
  • Why the constant c? So the bound survives a faster or slower machine or a rewritten loop. If c had to be 1, a program would stop being O(N²) when moved to a machine 3× slower.
  • Why n₀? So small inputs are exempt, like the small dinner groups.
  • Comparing growth, not values: 100N is O(N) because we may choose c = 100.
Worked example

Show f(N) = 2N² + 20N is Θ(N²). Lower: 2N² ≤ f(N) always, so c₁ = 2. Upper: 2N² + 20N ≤ 3N² ⇔ 20N ≤ N² ⇔ N ≥ 20. So c₁ = 2, c₂ = 3, n₀ = 20 works. f is also O(N³) and Ω(N), both true but not tight, and it is not O(N).

Exam trap

"Merge sort is O(N²)" is true but weak, like saying a marathon takes less than a week. The informative statement is Θ(N log N). The book prefers Θ whenever it is known.

Bounds on a problem, and "optimal"

A lower bound can also describe a problem: a claim about every algorithm that could ever solve it, including ones not invented yet. Any sort that works by comparing pairs needs about N lg N comparisons on some input: Ω(N log N).

An algorithm is optimal when its cost matches a proved lower bound on the problem, within a constant factor. Merge sort is Θ(N log N), so it is optimal, although another comparison sort may still have a smaller constant or use less memory.

Open problem example: matrix multiplication. The obvious algorithm is Θ(N³), the best known is about N^2.37, and the best proved lower bound is only Ω(N²) (you have to read the input). Nobody knows where between them the truth is.

History

Paul Bachmann used O in number theory in 1894 and Edmund Landau popularised it. Donald Knuth brought O, Ω and Θ into computer science in 1976. Writing f = O(g) is a convention: O(g) is a set of functions and the line means "f belongs to O(g)".

05

Which input? Best, worst and average case

Two inputs of the same size can cost very different amounts. So every cost claim also has to say which input it is about:

  • Worst case: the most expensive input of size N. A guarantee: it never does worse.
  • Best case: the cheapest input. Rarely useful, because you do not choose the input.
  • Average case: the cost averaged over inputs. Only meaningful once you say how inputs are distributed (usually: all equally likely).
The most common misconception

"O is the worst case, Ω the best case, Θ the average case" is wrong. Choosing a case and choosing a symbol are two separate decisions. Each case is its own function of N and can get an O, Ω or Θ bound, for example "linear search is Θ(N) in the worst case and Θ(1) in the best case". O and worst case appear together so often only because an upper bound on the worst case is a promise for every input.

Example: a stack on a resizing array. Most pushes write one element, Θ(1), the best case. Occasionally the array is full, and the push allocates a twice-as-big array and copies everything, Θ(N), the worst case. Calling push "O(N)" is true but misleading, which leads us to amortised cost.

06

Amortised cost

The amortised cost of an operation is the total cost of a sequence of operations divided by the number of operations. It spreads rare expensive operations over the cheap ones.

Proposition

Starting at capacity 1 and doubling when full, N pushes cost fewer than 3N units (one per write, one per copied element). So a push is Θ(1) amortised, even though a single push can be Θ(N).

Why: N writes cost N. The copies are 1 + 2 + 4 + … + 2ᵏ = 2ᵏ⁺¹ − 1, a geometric sum where each term is bigger than all the previous ones together. Since 2ᵏ < N, the copies total less than 2N. Writes plus copies: under 3N. The spikes get bigger, but they also get rarer at exactly the same rate.

Accounting method (same result, different argument): charge every push 3 units. 1 pays for the write, 2 go into a savings account. When a capacity-c array fills, the c/2 pushes since the last doubling have saved c units, exactly what copying c elements costs.

AmortisedAverage case
Averaged overa sequence of operationsa distribution of inputs
Guaranteeholds for every sequencea particular input can be unlucky

Exam traps
  • Growing by a fixed amount (e.g. +100 slots) is not enough: the copies form an arithmetic sum ≈ N²/200, so the amortised cost is Θ(N). Doubling is what makes the sum geometric.
  • If every operation has a deadline (audio, control systems), an occasional Θ(N) push can still be a problem. A linked stack is the safer choice there.
07

Space

Memory is analysed the same way, with the same notation. Space complexity normally means the extra (auxiliary) memory beyond the input, because you had to have the input anyway.

  • Θ(1), in-place: a few variables, nothing that grows with N. The pair and triple loops, linear search, iterative binary search and bubble sort.
  • Θ(N): e.g. merge sort's auxiliary array. Writing back into the input does not make it in-place.
  • The recursion stack: every pending call is a stack frame, so recursion d levels deep costs Θ(d) even if the code never allocates. A recursive walk down a linked list is N deep. Recursive binary search is lg N deep.

Time and space often trade against each other, for example keeping a size counter in a list so count() is Θ(1) instead of Θ(N).

08

The doubling test

Analysis on paper can be wrong, so we check it by measuring. Run the program on size N, then on 2N, and divide. If T(N) = aN^b:

T(2N) / T(N) = a(2N)^b / aN^b = 2^b   ⇒   b = lg( T(2N) / T(N) )

The unknown constant a (machine, compiler) cancels out. Ratio ≈ 2 means linear, ≈ 4 quadratic, ≈ 8 cubic. A ratio a little above 2 that slowly creeps down to 2 is the signature of N log N, since its ratio is 2(1 + 1/lg N).

Small inputs lie
  • The triple loop's first ratio was 5.04, not 8. The cause is the fixed start-up cost of the inner loop, paid about N²/2 times, which dominates while N is small. That is n₀ showing up in a measurement.
  • The single pass was noisy at first because the processor was still warming up to full clock speed.
Part 2 · Searching
09

Linear search

The search problem: given an array and a key, return an index where the key is, or −1 if it is absent. Linear (sequential) search compares the key with each element from left to right.

int linear_search(const Data* arr, int len, const Data& key) {
    for (int i = 0; i < len; ++i)
        if (arr[i] == key) return i;   // found it
    return -1;                          // fell off the end
}
  • Why −1? No array has index −1. A missing key is an ordinary answer, so it gets an ordinary return value, unlike pop on an empty stack, which is a bug and throws.
  • Why pass len? An array passed to a function decays to a pointer, and a pointer carries only an address. sizeof(arr) inside the function gives the size of the pointer.
CaseComparisonsBound
Best: key at index 01Θ(1)
Worst: key last, or absentNΘ(N)

Example: in [10, 50, 30, 70, 80, 60, 20, 90, 40], searching for 20 returns 6 after 7 comparisons (indices start at 0). Searching for 25 checks all 9 and returns −1. Finding out something is absent costs as much as the worst place it could be.

When it is the right choice

No sorting, no preparation, works on unsorted data, linked lists and streams, and reads memory in order (a small constant). Great for one-off questions. For many searches on a large collection, sorting first can pay off.

10

Binary search

If the array is sorted, one comparison tells you much more. If the key is smaller than the middle element, it cannot be anywhere to the right of it. So compare with the middle and throw away half of what is left, every time.

int binary_search(const Data* arr, int len, const Data& key) {
    int low = 0, high = len - 1;
    while (low <= high) {                  // interval not empty
        int mid = low + (high - low) / 2;   // never (low + high) / 2
        if (key == arr[mid])     return mid;
        else if (key < arr[mid]) high = mid - 1;  // only lower
        else                     low  = mid + 1;  // only higher
    }
    return -1;
}

Try it

Searching for 37 probes 23, then 42, then finds 37 at index 4: three probes. Searching for 120 probes 23, 42, 202 and ends with low = 6, high = 5: the interval has crossed, so the answer is −1. Linear search would have spent all 8 comparisons on that miss.

Every detail matters

  • low <= high, not <: when low == high one element is still left and must be checked. With < it would be skipped.
  • mid - 1 and mid + 1: both branches move strictly past mid, so the interval shrinks every pass. With high = mid, a one-element interval and a smaller key would loop forever.
  • Unsorted input: it still terminates, but it can confidently return −1 for a key that is right there.
The midpoint bug that hid for 20 years

(low + high) / 2 overflows when the array has over about a billion elements: the sum passes 2,147,483,647, signed overflow is undefined behaviour, and in practice you read at a negative index. Jon Bentley's 1986 Programming Pearls version had it, despite a correctness proof, and so did Java's library, until it broke a program in 2006. The proof reasoned about mathematical integers, which never overflow, and nobody in 1986 had 4 GB to test with. low + (high − low) / 2 gives the same midpoint and cannot overflow.

Why it is correct

Invariant

At the top of every pass: if the key is anywhere in the array, it is at some index between low and high. It holds at the start (the whole array). Each branch only discards indices that cannot hold the key, because the array is sorted. When low > high the interval is empty, so the key is not there and −1 is correct.

How many comparisons?

At most ⌊lg N⌋ + 1: the number of halvings plus the final check of the last remaining element.

11

Sort first? Linked lists, ranges and the STL

Is it worth sorting first?

Answering k searches on an unsorted array:

  • Linear search every time: about kN/2 comparisons.
  • Sort once, then binary search: about N lg N + k lg N.

Sorting wins once k ≈ 2 lg N. That is small: about 40 searches for a million elements (measured: 45, because std::sort makes about 1.13 N lg N comparisons). But keeping an array sorted costs Θ(N) per insertion, because everything after the insertion point must shift. Collections that change often use trees or hash tables instead.

Binary search wants random access

An array reaches arr[mid] in one step. A linked list must walk from the head. Using get(mid) from the head on every probe makes binary search Θ(N log N) pointer steps: worse than a plain linear scan. An algorithm's cost depends on the data structure under it.

Searching for a range

An IP geolocation database stores non-overlapping ranges sorted by start address, not one row per address. To find which range holds an address, we want the last range that starts at or before the key:

int floor_index(const Data* arr, int len, const Data& key) {
    int low = 0, high = len - 1, best = -1;
    while (low <= high) {
        int mid = low + (high - low) / 2;
        if (arr[mid] <= key) { best = mid; low = mid + 1; } // candidate, look right
        else                   high = mid - 1;
    }
    return best;   // last element ≤ key, or -1
}

Then check i >= 0 && key <= ends[i]. The i >= 0 guard must come first: if the key is before every range, floor_index returns −1, and there is no valid ends[i] to read. Otherwise, the end check tells you whether the address is inside the candidate range or in a gap. This works only because the ranges do not overlap. Addresses are stored as numbers (w·256³ + x·256² + y·256 + z), because as strings "10.0.0.1" would sort before "9.0.0.1". With 4.6 million ranges, a lookup reads at most 23 rows.

  • std::lower_bound on a std::list makes Θ(log N) comparisons but Θ(N) iterator steps. The guarantee is about comparisons.

Bubble sort

Sorting rearranges N items into order. Bubble sort walks from left to right comparing neighbours, and swaps them if the first is greater. After one pass the largest element has "bubbled" to the end, so each next pass can stop one place earlier. If a whole pass makes no swaps, the array is sorted and we can stop early.

for (int end = n - 1; end > 0; --end) {
    bool swapped = false;
    for (int j = 0; j < end; ++j)
        if (a[j] > a[j + 1]) { swap(a[j], a[j + 1]); swapped = true; }
    if (!swapped) break;   // early stop
}
CaseWhat happensCost
Worst: reverse-sortedevery element crosses the array; N(N−1)/2 comparisons and as many swapsΘ(N²)

Using a strict > means equal neighbours are never swapped, so their relative order is kept (the sort is stable). With >= it would not be.

How slow is quadratic?

Measured: 14 μs for 100 elements, 1 ms for 1,000, 113 ms for 10,000 and 14 s for 100,000. For a million? N² growth means 10× the elements takes 10² = 100× longer: about 1,400 seconds, or 23 minutes. That is why optimal algorithms matter.
