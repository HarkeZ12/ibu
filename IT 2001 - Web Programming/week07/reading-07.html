02Authentication and authorization

Authentication is the process of verifying the identity of a user: is the person who they claim to be? It is typically done with a username and password, two-factor authentication (2FA) or a JWT token.

Authorization determines what the authenticated user is allowed to access. A user can be authenticated and still not have permission for certain data or actions, depending on their roles or permissions.

In web apps it is common to use tokens to store user identity and permission data. A token confirms who you are, and it often also carries your role, which the server uses to decide what you may do.

03Storing passwords: never in plain text

Before tokens, one rule: the database must never contain the real passwords of your users. Databases get copied, leaked and stolen, and many people use the same password on several sites. Instead you store a hash: a value calculated from the password that cannot be turned back into it.

// at registration: store only the hash
$hash = password_hash($password, PASSWORD_DEFAULT);
// $2y$12$Qe0mZ0p8cXo4m7sQyXW0nOQ0jvN0q5p7w1mVZq3yqVhT2oB8u7x2S

// at login: compare the typed password with the stored hash
if (password_verify($typedPassword, $user['password'])) {
    // correct password
}
  • password_hash() adds a random salt, so two users with the same password get different hashes.
  • It is slow on purpose. One check takes a fraction of a second for you, but trying billions of passwords becomes very expensive for an attacker.
  • Never use md5() or sha1() for passwords. They are fast, which is exactly what you do not want here.
  • The password column needs room for the hash: use VARCHAR(255).
  • Never return the password hash in a JSON response and never write passwords into a log.
From the lectureOne-way: password_hash() turns Student123! into "$2y$10$TxLK…", 60 characters; nobody can turn it back, “not even us”. Salted: the same password hashed twice gives two different hashes; the salt is stored inside the hash. Slow on purpose: bcrypt has a cost factor and runs 2cost rounds, so each +1 doubles the time. PHP’s default was 10 and rose to 12 in PHP 8.4. password_verify() hashes the login attempt with the salt and cost from the stored hash and compares. Two rules in AuthService: one message for both mistakes (“Invalid email or password.”) and ignore "role" on register (everybody who registers is a student in CampusEvents).

04What a JSON Web Token is

JSON Web Tokens (JWTs) are a standardized, compact and secure way to transmit information between parties as a JSON object. They are widely used for authentication and authorization because they let servers verify the identity of clients without storing session data.

JWTs are digitally signed using either a secret key (with the HMAC algorithm) or a public/private key pair (with algorithms like RSA or ECDSA). The signing ensures the information cannot be tampered with: if someone modifies the payload, the signature validation fails. Because they are self-contained, JWTs are often used in stateless authentication, for example in APIs, where the server only verifies the token instead of keeping a session store.

JWTs are URL-safe and compact, so they are easy to pass in HTTP headers, query strings or even cookies. They support expiration times and other claims that enforce security policies. Because they often carry sensitive information, they should always be sent over HTTPS. The official site jwt.io has a debugger to decode, verify and generate tokens.

Key pointA JWT is signed, not encrypted. Anyone who holds the token can read its payload: paste a token into jwt.io and you see the content at once. The signature only guarantees that nobody changed it. So never put a password or other secret into a token.

JWTs are especially useful for:

  • Authentication: after login the server generates a JWT and returns it; the client sends it with later requests to protected resources.
  • Single Sign-On (SSO): JWTs are lightweight and easy to use across domains.
  • Information exchange: JWTs carry information between systems, and the signature guarantees its integrity.

From the lectureClassic PHP keeps $_SESSION on the server and gives the browser a cookie with the session id, PHPSESSID; every request the server looks the session up, and sessions are harder with several servers, other domains and mobile apps. 06JWT structure and claims

A JWT consists of three parts separated by dots: header.payload.signature. All parts are Base64Url encoded to form the final token.

  • Header: the token type (JWT) and the signing algorithm (e.g. HS256).
  • Payload: the claims, statements about an entity (typically the user). Registered claims are predefined optional fields such as iss (issuer), exp (expiration time), sub (subject) and aud (audience). Public claims are custom claims with globally unique names. Private claims are custom claims agreed upon between the communicating parties.
  • Signature: created from the encoded header and payload, signed with a secret key and the algorithm. It ensures the token was not tampered with.

07How JWT works: login once, then the Bearer header

  • Authentication: the user logs in with credentials. Once the identity is verified, a JWT is created and sent back. It contains claims (user id, roles, permissions) and is signed with a secret key. The client stores it, usually in localStorage or cookies.
  • Authorization: for later requests the client sends the JWT, often in the Authorization header as a Bearer token. The server verifies the signature and checks the claims (roles, permissions) to decide whether the user may access the resource.

Tokens serve as credentials, so they must be handled securely: give them an expiration (exp) and use them only over HTTPS.

Which header?The standard on the web is Authorization: Bearer <token>. Our API uses it too. The word Bearer names the kind of token: whoever holds (bears) the token gets access. The backend removes the word Bearer and verifies the rest. Almost every API you will meet expects the token in exactly this form.

08JWT in the project: register and login

We use the library firebase/php-jwt to create and verify tokens. Ask for version 7: Composer blocks the older 6.x versions because of a known security advisory.

composer require firebase/php-jwt:^7.0

The secret key that signs the tokens belongs with the other settings in backend/config/config.php (copy the new methods from config.example.php). Anyone who knows the key can create valid tokens for any user, so it must be long, random and never committed to a public repository. JWT_EXPIRATION says how many seconds a token stays valid:

// backend/config/config.php (inside class Config)
public static function JWT_SECRET()
{
    return self::get_env('JWT_SECRET', 'change-me-to-a-long-random-string-of-at-least-32-characters');
}
public static function JWT_EXPIRATION()
{
    return self::get_env('JWT_EXPIRATION', 60 * 60 * 24);   // 24 hours, in seconds
}

Registration and login are business logic, so they live in a service. It uses the UserService and UserDao from earlier weeks and throws the same exceptions as the other services, so the error handler turns them into the right status code:

// rest/services/AuthService.php
use Firebase\JWT\JWT;

class AuthService
{
    public function register($data)
    {
        Validator::required($data, ['email', 'password']);     // 400 if missing
        $data['role'] = 'customer';            // never trust a role sent by the client
        $user = $this->user_service->add($data);   // validates, password_hash(), INSERT
        return ['user' => $user, 'token' => $this->create_token($user)];
    }

    public function login($data)
    {
        Validator::required($data, ['email', 'password']);
        $user = $this->user_dao->get_by_email(strtolower(trim($data['email'])));
        // the same answer for "unknown email" and "wrong password"
        if (!$user || !password_verify($data['password'], $user['password'])) {
            throw new UnauthorizedException('Invalid email or password.');   // 401
        }
        unset($user['password']);              // never send the hash back
        return ['user' => $user, 'token' => $this->create_token($user)];
    }

    private function create_token($user)
    {
        $payload = [
            'user' => ['id' => $user['id'], 'email' => $user['email'], 'role' => $user['role']],
            'iat'  => time(),                                    // issued at
            'exp'  => time() + (int) Config::JWT_EXPIRATION()    // expires
        ];
        return JWT::encode($payload, Config::JWT_SECRET(), 'HS256');
    }
}
  • The role is set by the server ("customer"). A client must not be able to register as an admin by sending "role": "admin".
  • login() gives the same answer for an unknown email and for a wrong password. Telling them apart would let an attacker find out which emails are registered.
  • The token contains the user (id, email, role) without the password hash, the time it was created (iat) and its expiry (exp).
  • Both methods answer in the same shape, {"user": ..., "token": "..."}, so a new user is logged in right after registering. A failed login is not returned as null: the service throws UnauthorizedException and the error handler answers 401.
  • HS256 means the token is signed and verified with the same secret key.
// rest/routes/AuthRoutes.php
Flight::route('POST /auth/register', function () {
    $data = Flight::request()->data->getData();
    Flight::json(Flight::auth_service()->register($data), 201);
});
Flight::route('POST /auth/login', function () {
    $data = Flight::request()->data->getData();
    Flight::json(Flight::auth_service()->login($data));   // a wrong password -> exception -> 401
});

Register the service in index.php next to the other services: Flight::register('auth_service', 'AuthService');

From the lectureThe slide version of create_token() notes: “without exp a token is valid forever”. No secrets in the payload: id, email, role yes; password hash or 2FA secret never. Always exp: JWT_EXPIRATION is 24 h; an expired token gets 401 “Your session has expired”. JWT_SECRET is the master key: at least 32 random characters, in config.php, never in Git; php-jwt 7 rejects shorter HS256 keys. firebase/php-jwt: “one call to sign, one call to verify”.

09What middleware is

Middleware is code that intercepts HTTP requests and responses, a filter or pipeline through which all requests pass. It runs before or after the main logic: logging requests, authentication and authorization, modifying headers, parsing JSON bodies, or catching and formatting errors. It adds functionality without cluttering the business logic.

Middleware handles cross-cutting concerns in one central place. Instead of writing authentication checks, logging or preprocessing inside every route, you put them in middleware and reuse them. The code stays cleaner, more modular and easier to maintain.

In many frameworks middleware forms a chain or stack: each piece can process the request and either pass it on or return a response early. One middleware validates the token, another logs the request, a final one handles errors. Middleware is common in Express.js, Laravel and FlightPHP; frameworks ship built-in middleware (static files, body parsing) and you can write your own.

From the lecture · v1 → v2Middleware is “code that runs around every route”: Request → before() (auth, logging) → Route (service → DAO) → after() (optional) → Response. Examples: AuthMiddleware (no valid token, no route), Request log (one line per request in info.log), ErrorMiddleware (every exception becomes JSON), and elsewhere CORS, rate limits, compression. Laravel, Slim, Express and ASP.NET Core use the same idea and the same word.

10AuthMiddleware in FlightPHP, and handling errors

FlightPHP supports middleware at the route level and the group level. You can protect routes with authentication logic, validate inputs, and add headers or response transformations. Middleware functions are executed in the order they are defined. Middleware runs before the route and can stop the request.

The token check that many routes share goes into one class. It reads the token from the Authorization header, verifies it and remembers who the user is. FlightPHP calls its before() method before the route runs:

// middleware/AuthMiddleware.php
use Firebase\JWT\JWT;
use Firebase\JWT\Key;
use Firebase\JWT\ExpiredException;

class AuthMiddleware
{
    public function before($params)
    {
        $token = $this->read_token();
        if (!$token) {
            throw new UnauthorizedException('Missing authentication token.');
        }
        try {
            $decoded = JWT::decode($token, new Key(Config::JWT_SECRET(), 'HS256'));
        } catch (ExpiredException $e) {
            throw new UnauthorizedException('Your session has expired. Please log in again.');
        } catch (Exception $e) {
            throw new UnauthorizedException('Invalid authentication token.');
        }
        // every route can now ask: Flight::get('user')['id'], Flight::get('user')['role']
        Flight::set('user', (array) $decoded->user);
    }

    /** Header format:  Authorization: Bearer <token> */
    private function read_token()
    {
        $header = Flight::request()->getHeader('Authorization');
        if (!$header) {
            // some Apache setups move the header here (see .htaccess)
            $header = $_SERVER['REDIRECT_HTTP_AUTHORIZATION'] ?? '';
        }
        if (preg_match('/^Bearer\s+(\S+)$/i', $header, $matches)) {
            return $matches[1];
        }
        return null;
    }
}

If before() throws an exception, the route never runs: the exception goes to the error handler, which answers 401 with a JSON message. If before() finishes normally, the route runs and can read the logged-in user with Flight::get('user'). The middleware is not registered with Flight::register(); it is attached to routes.

Handling middleware errors

Middleware can stop a request in several ways:

  1. Throw an exception: throw new UnauthorizedException('...'). The error handler turns it into a JSON answer with the right status. This is what our project does.
  2. Return false from before(): FlightPHP stops the request with 403 Forbidden, but the client gets no useful message.
  3. Answer directly with Flight::halt() or Flight::jsonHalt(): it works, but then every middleware builds its own error format.

With exceptions, every error (also the ones thrown in a middleware, a service or a DAO) ends in one place. ErrorMiddleware is registered once in index.php:

// index.php
$error_handler = new ErrorMiddleware();
Flight::map('error', [$error_handler, 'handle']);          // every exception -> JSON
Flight::map('notFound', [$error_handler, 'not_found']);    // unknown URL -> 404

An HttpException keeps its own status and message. Every error answer has the same shape, for example {"error": "Missing authentication token."}.

From the lecturedecode() checks the signature, exp, and that the token uses the algorithm of our Key (HS256); anything else throws. Authorization: Bearer is the standard header and scheme (RFC 6750); Postman and Swagger send this one. Flight::set('user'): routes and services take the user id from the token, never from the request body.

11Applying middleware: single routes, groups, globally

  • Single routes: ->addMiddleware(new AuthMiddleware()) after the route.
  • Route groups: Flight::group('', function () { ... }, [new AuthMiddleware()]) protects every route inside the group.
  • Globally: Flight::before('start', ...) runs for every request. We use it for request logging, not for the token check, because login and register must stay public.

In index.php the public routes stay outside the group, and all other routes go inside it:

// index.php
// public routes – no token needed: POST /auth/register, POST /auth/login
require_once __DIR__ . '/rest/routes/AuthRoutes.php';

// protected routes – AuthMiddleware runs before EVERY route in this group
Flight::group('', function () {
    require_once __DIR__ . '/rest/routes/RestaurantRoutes.php';
    require_once __DIR__ . '/rest/routes/OrderRoutes.php';
}, [new AuthMiddleware()]);

Flight::start();

// rest/routes/AuthRoutes.php – one protected route outside the group
Flight::route('GET /auth/me', function () {
    Flight::json(Flight::get('user'));
})->addMiddleware(new AuthMiddleware());

Read it from the top. Login and register are outside the group, because a user who is not logged in has no token yet. Every route inside the group is protected without a single extra line in the route itself, and a route added to the group later is protected automatically, so nobody can forget it. Checking the token by hand in every route would also work, but the same 15 lines would then be copied into dozens of routes, and one forgotten copy leaves a route open to everybody.

From the lecture · Middleware in FlightPHPA middleware is a class with before() and after(), added to a route or a group. Order: before() runs in the order the middleware was added, after() in reverse order. return false: Flight stops and sends 403 Forbidden without a custom message; “we throw an exception instead”. Flight::before('start') is a filter, not route middleware: it runs once for every request, even a 404, and is used for the request log. In CampusEvents the public routes are /auth/register, /auth/login and /auth/google; the protected group requires EventRoutes.php, ClubRoutes.php and all other route files. “Protected by default” (a new route in these files is protected automatically) and “Public by exception” (register and login cannot need a token; /auth/me adds the middleware on its own route). Swagger: a bearerAuth security scheme; public endpoints say security: []; locks appear in Swagger UI.

12Roles and the logged-in user

After the middleware has run, every route can ask who is calling. Two uses are common.

Checking a role (authorization). Only an admin may delete a restaurant. A wrong role is not a missing login, so the answer is 403 Forbidden, not 401:

Flight::route('DELETE /restaurants/@id', function ($id) {
    $user = Flight::get('user');               // set by AuthMiddleware
    if ($user['role'] !== 'admin') {
        throw new ForbiddenException('Only an admin can delete a restaurant.');   // 403
    }
    Flight::json(Flight::restaurant_service()->delete($id));
});

Using the id from the token. An order belongs to the logged-in user. Take the user id from the token, never from the request body:

Flight::route('POST /orders', function () {
    $data = Flight::request()->data->getData();
    $user_id = Flight::get('user')['id'];      // from the verified token
    Flight::json(Flight::order_service()->place_order($user_id, $data['items']), 201);
});

If the route used a user_id sent by the client, any logged-in user could place orders in the name of somebody else. The token is the only trustworthy source of identity. When many routes need the same role check, it can move into a middleware too, the same way as the token check.

From the lecture · Next week (week 8)RoleMiddleware: one reusable line per route or group; the wrong role gets 403 Forbidden. Ownership rules: a student may cancel only their own registrations, checked in the service. Trust the token: the user id comes from the token, never from the request body. “Today: who are you (401). Next week: are you allowed (403).”

13Logging requests and errors

When something goes wrong on a server, nobody is sitting in front of it to see the error. The server writes what happens into log files, and we read them later. A small Logger class (Logger::info() and Logger::error()) writes two files in backend/logs/:

  • logs/info.log: one line for every request: method, URL, status, user, role and how long it took. RequestLogMiddleware writes it. It is registered globally with Flight::before('start', ...), because every request should be logged, public or not.
  • logs/error.log: the problems: failed logins, every 401 and 403, and every 500 with the real exception class, message, file and line. ErrorMiddleware writes it.
[2026-12-01 14:05:12] INFO GET /restaurants 200 user=2 role=customer 35ms
[2026-12-01 14:05:20] ERROR LOGIN FAILED email=ana@example.com
[2026-12-01 14:05:31] ERROR DELETE /restaurants/3 403 user=2 role=customer Only an admin can delete a restaurant.
[2026-12-01 14:06:02] ERROR POST /orders 500 user=2 role=customer PDOException: ... (OrderDao.php:42)

The client only gets a short message such as “Something went wrong on the server. Please try again later.”, never a stack trace, SQL or a file path, because those help an attacker. The details stay in our log. Never write passwords or tokens into a log: anybody who can read the log could use them.

From the lectureLogs are written by utils/Logger.php into backend/logs/. Example lines: INFO LOGIN user=2 role=student, INFO GET /events 200 user=2 role=student 14ms, INFO EXTERNAL API Open-Meteo 200 412ms, ERROR LOGIN FAILED email=ema@campusevents.ba, ERROR GET /events 401 user=- role=- Missing authentication token.. Log: method, path, status, user, role, time; logins, failed logins, external calls. Never log: passwords, tokens, 2FA secrets; “a log file is read by more people than the database”. Why bother: debug “it does not work”, spot 100 LOGIN FAILED in a minute, find slow endpoints. One request, three outcomes: valid token 200, no token 401, a bug 500; every case leaves a line in a log.

14Postman, Apache, Swagger and where to keep the token

Trying it in Postman

  1. Send POST /auth/register with {"email": "ana@example.com", "password": "secret123"}. Expect 201 and an answer with the user and a token.
  2. Send POST /auth/login with the same data. Expect 200 and {"user": ..., "token": "..."}. Try a wrong password: expect 401 and {"error": "Invalid email or password."}.
  3. Send GET /restaurants without a header. Expect 401.
  4. Add the header Authorization with the value Bearer, a space, and the token, and send again. Expect 200. (Postman can write this header for you: open the Authorization tab, choose Bearer Token and paste the token.)
  5. Change one character of the token and send again. Expect 401: the signature no longer matches.
  6. Paste the token into jwt.io and read the payload. Notice that no secret is needed to read it.
  7. Open backend/logs/info.log: every request you just sent is one line there. The failed login is also in backend/logs/error.log.

Sending the token through Apache and Swagger

Apache (XAMPP, MAMP). Some Apache setups do not pass the Authorization header to PHP, so even a correct token gives 401. Two lines in backend/.htaccess, above the FlightPHP rewrite rules, pass it on (AuthMiddleware also reads REDIRECT_HTTP_AUTHORIZATION for this case):

RewriteCond %{HTTP:Authorization} .
RewriteRule .* - [E=HTTP_AUTHORIZATION:%{HTTP:Authorization}]

Swagger UI. The documentation from Week 6 gets a security scheme in doc_setup.php. Swagger then shows an Authorize button: paste the token once (without the word Bearer) and Swagger sends it with every request. Public endpoints such as login and register say security: [], so they work without it:

// public/v1/docs/doc_setup.php
#[OA\SecurityScheme(securityScheme: 'bearerAuth', type: 'http', scheme: 'bearer', bearerFormat: 'JWT')]
#[OA\OpenApi(security: [['bearerAuth' => []]])]    // every endpoint needs the token ...

// public/v1/docs/paths/AuthPaths.php
#[OA\Post(path: '/auth/login', security: [], ...)]   // ... except the public ones

Document 401 for every protected endpoint as well: an answer without a token is now a normal, expected answer of the API.

For a course project localStorage is fine. In a real product, short-lived tokens, HTTPS everywhere and careful protection against XSS (Week 12) matter more than the storage place itself.

15Single Sign-On and two-factor authentication

With Single Sign-On (SSO) the user logs in with an account they already have, for example Google, instead of creating a new password for our app. Our own JWT stays:

  1. The frontend shows the Google sign-in button. After the login, Google gives the frontend an ID token, a JWT signed by Google.
  2. The frontend sends it to our backend: POST /auth/google with {"id_token": "..."}.
  3. The backend asks Google to verify the token and checks that it was made for our application (the aud claim is our client id) and that the email is verified.
  4. The backend finds the user by email, or creates the account the first time, and answers with our own token, exactly like POST /auth/login.

From here on nothing changes: the client sends our token in the Authorization header and AuthMiddleware verifies it. Google only replaces the password check.

Two-factor authentication (2FA) adds a second step to the login. After a correct password the user also types a 6-digit code from an authenticator app. The code is calculated from a shared secret and the current time (TOTP), so it changes every 30 seconds. Until the right code is sent, login answers {"two_factor_required": true} instead of a token, so a stolen password alone is not enough.

Both are optional extras in the lecture project. The required part for your project is registration, login and the middleware described above.

From the lecture · Authentication factorsSomething you know: a password or PIN; can be guessed, phished, reused on another site or leaked in a breach. Something you have: a phone with an authenticator app, or a security key (today: TOTP codes). Something you are: fingerprint or face; usually unlocks a device or a passkey and is not sent to the server. MFA = factors of two different kinds; two passwords are still one factor.
From the lecture · Single Sign-OnThe user logs in at one identity provider (Google, Microsoft, Apple, a company server); many apps trust its answer instead of keeping their own passwords.
ProtocolYearWhat it is
OAuth 2.0 (RFC 6749)2012Authorization: lets an app call an API on the user’s behalf with an access token. Not a login protocol by itself.
OpenID Connect2014An identity layer on top of OAuth 2.0. Adds the ID token, a JWT that says who the user is. “Sign in with Google”.
SAML 2.02005Older, XML-based. Still common for company and university logins.

Gains: one password fewer, the provider’s MFA for free, one place to block a user who leaves. Risk: if the provider account is taken over, every connected app is open.

16Common mistakes and summary

  • Secrets in the payload. The payload is readable by anyone who has the token.
  • No expiry, or a very long one. A stolen token then works forever. Hours or days, not years.
  • A short or guessable secret key such as “secret” or “123456”. It can be found by trying, and then anyone can sign tokens.
  • The secret key in a public Git repository.
  • Trusting data from the body instead of the token: user_id, role, is_admin.
  • Checking the role only in the frontend by hiding a button. The API must check it too.
  • Answering 200 with an error text when the login fails. Use 401; use 403 when the user is known but not allowed.
  • Different answers for “unknown email” and “wrong password”.
  • No HTTPS in production. A token sent over plain HTTP can be read on the way.
  • A protected route without the token check. Every new route must pass through the middleware.
  • Passwords or tokens in the log. A log line says who did what (user id, URL, status), never the password or the token itself.
  • The missing .htaccess rule on Apache. The Authorization header never reaches PHP, so every request answers 401 even with a valid token.
  • Stack traces or SQL in the error answer. The client gets a general message; the details belong in logs/error.log.
SummaryJWTs allow secure, stateless user authentication through a structured token with a header, payload and signature. Middleware processes requests before or after the main logic, which makes cross-cutting concerns like authentication and logging easy to handle. In FlightPHP, both function-based and class-based middleware can secure routes and manage incoming requests. Combined with role-based authorization, JWTs and middleware form a secure and flexible authentication system.

17Check Yourself and glossary

Try to answer before you open the answer. These are the kinds of questions you will meet in the quiz.

What is the difference between authentication and authorization? Which status code belongs to each when it fails?

Authentication checks who you are (401 when it fails). Authorization checks what you may do (403 when it fails).

Why do we store password_hash($password) and not the password itself?

So that a leaked database does not reveal the passwords. A hash cannot be turned back into the password.

Why is md5() a bad choice for passwords?

It is very fast, so an attacker can try billions of passwords, and it has no salt.

Name the three parts of a JWT.

Header, payload and signature.

Can the client read the payload of its token? Can it change it?

It can read it (it is only encoded). It cannot change it without breaking the signature.

What does the exp claim do?

It sets the moment after which the token is no longer accepted.

What happens when a user changes "role": "customer" to "role": "admin" in the payload and sends the token?

The signature was calculated from the old payload, so verification fails and the server answers 401.

What is middleware, and why do we use it for authentication?

Code that runs before (or after) the route for many routes at once. It keeps the token check in one place instead of repeating it in every route.

Why are POST /auth/login and POST /auth/register outside the group protected by AuthMiddleware?

A user who is not logged in yet has no token, and these two routes are how they get one.

A route creates an order. Where does it take the user id from, and why?

From the verified token: Flight::get('user')['id']. A value in the request body could be changed by the client.

The API answers 500. Where do you find out what really happened?

In logs/error.log. ErrorMiddleware writes the exception class, message, file and line there; the client only gets a general message.

With Google SSO, who checks the password, and which token does our API get with every request afterwards?

Google checks it. Our backend verifies the Google ID token once and then gives out its own JWT, which the client sends with every request.

⏱The 60-second version

  1. Authentication = who are you (fails with 401). Authorization = what may you do (fails with 403).
  2. Store password_hash(), check with password_verify(). Salted, slow, one-way. Never md5/sha1. VARCHAR(255).
  3. A JWT = header.payload.signature, Base64Url. Signed, not encrypted: anyone can read it, nobody can change it without the secret.
  4. Login once → server signs a token (HS256, JWT_SECRET, exp) → client sends Authorization: Bearer <token> every time. Stateless.
  5. AuthMiddleware::before() reads and verifies the token, throws UnauthorizedException (401) or does Flight::set('user', ...). Attach it to a group; login and register stay outside.
  6. info.log = every request, error.log = problems. Client gets a generic 500, never a stack trace. Never log passwords or tokens.
  7. SSO: Google checks the password, we still issue our own JWT. 2FA (TOTP): 6 digits, every 30 s, from a shared secret and time.

02401 vs 403

Big idea: first we ask who are you (authentication), then are you allowed (authorization).

Authentication · 401

Who are you? At login and on every request when the token is checked. Example: email and password are correct.

Authorization · 403

What may you do? After authentication, before the action. Example: only an admin may delete a restaurant.

Trap: “401 Unauthorized” really means not authenticated (historical name). A logged-in user with the wrong role gets 403, not 401.
A request has no token. 401 or 403?

401: we do not know who you are.

A customer with a valid token tries to delete a restaurant. 401 or 403?

403: we know you, the answer is no.

03Passwords

Big idea: the database stores a one-way, salted, slow hash, never the password.

  • password_hash($pw, PASSWORD_DEFAULT) at registration; password_verify($typed, $user['password']) at login.
  • Salt: same password → different hashes; salt is stored inside the hash.
  • Slow on purpose: bcrypt cost, 2cost rounds, +1 doubles the time.
  • Never md5()/sha1(): fast and unsalted. Column VARCHAR(255). Hash never in JSON or logs.
Trap: you cannot compare password_hash($typed) === $stored: a new salt gives a new hash every time. Use password_verify().
Why is md5 bad for passwords?

It is very fast, so attackers can try billions of guesses, and it has no salt.

Two users have the password “Student123!”. Are their hashes equal?

No, each hash has its own random salt.

Read Section 3 →

04What a JWT is

Big idea: a compact, signed JSON object; the server verifies it instead of storing a session.

  • Signed with a secret key (HMAC) or a public/private key pair (RSA, ECDSA).
  • URL-safe and compact: fits in headers, query strings, cookies. Supports expiration. Always over HTTPS.
  • Uses: authentication, SSO, information exchange. Debugger: jwt.io.
Trap: “signed” ≠ “encrypted”. Anyone can read the payload. Never put a password or secret into it.
Can the client read its own token? Can it change it?

Read: yes (Base64Url). Change: not without breaking the signature.

Read Section 4 →

05Sessions vs tokens

Session + cookie

State on the server; client sends a session id cookie (PHPSESSID); server looks it up; easy early logout; good for server-rendered sites.

Token (JWT)

State in the token; client sends it in a header; server checks the signature, no lookup; stateless; good for SPA and mobile APIs; valid until exp.

Trap: early logout is easy with sessions and harder with tokens. That is why exp should be short.

06JWT parts and claims

Header

{"typ":"JWT","alg":"HS256"}: which algorithm signed it.

Payload

Claims: user, iat, exp… readable by anyone.

Signature

HMAC-SHA256(header + "." + payload, JWT_SECRET).

  • Registered: iss (issuer), sub (subject), aud (audience), exp (expiration), iat (issued at). Public: custom, globally unique names. Private: custom, agreed between the parties. Our user claim is our own.
  • Times are Unix timestamps in seconds; time() + 3600 = one hour from now.
Which claim says until when the token is valid?

exp.

Which claim did the server check in Google SSO to be sure the token was made for our app?

aud (audience) = our client id.

09What middleware is

Big idea: code around every route, written once; a checkpoint that can stop the request.

  • Handles cross-cutting concerns: auth, logging, headers, JSON parsing, error formatting (elsewhere also CORS, rate limits, compression).
  • Arranged as a chain/stack: each piece passes the request on or returns early.
  • v1 = check by hand in each route (copied 40 times, forgotten once). v2 = one class, run before every route of a group.

10AuthMiddleware and errors

  • before(): no token → “Missing authentication token.”; ExpiredException → “Your session has expired…”; other error → “Invalid authentication token.” All are 401.
  • Success → Flight::set('user', (array) $decoded->user).
  • read_token(): getHeader('Authorization'), fallback $_SERVER['REDIRECT_HTTP_AUTHORIZATION'], regex /^Bearer\s+(\S+)$/i.
  • Stop a request: throw (ours, JSON + right status) · return false (403, no message) · Flight::halt()/jsonHalt() (own format each time).
  • ErrorMiddleware: Flight::map('error', ...) and Flight::map('notFound', ...). 400 / 401 / 403 / 404 / else 500.
Trap: AuthMiddleware is not registered with Flight::register(); it is attached to routes or groups.

11Groups and index.php

Single route

->addMiddleware(new AuthMiddleware()), e.g. GET /auth/me.

Group

Flight::group('', fn, [new AuthMiddleware()]): every route inside.

Global

Flight::before('start', ...): every request, even 404. Request log only.

  • Public routes (register, login, and on the slides /auth/google) are required before and outside the group.
  • Protected by default, public by exception. A new route inside the group is protected automatically.
  • Order: before() in the order added, after() in reverse.

12Roles and the user from the token

  • Role check: Flight::get('user')['role'] !== 'admin' → ForbiddenException → 403.
  • Ownership: $user_id = Flight::get('user')['id'], never user_id from the body.
  • Many routes with the same role check → move it into middleware (RoleMiddleware, week 8).
Why not take user_id from the request body?

The client could send someone else’s id and act in their name. The token is the only trustworthy source.
