02Frameworks & their benefits

A framework is a pre-built structure that provides developers with tools, reusable code libraries and established best practices for building software. Think of it as the foundation and scaffolding of a building: you do not lay every brick from scratch. Frameworks give predefined ways to handle routing, database interaction, input validation, error handling and more, so developers can focus on the unique logic of their application while the framework abstracts away common, repetitive tasks.

Four benefits

1Faster developmentBuilt-in features such as routing systems, middleware and database abstraction let you achieve more with less code.
2Best practicesMost frameworks follow patterns like MVC: data (Model), user interface (View) and application logic (Controller) are kept apart, so code is easier to understand, test and modify.
3SecurityMany frameworks protect by default against SQL injection, cross-site scripting (XSS) and cross-site request forgery (CSRF).
4Easier maintenanceModular, well-structured code, often with documentation, is easier to update or scale later.

Two categories of PHP frameworks

CategoryExamplesWhat you getBest for
Full-stackLaravel, Symfony, CodeIgniterEverything out of the box: ORM (Object Relational Mapping), authentication, templating engines and moreLarge applications with many features
Micro-frameworkFlightPHP, Slim, LumenLightweight; only the essentials such as routing and middlewareSmall applications or services where simplicity and speed matter

03Overview of FlightPHP

FlightPHP is a micro-framework written in PHP. It is designed to be fast, simple and flexible, which makes it ideal for lightweight web applications and REST APIs. Unlike full-stack frameworks, it focuses only on what is necessary for a functional backend, without extra layers of complexity.

Key features:

  • a simple routing system that maps URLs to functions;
  • built-in support for middleware and request handling;
  • it can be extended with custom plugins;
  • easy JSON response handling, which makes it ideal for APIs.

FlightPHP is particularly good for learning how web applications are structured and how APIs are built: its simplicity helps beginners understand the core concepts without being overwhelmed.

VersionThis course uses FlightPHP version 3. Its documentation is short and worth opening next to this reading: docs.flightphp.com.

04Microservices in web development

Microservices are an architectural style in which an application is composed of many small, independent services. Each service performs a single function and can be developed, deployed and scaled independently.

BenefitsScalability, faster development, resilience, and flexibility in technology use.
ChallengesIncreased complexity, network latency, and keeping data consistent across services.

Even with these challenges, the model offers greater agility and modularity in large applications.

05Composer & the vendor folder

Composer is the dependency manager for PHP. Dependencies are external libraries or packages your project needs to work. You list them in a file named composer.json. To install FlightPHP you run:

composer require flightphp/core

This adds FlightPHP to composer.json. Composer then installs it into a special folder called vendor, where all dependencies are stored.

The vendor folder

vendor/ is created automatically by Composer and holds every library the project needs. Do not edit files in it. Because it is large and generated, add it to .gitignore so it is not uploaded to Git. Someone who clones the project runs composer install to regenerate it.

File or folderWhat it isIn Git?
composer.jsonthe list of libraries your project needsyes
composer.lockthe exact versions that were installed, so everyone on the team gets the same onesyes
vendor/the downloaded libraries and the autoloaderno (add it to .gitignore)

One line at the top of index.php makes every installed library available:

require 'vendor/autoload.php';

06.htaccess & the front controller

The .htaccess file configures Apache web servers: URL rewriting, access permissions and redirections. For PHP applications it is especially useful for clean URLs and routing. Without it, users would reach PHP files through full paths such as index.php?page=home; with it, URLs become clean, such as /home.

A typical .htaccess for FlightPHP

RewriteEngine On
RewriteCond %{REQUEST_FILENAME} !-f
RewriteCond %{REQUEST_FILENAME} !-d
RewriteRule ^(.*)$ index.php [QSA,L]
  1. Turn rewriting on.
  2. If the requested path is not a real file (!-f)…
  3. …and not a real folder (!-d)…
  4. …send the request to index.php and keep the query string (QSA).

So every request goes through index.php, which lets your routing logic handle it. index.php is the single entry point of the backend, also called the front controller:

backend/index.php

<?php
// backend/index.php
require 'vendor/autoload.php';

require_once 'rest/services/RestaurantService.php';
Flight::register('restaurantService', 'RestaurantService');

require_once 'rest/routes/RestaurantRoutes.php';

Flight::start();

07HTTP in five minutes: requests & responses

Routes speak HTTP, so you need to read it. Every exchange between a client and your backend is one request followed by one response. Both are plain text with the same three parts: a first line, headers, and an optional body.

PartIn the requestIn the response
First linethe method and the path: POST /restaurantsthe status code: 201 Created
Headersextra information, e.g. Content-Type: application/jsonthe same idea, e.g. Content-Type: application/json
Bodythe data the client sends (empty for GET and DELETE)the data the server returns; in our API always JSON

Status codes our API uses

The status code tells the client how the request went before it even reads the body. You do not need to learn all of them:

08REST: designing the URLs of an API

REST is a set of conventions for web APIs. The main idea: a URL names a resource (a thing, such as restaurants), and the HTTP method says what to do with it. You do not put verbs into the URL.

Method and URLMeaningSuccess code
GET /restaurantslist all restaurants200
GET /restaurants/2get restaurant 2200, or 404 if it does not exist
POST /restaurantscreate a restaurant (data in the body)201
PUT /restaurants/2replace restaurant 2 (data in the body)200
PATCH /restaurants/2change some fields of restaurant 2200
DELETE /restaurants/2delete restaurant 2200 or 204
GET /restaurants/2/menu-itemslist the menu items of restaurant 2200

Rules

  • Use plural nouns for resources: /restaurants, /orders, /menu-items.
  • Use the path to identify a resource (/restaurants/2) and the query string to filter, sort or search a list (/restaurants?city=Mostar).
  • Do not write /getRestaurants or /deleteRestaurant?id=2. The method already says what happens.
  • GET never changes data. A client must be able to repeat a GET as often as it likes.
  • Always answer in the same format. In our API both data and errors are JSON.
Not RESTGET /deleteRestaurant?id=2POST /restaurants/delete/2
RESTDELETE /restaurants/2GET /restaurants?city=Mostar

09Handling requests in FlightPHP

FlightPHP handles the HTTP methods GET, POST, PUT and DELETE. Routes are defined with Flight::route(). A route is a rule that tells the application which code to run when a certain URL is requested with a specific HTTP method. It connects your application to the outside world: what happens when a user visits a page, submits a form or sends data to the server.

In the first example the route is defined for GET on the path /hello. A GET request usually happens when you open a URL in a browser, so typing http://yourdomain.com/hello matches this route, its function runs, and the server sends back the text “Hello, FlightPHP!”.

Flight::route('GET /hello', function() {
    echo "Hello, FlightPHP!";
});

Flight::route('POST /student', function() {
    echo "Student created!";
});

Reading data from the request

Flight::request()->queryGET parameters (the query string)
Flight::request()->dataPOST data (the body)
Flight::request()->filesuploaded files
Flight::route('POST /register', function() {
    $name = Flight::request()->data->name;
    echo "Welcome, $name!";
});

10Working with parameters in URLs

Parameters make an application dynamic. FlightPHP reads them either from the path of the URL or from the query string.

A parameter in the path

In /student/123, @id is a placeholder; visiting /student/123 passes 123 to the $id parameter of the function.

Flight::route('GET /student/@id', function($id) {
    echo "Fetching data for student with ID: $id";
});

A parameter in the query string

For /students?name=John, read the value with Flight::request()->query:

Flight::route('GET /students', function() {
    $name = Flight::request()->query['name'];  // Example: ?name=John
    echo "Searching for students named: $name";
});

Several parameters in the path

Flight::route('GET /student/@id/course/@courseId', function($id, $courseId) {
    echo "Fetching data for student with ID: $id enrolled in course with ID: $courseId";
});

This captures both id and courseId from the path.

Path and query parameters together

Flight::route('GET /student/@id', function($id) {
    $search = Flight::request()->query['search'] ?? null;
    echo "Fetching data for student with ID: $id. Search term: $search";
});

For /student/123?search=math this prints: Fetching data for student with ID: 123. Search term: math. The ?? operator gives a default (null) when the parameter is missing.

A path parameter with body data (POST)

Flight::route('POST /student/@id', function($id) {
    $name = Flight::request()->data->name;
    echo "Student $name with ID: $id has been registered.";
});

A POST to /student/123 with name=John prints: Student John with ID: 123 has been registered.

Several query parameters

Flight::route('GET /search', function() {
    $name = Flight::request()->query['name'] ?? 'No name provided';
    $age  = Flight::request()->query['age']  ?? 'No age provided';
    echo "Searching for name: $name, age: $age";
});

For /search?name=John&age=25 this prints: Searching for name: John, age: 25.

11Generating JSON responses

APIs usually answer with JSON. Flight::json() sets the correct headers automatically and formats the data as JSON:

Flight::route('GET /student/@id', function($id) {
    $user = ["id" => $id, "name" => "John Doe"];
    Flight::json($user);
});

This makes FlightPHP ideal for RESTful APIs that exchange data as JSON. Flight::json() takes the status code as its second argument. Without it the code is 200:

Flight::json($restaurant);                              // 200 OK
Flight::json($created, 201);                            // 201 Created
Flight::json(['error' => 'Restaurant not found'], 404); // 404 Not Found

12Putting it together: routes for restaurants

The examples so far used echo to keep things short. Real routes in our project do three things and nothing more:

  1. read the input;
  2. call one service method;
  3. answer with JSON and a status code.

This is the complete route file for restaurants, built on the RestaurantService from Week 4:

rest/routes/RestaurantRoutes.php

<?php
// rest/routes/RestaurantRoutes.php

// GET /restaurants              all restaurants
// GET /restaurants?city=Mostar  filtered by city
Flight::route('GET /restaurants', function () {
    $city = Flight::request()->query['city'] ?? null;
    $service = Flight::restaurantService();
    Flight::json($city ? $service->getByCity($city) : $service->getAll());
});

// GET /restaurants/2          one restaurant
Flight::route('GET /restaurants/@id', function ($id) {
    $restaurant = Flight::restaurantService()->getById((int) $id);
    if ($restaurant === null) {
        Flight::json(['error' => 'Restaurant not found'], 404);
        return;
    }
    Flight::json($restaurant);
});

// POST /restaurants           create; JSON in the body
Flight::route('POST /restaurants', function () {
    $data = Flight::request()->data->getData();
    Flight::json(Flight::restaurantService()->create($data), 201);
});

// PUT /restaurants/2          update; JSON in the body
Flight::route('PUT /restaurants/@id', function ($id) {
    $data = Flight::request()->data->getData();
    $updated = Flight::restaurantService()->update((int) $id, $data);
    if ($updated === null) {
        Flight::json(['error' => 'Restaurant not found'], 404);
        return;
    }
    Flight::json($updated);
});

// DELETE /restaurants/2       delete
Flight::route('DELETE /restaurants/@id', function ($id) {
    if (!Flight::restaurantService()->delete((int) $id)) {
        Flight::json(['error' => 'Restaurant not found'], 404);
        return;
    }
    Flight::json(['message' => 'Restaurant deleted']);
});
  • @id in the path arrives as a string, so the route converts it with (int) before it calls the service.
  • Flight::request()->data->getData() returns the JSON body as a PHP array when the client sends the header Content-Type: application/json.
  • There is no validation and no SQL here. The route trusts the service to check the data and to throw an exception when something is wrong.
  • update() in RestaurantService is your task in the lab: validate like create(), call the DAO, and return the updated restaurant or null.

13Handling errors in one place

The POST route above has no try and catch. If create() throws an InvalidArgumentException, who answers the client? Instead of repeating try/catch in every route, tell FlightPHP once what to do with any exception. Put this into index.php, before Flight::start():

// one handler for every exception thrown in a route or a service
Flight::map('error', function (Throwable $e) {
    if ($e instanceof InvalidArgumentException) {
        Flight::json(['error' => $e->getMessage()], 400);
        return;
    }
    error_log($e->getMessage());     // the real message goes to the server log
    Flight::json(['error' => 'Something went wrong on the server'], 500);
});

// a URL that matches no route
Flight::map('notFound', function () {
    Flight::json(['error' => 'Route not found'], 404);
});
  • A validation problem becomes 400 with the message from the service, which is safe to show.
  • Anything else becomes 500 with a general message. The details (for example a database error) are written to the log and never sent to the client.
  • Every answer of the API is now JSON, including the errors. A frontend can rely on that.

14Trying your routes

You do not need a frontend to test an API. Use Postman (Week 2), or curl in a terminal:

# list
curl http://localhost/project/backend/restaurants

# create (note the header and the JSON body)
curl -X POST http://localhost/project/backend/restaurants \
     -H "Content-Type: application/json" \
     -d '{"name": "Kilim", "city": "Ilidža"}'

# show the status code and the headers of the response
curl -i http://localhost/project/backend/restaurants/999
-X POSTchooses the HTTP method
-Hadds a header
-dsends the body
-ialso prints the status line and the response headers
Test three cases for every routeA correct request, a request with invalid data, and a request for something that does not exist. Check the status code each time, not only the body.

15Common mistakes

MistakeWhy it is wrong / what to do
Verbs in the URL: /getRestaurants, /restaurants/delete/2Use the method instead.
Always answering 200, even for errorsThe status code is part of the answer.
echo instead of Flight::json()echo sends text without the JSON header and without a status code.
Business rules or SQL in a routeA route reads input, calls one service method and answers.
Forgetting Content-Type: application/json in Postman or curlThe body then arrives empty.
Forgetting .htaccess or placing it in the wrong folderEvery URL except index.php then answers 404 from Apache.
Committing the vendor folder to GitIt is generated; add it to .gitignore.
Showing database exception messages to the clientLog them and send a general message.

16Check yourself & glossary

Try to answer before you open the answers. These are the kinds of questions you will meet in the quiz.

1. What is the difference between a full-stack framework and a micro-framework? Name one of each.

A full-stack framework (Laravel, Symfony) brings almost everything; a micro-framework (FlightPHP, Slim) brings mainly routing and you add the rest.

2. What is stored in composer.json, composer.lock and vendor/? Which go into Git?

The needed libraries; the exact installed versions; the downloaded code. composer.json and composer.lock go into Git, vendor/ does not.

3. What does the .htaccess file in our backend do?

It sends every request that is not a real file or folder to index.php, so that FlightPHP can route it.

4. Name the three parts of an HTTP request.

The first line with method and path, the headers, and the body.

5. Which method and URL would you use to delete menu item 15?

DELETE /menu-items/15.

6. A client asks for GET /restaurants/999 and there is no such restaurant. Which status code?

404 Not Found.

7. What is wrong with the route GET /deleteRestaurant?id=2?

The URL contains a verb and uses GET to change data. It should be DELETE /restaurants/2.

8. How does a route read (a) @id from the path, (b) ?city=Mostar, (c) a JSON body?

(a) as the function parameter $id, (b) Flight::request()->query['city'], (c) Flight::request()->data->getData().

9. A service throws InvalidArgumentException. Which status code should the client receive, and where is that decided?

400 Bad Request. It is decided in the presentation layer: in the route or in the central error handler.

10. Why should the message of a PDOException not be sent to the client?

It can reveal table names, queries and other details that help an attacker. Log it and send a general message.

Glossary

FrameworkReady-made code and conventions that give an application its basic structure.
Micro-frameworkA small framework that offers mainly routing; FlightPHP is one.
ComposerPHP’s package manager; it installs libraries into vendor/.
Front controllerThe single file (index.php) through which every request enters the application.
RouteA rule that connects an HTTP method and a URL pattern with a function.
EndpointOne method + URL of an API, for example GET /restaurants.
HTTP methodThe action of a request: GET, POST, PUT, PATCH or DELETE.
Status codeA three-digit number in the response that says how the request went.
HeaderA name and value sent with a request or response, for example Content-Type.
Path parameterA variable part of the URL path, such as 2 in /restaurants/2.
Query stringThe part of the URL after ?, used for filters and options.
RESTConventions for web APIs: URLs name resources, methods say what to do.
ResourceA kind of thing the API manages, such as restaurants or orders.
JSONThe text format in which our API sends and receives data.
