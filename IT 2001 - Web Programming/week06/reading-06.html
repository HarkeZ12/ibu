OpenAPI and Swagger

In Week 5, CampusEvents gained RESTful FlightPHP routes. Week 6 describes what those routes accept and return so a frontend developer or a tool can use the API without reading the backend implementation. For the lab you need the Week 5 backend, PHP 8.2 or newer, Composer, and internet access for the Swagger UI CDN.

OpenAPI Specification (OAS)The shared, machine-readable format for a REST API contract. An OpenAPI document can be written in JSON or YAML.
SwaggerThe family of tools around the format, including Swagger UI, Swagger Editor and Swagger Codegen.
swagger-phpThe PHP library that generates the contract from documentation attached to code.
Swagger UIThe browser page that reads the contract, presents it and lets you send requests.

The OpenAPI document is a contract between the API provider and its consumers. It lists every endpoint, the expected input and output, the parameters and the error responses, so frontend developers can build their part from the specification without waiting for the backend. Think of OpenAPI as the blueprint and Swagger as the toolkit that brings the blueprint to life.

The format first appeared as Swagger in 2011. In November 2015 it was donated to the OpenAPI Initiative, an open project of the Linux Foundation, and on 1 January 2016 it was renamed the OpenAPI Specification. The tools kept the Swagger name: Swagger UI, Swagger Editor and Swagger Codegen. People still say "Swagger docs"; they mean an OpenAPI document shown in Swagger UI.

OpenAPI document structure

FieldWhat it describes
openapiThe specification version. The reading's generated document starts with 3.0.0.
infoAPI title, description, contact and API version. CampusEvents has API version 1.0.
serversAPI base URLs. Swagger UI uses a server URL when sending a request.
pathsOne entry per URL pattern. Each HTTP method on that path is a separate operation with its own parameters, body and responses.
componentsReusable definitions such as Event and Error. Security schemes can also be defined here.
tagsGrouping labels. Swagger UI can display the events or weather operations together.

swagger-php also adds the top-level tags list. The OpenAPI versions in use today are 3.0, 3.1 and 3.2 (published in September 2025). swagger-php 6 can produce all three; by default it produces 3.0.0, which is the first line of our document. Do not mix it up with info.version, the version of the CampusEvents API itself (1.0).

Inside the document you meet four key components:

PathsThe available endpoints, their HTTP methods, parameters and request/response models. In CampusEvents: /events, /events/{id}, /weather/forecast and 15 more.
OperationsOne HTTP method on one path: input parameters, expected responses, error codes and authentication requirements. GET /events/{id} returns 200 with an event or 404 with an error.
Models (schemas)The data structures of requests and responses, with data types and properties, such as the Event schema with id, title, starts_at and capacity.
SecurityHow callers get access: API keys, OAuth, bearer tokens or other schemes. CampusEvents gets login and tokens in Week 7.

Operations can also carry tags. A tag is a label, such as events or weather, and Swagger UI shows all operations with the same tag together.

Design-first and code-first

ApproachOrder of workWhen it fits
Design-firstAgree on the OpenAPI document, then implement the API to match it.Frontend and backend can start in parallel. Tools include Swagger Editor, Stoplight and Redocly.
Code-firstBuild the API, describe it alongside the code and generate the contract.The routes already exist or one team builds the whole API. CampusEvents takes this approach.

We use code-first: the routes already exist from Week 5, and we add the documentation next to them. Either way the document is the contract; the difference is only who writes it first. Swagger UI then lets anyone see all endpoints, methods and data structures in one place, try requests in the browser, and understand which inputs and outputs are expected.

Compared with Week 5, three lines in require are new: ext-curl, ext-pdo and zircote/swagger-php. The ext-... lines do not download anything. They tell Composer to check that these PHP extensions are enabled; if one is missing, Composer stops and names it. On XAMPP or WAMP you enable an extension in php.ini, for example by removing the ; in front of extension=curl, and restart Apache.

Version constraints. The caret means "this version or any newer version that is compatible with it". ^6.12 allows 6.12.0 and every later 6.x version, but never 7.0, because a new major version may break your code. ^0.16 is stricter: for versions that start with 0, the caret allows only 0.16.x.

composer require adds the line to composer.json with a caret constraint for the newest version, downloads the library and the libraries it needs into vendor/, and records the exact versions in composer.lock. composer install reads composer.lock and installs exactly those versions: in the lecture project swagger-php 6.12.0 and FlightPHP v3.19.3, so everybody works with the same code. swagger-php also brings nikic/php-parser, symfony/finder and symfony/yaml; you never install those by hand. composer show zircote/swagger-php prints the installed version and its dependencies.

PHP 8 attributes

Annotations are metadata about classes, methods, properties or variables. They are not executed as part of the code; a tool scans the code, extracts them and interprets their meaning. PHP long had no built-in syntax for this, so swagger-php read @OA\Get(...) from doc comments, which needs the extra library doctrine/annotations. Since PHP 8.0 the language has real attributes, written #[...], which PHP itself parses. swagger-php generates exactly the same OpenAPI output from both styles. Docblock annotations are deprecated since swagger-php 6.11 and will be removed in swagger-php 8.

Compare the annotation with the PHP attribute 
/**
 * @OA\Get(
 *     path="/events/{id}",
 *     tags={"events"},
 *     summary="Get one event",
 *     @OA\Parameter(name="id", in="path", required=true, @OA\Schema(type="integer")),
 *     @OA\Response(response=200, description="The event")
 * )
 */
#[OA\Get(
    path: '/events/{id}',
    tags: ['events'],
    summary: 'Get one event',
    parameters: [
        new OA\Parameter(name: 'id', in: 'path', required: true, schema: new OA\Schema(type: 'integer'))
    ],
    responses: [new OA\Response(response: 200, description: 'The event')]
)]

Every file with attributes starts with use OpenApi\Attributes as OA;, so that OA\Get means the class OpenApi\Attributes\Get. php -l only checks syntax: a misspelled argument name such as summry: is still valid PHP and only fails when swagger-php reads it.

AttributeJob
OA\Info, OA\ServerAPI metadata and base URL.
OA\Get, OA\Post, OA\Put, OA\DeleteOne HTTP operation on one path.
OA\Parameter, OA\RequestBodyAn individual path or query input, or the payload sent with POST or PUT.
OA\ResponseOne possible response, identified by its status code.
OA\Schema, OA\Property, OA\ItemsData shape, an object property, or the elements of an array.
OA\JsonContentJSON content of a request body or response. It either points to a schema with ref or describes the data itself.
OA\TagA tag with its own description. Optional: swagger-php creates the tags automatically from the tags of the operations.

Documentation files and metadata

The steps from the lecture: install swagger-php with Composer, add the folder backend/public/v1/docs/, put the general API information and reusable schemas in doc_setup.php, add attributes for each endpoint in paths/*Paths.php (one class per route file), generate the document in swagger.php, and show it with Swagger UI in index.html.

Why separate files, and not attributes directly above the routes? Our routes are closures passed to Flight::route(...), and swagger-php reads attributes only from classes and their methods and properties, not from closures. So EventPaths documents EventRoutes.php, with one empty method per endpoint that only carries the attribute. The route files stay short, and the rule is easy to check: one route, one method.

backend/
├── composer.json                  # + zircote/swagger-php
├── public/v1/docs/
│   ├── index.html                 # Swagger UI
│   ├── swagger.php                # generates the OpenAPI document as JSON
│   ├── doc_setup.php              # API info, server, reusable schemas
│   └── paths/
│       ├── EventPaths.php         # documents rest/routes/EventRoutes.php
│       ├── WeatherPaths.php       # documents rest/routes/WeatherRoutes.php
│       └── ...                    # Category, Club, Dashboard, Registration, Review, User
└── rest/routes/                   # the real routes (unchanged)

In doc_setup.php, OA\Info, OA\Server and the shared schemas sit on an empty class, OpenApiSpec, because an attribute must belong to a code element. The comment at the top is a plain /* comment on purpose: swagger-php would turn a /** doc comment into a description.

  • OA\Info gives the title, description, version and contact shown at the top of Swagger UI.
  • OA\Server uses the constant API_BASE_URL, which swagger.php calculates from the current request. The server URL is always the address you opened the documentation from: XAMPP, the PHP built-in server or, later, the deployed app. You never change it by hand.
  • The Error schema describes the body of every error response. It matches what Flight::map('error') in index.php sends, for example {"error":"Event not found."}.

Schemas, refs and allOf

EventInput describes what a client sends. Its required fields are title, club_id, category_id, location, starts_at and capacity. The input also defines optional city and description. The starts_at example uses YYYY-MM-DD HH:MM; the reading also shows the HTML datetime-local form with a T.

Event describes the response. allOf brings in EventInput by reference and the response adds server-provided fields such as id, available_seats, club_name, category_name, is_upcoming, average_rating and review_count. Put shared shapes in doc_setup.php and reference them with exact, case-sensitive names such as #/components/schemas/Event.

required lists the fields the client must send; these are the same fields the service layer validates. allOf combines schemas: an Event is everything in EventInput plus the fields only the server produces. The client never sends those, so they do not belong in EventInput. example values appear in Swagger UI and are used as the default body when you click "Try it out".

CampusEvents routes and responses

OperationRequestDocumented responses
GET /events/{id}id is a required integer path parameter. The name must match {id}. FlightPHP writes the route as GET /events/@id:[0-9]+.200 with Event or 404 with Error.
POST /eventsA required OA\RequestBody contains OA\JsonContent referencing EventInput.201 with Event or 400 with Error.
  • The attribute path uses curly braces, /events/{id}; the FlightPHP route uses @id:[0-9]+. Both describe the same URL in two notations, and the parameter name must match the name in the braces.
  • Document every response the route can return, not only the successful one. POST /events answers 201 when the event is created, not 200, and 400 when the data is invalid. A frontend developer needs to know about 400 and 404.
  • Error responses point to the shared Error schema, successful responses to Event, and the request body to EventInput.
  • tags group endpoints in Swagger UI. Use one tag per resource.
  • No router uses the method names (getEventsById, postEvents). They only have to be unique inside the class, because PHP refuses two methods with the same name.

Generating the OpenAPI JSON

  1. Load vendor/autoload.php so the generator and attribute classes can be resolved.
  2. Build API_BASE_URL from the request's scheme, host and path prefix. Strip the public/v1/docs/swagger.php suffix before the docs classes use the constant.
  3. Collect doc_setup.php and paths/*.php and load them with require_once. swagger-php reads attributes through PHP reflection, so the classes must be loaded before generate() is called. Without that loop the document contains only "openapi": "3.0.0".
  4. (new \OpenApi\Generator())->generate($files) returns the document as an object, and toJson() turns it into JSON, sent with Content-Type: application/json.

error_reporting and display_errors keep PHP notices out of the output: a single warning printed before the JSON would make the whole document invalid. Open {base}/public/v1/docs/swagger.php in the browser; you should see a long JSON document that starts with "openapi": "3.0.0".

How do these files load, when every request normally goes to FlightPHP? With Apache, backend/.htaccess sends a request to index.php only if it is not an existing file or folder (RewriteCond %{REQUEST_FILENAME} !-f and !-d). swagger.php and the docs/ folder exist, so Apache serves them directly. With the PHP built-in server, server.php in the week folder does the same job: it serves a folder that contains an index.html and runs existing PHP files directly.

Read swagger.php 
<?php
/*
 * Generates the OpenAPI (JSON) document from the PHP 8 attributes in doc_setup.php (API info, schemas)
 * and paths/*.php (one class per route file). Swagger UI (index.html) reads it.
 */
// Deprecation notices from libraries would break the JSON output
error_reporting(E_ALL & ~E_DEPRECATED & ~E_USER_DEPRECATED);
ini_set('display_errors', '0');

require __DIR__ . '/../../../vendor/autoload.php';

// Base URL of the API, e.g. http://localhost:8000/backend/ (works locally and after deployment)
$scheme = (!empty($_SERVER['HTTPS']) && $_SERVER['HTTPS'] !== 'off') ? 'https' : 'http';
$path = preg_replace('#public/v1/docs/swagger\.php$#', '', parse_url($_SERVER['REQUEST_URI'], PHP_URL_PATH));
define('API_BASE_URL', $scheme . '://' . $_SERVER['HTTP_HOST'] . $path);

// swagger-php reads the attributes with reflection, so the documentation classes must be loaded first
$files = array_merge([__DIR__ . '/doc_setup.php'], glob(__DIR__ . '/paths/*.php'));
foreach ($files as $file) {
    require_once $file;
}

$openapi = (new \OpenApi\Generator())->generate($files);

header('Content-Type: application/json');
echo $openapi->toJson();

Swagger UI and live requests

The docs index.html loads Swagger UI 5 from the CDN. It fetches the document from the relative URL swagger.php and mounts the interface in #swagger-ui. The Schemas section lists the documented models. The page enables deepLinking and sets persistAuthorization for the Week 7 token workflow.

ServerBase URL used in the reading
XAMPP or WAMPhttp://localhost/campus-events-app/week-06/backend
php -S localhost:8000 server.php in week-06/http://localhost:8000/backend

Open {base}/public/v1/docs/. Expand an operation, choose Try it out, enter values and click Execute. The UI shows the curl command, request URL, status, response body and headers. Open {base}/public/v1/docs/swagger.php to see the raw JSON.

  • GET /events/{id} with id 1 returns 200 and the Welcome Concert. With id 999 it returns 404 and {"error":"Event not found."}, exactly as documented.
  • GET /weather/forecast with the city Xqzzyy returns 404 and {"error":"No city called 'Xqzzyy' was found."}. This request goes on to Open-Meteo, so it needs internet; without internet you get the documented 503 with {"error":"The weather service is not available at the moment. Please try again later."}.

Careful. "Try it out" works on real data. A POST really inserts a row, and a DELETE you execute in Swagger UI really deletes it. DELETE /events/1 answers 400 only because students are registered for that event; an event without registrations is deleted.

Not everything in the backend is documented, on purpose. The step-by-step demo routes from Week 5 (/get_events, /v2/events, ...) and /weather/v1/forecast are only there to compare versions in the lecture, so they have no attributes and do not appear in Swagger UI. docs/api.http contains ready-made requests for the documented routes and for some of the demo routes, which you can send from VS Code (REST Client extension) or PhpStorm.

A look ahead to Week 7. Some routes will need a login token. OpenAPI describes that as a security scheme: you declare it once in doc_setup.php, Swagger UI then shows an Authorize button, and the token is sent in the header Authorization: Bearer <token>. index.html already contains persistAuthorization: true, which makes Swagger UI remember the token after a page reload.

    bearerFormat: 'JWT'
)]

Debugging and keeping docs in sync

Common mistakeWhat you see and how to fix it
FlightPHP syntax in the path: /events/@id in the attribute.swagger-php accepts it without a warning. Swagger UI still shows an id field, but the value is never put into the URL: "Try it out" sends GET /events/@id and gets 404 {"error":"Endpoint not found."}. OpenAPI needs /events/{id}.
A path parameter is not described with OA\Parameter, or has a different name than in the braces.Declare it with the same name as in the braces and in: 'path'.
Forgot use OpenApi\Attributes as OA; at the top of a paths file.There is no visible error: the endpoints of that file are simply missing from Swagger UI.
Misspelled argument name, e.g. summry: instead of summary:.php -l finds nothing, because the syntax is valid. swagger-php skips the whole class and only writes a warning to the server log (Skipping unloadable \EventPaths: Unknown named parameter $summry), so all endpoints of that file disappear.
A missing comma or bracket inside an attribute.A PHP syntax error: swagger.php answers 500 with an empty page and Swagger UI says "Failed to load API definition". Run php -l public/v1/docs/paths/EventPaths.php to find the line.
Wrong schema name in ref, e.g. #/components/schemas/Events.swagger.php still returns the JSON and Swagger UI shows no error, but the example value is only "string". The only message is a warning in the server log: $ref "#/components/schemas/Events" not found. Names are case-sensitive.
Hard-coded server URL, e.g. OA\Server(url: 'http://localhost/project/backend') while you run php -S localhost:8000."Try it out" sends the request to an address that does not exist and shows "Failed to fetch". That is why the project calculates API_BASE_URL from the request.
A server field in the input schema, e.g. available_seats in EventInput.The service sets it from capacity; it belongs to Event (output) only.
Documentation that no longer matches the code: the route returns 201 but the attribute says 200.Change the attribute in the same commit as the route.
Only the 200 response is documented.Add 400, 404 and 503 where they can happen; look at the exceptions the service throws.
Properties copied into every route.Define the schema once in doc_setup.php and use ref.
Composer run in the wrong folder, or vendor/ missing after a clone.composer.json is in backend/; run Composer there. Without vendor/, PHP stops at require .../vendor/autoload.php. Run composer install.

Where is the server log? With the PHP built-in server the warnings appear in the terminal where php -S runs; with XAMPP they go to the PHP or Apache error log. After every change: open Swagger UI, use "Try it out" and compare the result with the documentation.

Summary and Check Yourself

  • Standardisation: OpenAPI provides a standard way to design and document RESTful APIs.
  • A complete description: the specification defines endpoints, operations, data models and security details.
  • Interactive documentation: Swagger UI generates documentation you can read and test in the browser, which makes collaboration easier.
  • Documentation next to the code: PHP attributes, read by swagger-php, keep the documentation inside the codebase, so it is updated together with the code.
  • Easy installation: one Composer package, zircote/swagger-php, recorded in composer.json and composer.lock.

Try to answer before you open an answer. These are the kinds of questions you will meet in the quiz.

1. What is the difference between OpenAPI and Swagger?

OpenAPI is the specification (the standard format). Swagger is a family of tools that work with it, such as Swagger UI.

2. Name four top-level parts of an OpenAPI document and say what each contains.

info (title, version), servers (base URLs), paths (endpoints and their operations), components (reusable schemas and security schemes). tags is a fifth.

3. In which two formats can an OpenAPI document be written?

JSON or YAML.

4. What is the difference between the design-first and the code-first approach?

Design-first: write the document, then the code. Code-first: write and document the code, then generate the document.

5. Which command adds swagger-php to a project, and which command installs the versions from composer.lock?

composer require zircote/swagger-php adds it; composer install installs exactly what composer.lock records.

6. What does "zircote/swagger-php": "^6.12" allow?

Version 6.12.0 and every later 6.x version, but not 7.0.

7. Why is vendor/ not committed to Git?

It can always be recreated with composer install from composer.json and composer.lock.

8. How is the FlightPHP route GET /events/@id:[0-9]+ written in an attribute?

path: '/events/{id}', with an OA\Parameter named id and in: 'path'.

9. Which attributes describe the JSON body of a POST request?

OA\RequestBody with OA\JsonContent inside it, usually with ref to an input schema.

10. Why are there two schemas, EventInput and Event?

EventInput is what the client sends; Event is what the API returns: the input fields plus server fields such as id and available_seats, combined with allOf.

11. What does swagger.php do, and what does Swagger UI do with its output?

swagger.php loads doc_setup.php and paths/*.php, lets swagger-php scan the attributes and prints the OpenAPI document as JSON. Swagger UI reads that JSON and draws the interactive page.

12. A colleague says: "The docs say POST /events returns 200, but I get 201." What happened, and how do you prevent it?

The code and the documentation are out of sync. Change the route and its attribute in the same commit, and check Swagger UI after every change.

13. Why should you be careful with "Try it out" on a DELETE endpoint?

It sends a real request, so the data is really deleted. Use a row you are allowed to delete.

Glossary

API documentationA description of the endpoints of an API: what to send and what comes back.
OpenAPI Specification (OAS)The standard format for describing REST APIs, in JSON or YAML.
SwaggerA family of tools built around OpenAPI.
Swagger UIA web page that shows an OpenAPI document as interactive documentation.
swagger-phpA PHP library (zircote/swagger-php) that generates an OpenAPI document from attributes or annotations in your code.
AnnotationMetadata written in a doc comment above code and read by a tool, e.g. @OA\Get(...).
AttributeThe built-in PHP 8 syntax for metadata on code: #[...].
ComposerThe dependency manager for PHP.
composer.jsonLists the libraries a project needs and which versions are allowed.
composer.lockRecords the exact installed versions, so everybody installs the same.
vendor/The folder where Composer puts the libraries and autoload.php.
PathOne URL of the API, for example /events/{id}.
OperationOne HTTP method on a path, for example GET /events/{id}.
SchemaThe description of the shape of data: its properties and their types.
ComponentA reusable part of an OpenAPI document, such as a schema or a security scheme.
$ref / refA reference to a component, for example #/components/schemas/Event.
allOfCombines several schemas into one.
TagA label that groups operations in the documentation.
YAMLA text format that uses indentation instead of brackets; often used for OpenAPI files.
